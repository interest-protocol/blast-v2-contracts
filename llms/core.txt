# Blast contracts: Shared core integrator reference

> Everything an integrator needs to understand and call Blast's shared money vocabulary on Sui: basis points and exact apportionment, outright and vested payouts, LP-fee splits, the protocol-fee ledger with partner cuts, the treasury, Merkle proofs, and the sealed migration hand-off between a sale and its venue. Sui mainnet only.

This file is self-contained: give it to an AI agent and ask it anything about Shared core. It also covers the packages its calls depend on: `blast_partners`, `blast_admin`. Other products are in [llms-full.txt](https://github.com/interest-protocol/blast-v2-contracts/blob/main/llms-full.txt), which joins every product in one file.

How it is organized:

1. **Packages and deployment status**: each package, whether it is live on Sui mainnet, and its IDs.
2. **Guides**: how each product works end to end, starting with the calling conventions every product shares. Each product guide opens with its deployment status. Use them for behavior, flows, economics, and pitfalls.
3. **API reference**: generated from the Move source. Every public function and type with its doc comment, every event, every abort code, and the package constants. Use it for exact signatures and field layouts.

When the guides and the reference disagree, the reference is right: it is generated from the source on every change. When this file does not say a behavior exists, treat it as unsupported. Source for every module is linked from the reference ([repository](https://github.com/interest-protocol/blast-v2-contracts)).

Conventions: amounts are atomic units of the coin named; rates are basis points (BPS) out of 10,000; timestamps are Unix milliseconds from Sui's shared `Clock` at `0x6`, while durations and delays are elapsed milliseconds. Types are written as Move: `module::Type` names a type in another module of the same package, `package::module::Type` one in another Blast package, and well-known Sui framework types appear bare.

## Calling Blast contracts

Every Blast product is a set of Sui Move packages called from programmable
transaction blocks (PTBs). This section covers what every product shares. Each
product guide below assumes it.

### Products and packages

| Product | What users do | Packages |
| --- | --- | --- |
| Presale | commit Quote to a capped or overflow sale, claim tokens or refunds, earn LP fees and holder rewards after migration | `blast_presale`; the shared venues `blast_migrators`; one-off partner venues such as `blast_aftermath_dao_presale`; `blast_vault` (LP vault, holder rewards) |
| Launchpad | launch a coin on a bonding curve, trade it, graduate it into a DEX pool | `blast_fun` (curve, lifecycle, fees), a generated coin package per launch, `blast_migrators` (Cetus and Bluefin venues for both products: venue start, migration, LP fees), `blast_vault` (LP vault, holder rewards) |
| Partner codes | earn a share of Blast's fee on the flow an app brings | `blast_partners` |
| Boosts | hold a leveraged long or short coin backed by Aftermath perpetuals | `blast_boosts_core`, `blast_boosts_products`, `blast_boosts_aftermath` |
| blastSUI | stake SUI with one validator through funSUI and blastSUI | `blast_sui` |
| Administration | Blast's operators manage roles, fees, and upgrades | `blast_admin` |

Each package and what it depends on:

```text
blast_migrators              -> blast_core, blast_vault, blast_admin, Cetus, Bluefin
blast_aftermath_dao_presale  -> blast_core, Aftermath AMM
blast_fun                    -> blast_core, blast_partners, blast_admin
blast_presale                -> blast_core, blast_partners, blast_admin
blast_vault                  -> blast_core, blast_partners, blast_admin
blast_core                   -> blast_partners, blast_admin, blast_fun_vesting
blast_partners               -> blast_admin
blast_boosts_aftermath       -> blast_boosts_core, blast_partners, blast_admin, Aftermath perpetuals
blast_boosts_core            -> blast_admin
blast_sui                    -> blast_admin, Sui system
blast_admin                  -> Sui framework only
```

No product imports a venue or the vault, and no venue imports a product. They
compose inside one PTB through `blast_core` values: a venue's `prepare` returns
the `VenueTicket` the product's creation call redeems, and at migration the
product's `migrate` returns the `Migration` that the next command passes to the
stored venue's `migrate`, which locks the liquidity in a
`blast_vault::vault::Vault`.
Use the presale guide for presale calls.

`blast_fun_vesting` (used by `blast_core` for vesting payouts) lives in this repository at
`sui/utilities/vesting` and is immutable on mainnet. The standalone
OTC package lives at `sui/utilities/otc`. See the [utility integration guide](https://github.com/interest-protocol/blast-v2-contracts/blob/main/docs/utilities.md).

### Time values

Timestamp parameters ending in `_at_ms` are points in time measured in Unix
milliseconds. Duration parameters ending in `_duration_ms` are lengths of time;
`_delay_ms` parameters are offsets from the documented anchor. For example,
`commitment_starts_at_ms + commitment_duration_ms` is the commitment window's
end timestamp. Stored fields and event payloads retain their published names;
read their documented meaning rather than assuming every `_ms` value is a
timestamp. Framework calls such as `Clock::timestamp_ms` retain their native
names.

### Building a call

- **Target.** A call is `moveCall` with target
  `<package-id>::<module>::<function>`. Use the package ID (`published-at`) from
  the deployment table.
- **Type arguments.** Pass fully qualified type strings. A Blast type is named by
  the package that first defined it (`original-id`), even after an upgrade.
- **`TxContext`.** A trailing `ctx: &TxContext` or `&mut TxContext` parameter is
  supplied by Sui. Leave it out of the arguments.
- **Shared objects.** Pass a shared object by ID. A `&` parameter takes it
  read-only, `&mut` or by value takes it mutably; mutable access orders the
  transaction through consensus with every other writer of that object.
- **System objects.** `Clock` is `0x6` (always `&Clock`), the Sui system state is
  `0x5`, and the Coin Registry is `0xc`.
- **Coins in.** A function that takes `Coin<T>` by value consumes it whole. Split
  the exact amount first (`SplitCoins`; for SUI, split from the gas coin) and
  merge several coins first when needed (`MergeCoins`).
- **Values out.** Most Blast functions return coins and objects instead of
  transferring them. Every returned value without the `drop` ability must be used
  before the PTB ends: transfer it (`TransferObjects`), pass it to a later call,
  or merge it. A value with no abilities at all (a "hot potato", such as a
  launch initializer or a migration handoff) can only be consumed by the specific
  later call that accepts it, so the whole sequence must sit in one PTB.
- **Basis points.** The launch products and the vault share one validated
  `Bps` type, `blast_core::bps::Bps`. Build one inside the PTB with
  `blast_core::bps::new`, which aborts above 10,000.
- **Options.** Pass `Option<T>` arguments with `0x1::option::some` or
  `0x1::option::none` calls, or as pure BCS-encoded options.

### Reading state

- **Getters** are public functions that take `&` objects and return values. Run
  them through a dev-inspect or simulated transaction to read without signing
  or paying.
- **Object fields** can be read directly from a full node and decoded with BCS.
  The API reference prints every struct with its fields in declaration order,
  which is the BCS order. Fields are readable on chain even though Move code
  outside the module cannot access them.
- **Per-user records** (commitments, claims) usually live in dynamic fields
  keyed by a small key struct the reference lists; read them with the
  dynamic-field RPC calls.
- **Events** reconstruct history; contract state and completed events are the
  source of truth, and any off-chain preview is an estimate.

### Versions and upgrades

Upgrade rules depend on the package lineage.

| Posture | Packages | What callers do |
| --- | --- | --- |
| Shared UpgradeCap manager | `blast_admin`, `blast_partners`, `blast_core`, `blast_aftermath_dao_presale` | The manager holds the compatible UpgradeCaps. Each upgrade or immutability request waits 48 hours. The Blast multisig holds the controller. |
| Immutable | `blast_boosts_core`, `blast_upgrade_cap_manager` | The code never changes. |
| Dependency-only | Historical presale publications | These older lineages can relink venue packages and do not use a version object. |
| Version-gated | `blast_presale`, `blast_fun`, `blast_vault`, `blast_migrators`, `blast_sui`, `blast_boosts_aftermath` | Mutating calls take the package's shared version object (for the launch packages, `blast_admin::package_version::PackageVersion<OTW>`). After an upgrade advances it, calls through an older package ID abort with a version mismatch, so always call the current ID. `blast_vault` is made immutable after its audit. |
| Additive | `blast_boosts_products` | Upgrades only add product tags; it holds no state. |

### Events

- Query events by their Move type, named with the `original-id`.
- `blast_sui` and `blast_boosts_aftermath` wrap every payload in the `Event<T>`
  envelope of their own `blast_events` module (for example
  `blast_sui::blast_events::Event`), so the event type is
  `<original-id>::blast_events::Event<<original-id>::<module>::<Payload>>`.
  Every other package, the launchpad included, emits payload structs directly.
- Sui orders events by checkpoint, transaction, and event index within the
  transaction; payloads carry no sequence numbers of their own.
- The reference lists every event struct under its module with its fields.

### Errors

A failed call returns a Move abort naming the module and function that aborted
and a `u64` code. Blast uses two styles:

- **Named errors** (`#[error]` constants): `blast_aftermath_dao_presale`. Sui's RPC and SDKs
  decode these into the constant's name and message; the reference lists each
  module's constants with their messages.
- **Numeric codes**: `blast_admin`, `blast_partners`, `blast_core`, `blast_vault`,
  `blast_fun`, `blast_presale`, `blast_migrators`, `blast_sui`, `blast_boosts_core`,
  and `blast_boosts_aftermath` abort with small integers. Look the
  number up in that package's abort-code table in the reference.

The abort names the module where it happened, which may be a package called
underneath the one you called: a migrator call can abort inside `blast_core`,
`blast_vault` or `blast_admin`, and an abort in a Cetus, Bluefin, or Aftermath
module comes from the venue. Simulate a transaction before signing to see its abort without
spending gas.

### Network

Blast deploys only to Sui mainnet. There is no testnet deployment, faucet, or
test address. Try a transaction with a mainnet simulation (dev-inspect or dry
run) before signing it.

## Shared core

> **Deployment status:** `blast_core` is live on mainnet, published from an earlier revision; the source described here has changed since, so confirm signatures against the live package.

### What it is

Package `blast_core` holds the money building blocks every Blast launch product shares, each
defined once: a basis-points unit and its exact apportionment, outright or vested payouts, the LP-fee split, the ledger that holds Blast's fees and pays the partner's cut,
the one treasury address, Merkle proofs, and the sealed values that carry a sale's liquidity to its
venue and prove a sale's ownership to its vault. It holds no user funds of its own. Products and
vaults embed its values and call it; integrators read its events and build PTBs that pass its
values between product and venue calls.

### Units and payouts

- `blast_core::bps::Bps` is a rate from 0 to 10,000 basis points; `blast_core::bps::new` aborts
  above 10,000. `blast_core::bps::apply_up` applies it rounding up.
- `blast_core::bps::apportion` splits an amount over rates that sum to exactly 10,000 by largest
  remainder: every part takes its floor, an optional named part takes its ceiling, and the
  leftover units go one each to the largest remaining remainders, earlier parts first. The parts
  always sum to the amount.
- Every launch package uses one basis-points denominator, `blast_core::constants::basis_points_denominator`
  (10,000), and one cap on Blast's share of LP fees, `blast_core::constants::max_lp_fee_bps`
  (3,000 per asset). The bounds core's constructors enforce are public too:
  `blast_core::constants::max_routes` (20 routes per fee split) and
  `blast_core::constants::max_vesting_duration_ms` (2^63 ms). All four are public compile-time
  macros.
- A `payout::Recipient`, built with `payout::recipient`, is a nonzero destination address and
  optional `payout::VestingTerms` (from `payout::vesting_terms`); the zero address aborts.
  `payout::pay_or_vest` pays an amount to a recipient as a coin or, when it vests, locks the amount
  in an irrevocable, shared `blast_fun_linear_vesting::Vesting` schedule that starts at the payout
  and returns its ID. A zero amount sends and locks nothing. Each product keeps its own recipient
  lists and shares. `payout::destination` and `payout::recipient_vesting_terms` (called as
  `recipient.vesting_terms()`) read a recipient; `payout::cliff_delay_ms`,
  `payout::period_duration_ms`, and `payout::periods` read its terms.

### Fee splits

`fee_split::FeeSplit` is a list of up to 20 routes summing to 10,000. Each route has a positive
share and a `fee_split::Destination`: an address, the vault's owner, auto-LP, holder rewards, or
burn. No address and no special kind appears twice. `fee_split::apportion` divides one collection
across the routes in order.

### Protocol fees, partners, and the treasury

`protocol_fees::Ledger` holds Blast's Meme, Quote, and SUI fees for one launch, presale, or vault.
Only the module that owns it can create it, under its package witness, and every payment event
names that witness type, so a payment's origin is attributable.
`protocol_fees::new` borrows the origin object's UID and records its ID. Here `origin` identifies
the launch, presale, or vault the fees came from; it does not identify the beneficiary or grant
owner authority.
`protocol_fees::take_cut` moves Blast's rounded-up cut of a fee into it. A ledger is bound at
creation to the partner its sale named, or to none. `protocol_fees::pay` pays everything to the
treasury and aborts when a partner is bound; `protocol_fees::pay_with_partner` first pays that
partner its cut of each asset through `blast_partners::blast_partners::pay`, then the treasury the
rest. Both emit `blast_core_events::ProtocolFeesPaid`; an empty ledger sends and emits nothing. Products expose these payouts as calls anyone
may make. `protocol_fees::balances`, `protocol_fees::package_witness`, `protocol_fees::origin`, and
`protocol_fees::partner_id` read a ledger. `protocol_fees::destroy` deletes one that holds nothing
and aborts while any fee is held, so it must be paid out first.

`blast_treasury::Treasury` is a shared singleton holding the address Blast's fees go to. A Blast
admin with `blast_domain::TreasuryAdmin` schedules a new address with
`blast_treasury::schedule_destination`; anyone applies it with `blast_treasury::apply_destination`
once its notice has passed (48 hours from publication); a Blast admin with
`blast_domain::CancelAdmin` cancels it with `blast_treasury::cancel_destination`. Read the current
address with `blast_treasury::destination`, the notice the next change waits with
`blast_treasury::delay_ms`, and a scheduled change, as a `delayed::Proposal<address>`, with
`blast_treasury::pending_destination`. `blast_treasury::is_destination_ready` takes the `Clock` and
returns whether `blast_treasury::apply_destination` would succeed now: a change is scheduled, the
clock reads its `ready_at_ms` or later, and the clock plus its next notice still fits in a `u64`;
it returns false with nothing scheduled, before `ready_at_ms`, and after a cancel or an apply. The
treasury is never deleted: every ledger pays through it.

### Migration hand-off and owner proof

- Before a sale's supply is minted, its venue prepares the coin and returns a
  `migration::VenueTicket` for the sale's exact Meme and Quote pair, sealed by the venue's witness
  (`migration::issue_ticket`), so a ticket cannot start a sale of another coin or Quote. The venue
  keeps the pair's pool tier. The product's creation call redeems the ticket with `migration::redeem_ticket`
  and stores the venue.
- `migration::VaultTerms` are a vault's terms: the sale, the package witness that sealed them, the fee
  split, Blast's LP-fee shares, the partner, and whether residuals go to Blast or the owner.
  `migration::vault_terms` borrows the sale's `&UID` under the issuing package's witness and records its ID.
  It aborts when either of Blast's LP-fee shares exceeds 3,000 basis points, so every sealed term is within the cap.
- At migration the product creates a `migration::Migration` with `migration::new`, sealed by its own witness, holding the
  pool's Meme and Quote and terms the same package witness sealed. Only the stored venue can consume it,
  with `migration::redeem`; any other venue aborts.
- `owner_proof::OwnerProof` is a product's sealed statement that the caller holds the sale's
  creator authority, issued with `owner_proof::new` by borrowing the sale's `&UID` after checking
  that authority. The proof records the sale's ID. A vault consumes it with
  `owner_proof::assert_terms`, which aborts unless it names
  the vault's package witness and sale.

`VenueTicket`, `Migration`, and `OwnerProof` cannot be dropped, copied, or stored, so the PTB
that creates one must consume it. `VaultTerms` can be copied and stored.

Readers never consume them. `migration::ticket_venue` (called as `ticket.venue()`) reads a ticket's
venue. `migration::venue`, `migration::balances` (the Meme and Quote amounts), and
`migration::terms` read a migration; only `migration::redeem` releases its balances, and a copy of
its terms authorizes nothing, since an admitted venue never takes terms from its caller and each
sale has one vault. `migration::origin`, `migration::package_witness`, `migration::fee_split`,
`migration::protocol_bps`, `migration::partner_id`, and `migration::residuals` read terms;
`migration::is_protocol` and `migration::is_owner` read the `migration::ResidualPolicy` it
returns. `owner_proof::package_witness` and `owner_proof::origin` read
a proof.

### Sealed treasury caps and venue admissions

A product keeps a generated coin's `TreasuryCap` out of every hand but its own from the coin's
publication until the sale starts, so no one mints before the sale. The seal is
`sealed_treasury_cap::SealedTreasuryCap<Coin>` (`key, store`, wallet-held and transferable): the
product's own currency-creation call (`launch_ticket::new` for a launch, `blast_presale::sale_token::new` for a sale token)
wraps the fresh cap with `sealed_treasury_cap::new` under its package witness, and the publisher
receives the sealed cap. Only that product's witness opens it, through
`sealed_treasury_cap::into_treasury_cap`, which the product's `new` calls; a caller with another
witness aborts with `blast_core::errors::EWrongPackageWitness` (code 10).

A venue that must touch the cap while preparing the coin (Cetus mints its pool-creation capability
from it) borrows it with `sealed_treasury_cap::treasury_cap_mut`, presenting its own witness and
a `sealed_treasury_cap::VenueAdmission`: the product's droppable proof that it admits that venue,
issued under its package witness by `sealed_treasury_cap::venue_admission` after the product
checked its own venue allowlist (`launch_config::venue_admission` and
`creation_policy::venue_admission`, both *anyone*, abort with the product's venue-not-allowed
error). The borrow aborts with `blast_core::errors::EWrongPackageWitness` (code 10) when the admission
comes from a product other than the one that sealed the cap, and with
`blast_core::errors::EVenueNotAdmitted` (code 14) when the admission names another venue. A reference
result never leaves Move code, so only the venue's own call reaches the cap.

Readers: `sealed_treasury_cap::package_witness`, `sealed_treasury_cap::treasury_cap_id`, and
`sealed_treasury_cap::total_supply` read a sealed cap; `sealed_treasury_cap::admission_package_witness`
(called as `admission.package_witness()`) and `sealed_treasury_cap::admission_venue` (`admission.venue()`)
read an admission.

### Pool seed price

`migration::sqrt_price_x64` derives the price a concentrated-liquidity venue (Cetus or Bluefin)
seeds a migrated pool at, from the migration's atomic Meme and Quote amounts:
`floor(sqrt(B / A) * 2^64)`, where B / A is Quote / Meme when Meme is coin A and Meme / Quote
otherwise. Display decimals never enter it, and the divisor amount must be positive.
`migration::is_seedable_price` says whether both venues can seed a full-range pool at that price:
it must lie within half of their shared sqrt-price range (from 2 x 4,295,048,016 to
79,226,673,515,401,279,992,447,579,055 / 2). A product uses it to refuse a sale that could never
migrate. Both are pure reads anyone may call.

### Merkle proofs

`blast_core::merkle::verify` checks a positional Blake2b-256 proof of a leaf digest at an index. Leaves hash
as `blake2b256(0x00 || domain || payload)` with `blast_core::merkle::leaf`, where each tree's
purpose names its own domain string; internal nodes hash as `blake2b256(0x01 || left || right)`;
an odd node at any level is its own sibling. Malformed roots, digests, or siblings,
an empty tree, an index outside it, or a proof of the wrong depth return false instead of aborting.

### Roles

`blast_domain` declares Blast's product roles for the shared ACL: `TreasuryAdmin`, `FeeAdmin`,
`ListingAdmin`, `VenueAdmin`, `RewardsAdmin`, `BuybackAdmin`, `AutoLpAdmin`, `CreatorAdmin`,
`ClaimSignerAdmin`, and `CancelAdmin`. Only Blast admins hold them.

### Errors

Every abort is a small integer from the package's numeric registry; the reference lists each code.
The abort names the module that raised it.

## API reference: `blast_core` (Shared core)

Live on mainnet, published from an earlier revision. The source documented here has changed since; until it is republished, confirm signatures against the live package.

Events: payload structs are emitted directly, each under its own type.

Abort codes: this package aborts with the numeric codes below from whichever module detects the failure; the abort location names that module.

| Code | Constant | Meaning |
| --- | --- | --- |
| 0 | `EInvalidBps` | A basis-points rate must be at most 10,000. |
| 1 | `EInvalidApportionment` | Apportioned rates must sum to 10,000 and name a rounded-up part inside them. |
| 2 | `EInvalidVestingTerms` | Vesting needs positive steps whose total and cliff fit the technical bound. |
| 3 | `EInvalidRoute` | A route needs a positive share and a nonzero address. |
| 4 | `EInvalidFeeSplit` | A fee split needs at most 20 distinct routes summing to 10,000. |
| 5 | `EInvalidTreasury` | The treasury must be a nonzero address. |
| 6 | `EInvalidPair` | The Meme and Quote types must differ. |
| 7 | `EPartnerMismatch` | Blast's fees pay with exactly the partner the sale named, or with none. |
| 8 | `EWrongVenue` | Only the venue the sale stored can redeem its migration. |
| 9 | `EWrongOwner` | The owner proof must name the vault's package witness and sale. |
| 10 | `EWrongPackageWitness` | The package witness must be the one that sealed the vault terms or the treasury cap. |
| 11 | `EInvalidLpFeeBps` | Blast's LP-fee share of each asset must be at most 3,000 basis points. |
| 12 | `EInvalidRecipient` | A payout recipient must be a nonzero address. |
| 13 | `ELedgerNotEmpty` | A ledger must hold no fees to be destroyed. |
| 14 | `EVenueNotAdmitted` | A venue borrows a sealed treasury cap only with the sealing product's admission of that venue. |

### `blast_core::blast_domain`

Blast's product administration roles in the shared Blast ACL, one set for the launchpad, the presale, the vault, and the venues (ADR 0137). An `AdminCap` holding `Role` signs in to `AdminWitness<Role>`, and a function's witness parameter names the one role it accepts, so no role authorizes another's actions.

### `blast_core::migration`

The sealed contract between a sale and the venue that migrates it.  Before supply leaves the sale's `TreasuryCap`, a venue prepares the coin and returns a `VenueTicket` sealed by its witness; the product admits and stores the ticket's venue. At migration the product creates a `Migration` sealed by its own witness, carrying the pool's balances and the new vault's terms, and only the stored venue's witness can redeem it. Neither the ticket nor the migration can be dropped, copied, or stored, so a transaction completes the migration whole or aborts.  Every witness is identified by `type_name::with_original_ids`, which stays fixed across upgrades of the venue or product package; allowlists that admit these names must use the same form.  The module also derives the price a concentrated-liquidity venue seeds the pool at, and whether both such venues can seed it, so a product can refuse a sale that could never migrate.

Source: https://github.com/interest-protocol/blast-v2-contracts/blob/main/sui/launch/core/sources/migration/migration.move

### `blast_core::sealed_treasury_cap`

A coin's `TreasuryCap` sealed by the product that created the currency, from publication until that product's `new` opens it.  The seal closes the window in which a coin's creator could mint before a sale starts: between publication and the venue's preparation of the coin, which borrows the cap to reserve the pair's pool creation, the holder of a sealed cap can only hand it to a venue the sealing product admits. ### `blast_partners::blast_partners`

Blast partner codes, shared by every Blast product.  A partner is one deal: it is paid a share of the fee Blast charges on every trade that names it, in the same transaction. A company holds one `PartnerCap` for all its deals, each a separate partner with its own share. Blast's partner administrator registers partners under a cap, proposes each one's share, and can propose moving a partner to another cap; the cap's holder sets where each of its partners is paid. Initial terms apply at registration. A later share or cap applies only when someone applies it, no sooner than `PARTNER_CHANGE_DELAY_MS` after it was proposed. That delay is fixed: this module never changes it, and the package is published immutable. The recipient the cap holder sets applies at once.  Products call `pay` with Blast's own fee on a trade. `pay` emits `PartnerPaid` for what the partner received; the product records the trade and the amount in its own event. Share and cap lifecycle events come from `blast_admin::delayed`, keyed by `ShareKey` and `CapKey` and owned by the partner.

Source: https://github.com/interest-protocol/blast-v2-contracts/blob/main/sui/launch/partners/sources/blast_partners.move

### `blast_partners::partner_list`

The partners one Blast product accepts, one list per product.  A product embeds a `PartnerList` in the object holding its policy and alone decides who may change it: the list has `store` and no authority of its own, so only the embedding module can reach it mutably. Adding a partner accepts it at once. Removing one keeps it accepted for the fixed delay Blast gives for every change to a partner, `blast_partners::delay_ms()`, so anything built to name it keeps working that long. Sales and trades that already name a removed partner keep paying it; the list only gates naming it anew. Destroying the list ends every acceptance at once, without the delay, so a product destroys it only with the object that embeds it.

### `blast_admin::delayed`

Settings that change only after their applied delay, and the deadline rules every delayed type shares.  A timelock in the Compound/OpenZeppelin sense: schedule, wait the applied delay, then apply; cancellable until applied. Settings live here; one-shot actions in `delayed_action`, allowlists in `delayed_set` and keyed values in `delayed_map`.  Every value carries a module-defined key `K` and the ID of the object that stores it. Constructors take that object's `&UID`, which only the code creating or holding the object has, so no package can attribute a value or its events to another's object. Embedding modules use a struct without a public constructor as `K`, so only their module can pack it. Each delayed module emits every lifecycle fact of its type, generic in `K` and carrying `parent`; embedding modules emit only their own side effects.  Every change, a shorter delay included, waits the delay applied when it was scheduled. A delay can start at zero, so a schedule and its apply in one transaction then act as a setter; there is no other mutation path. No delay exceeds `max_delay_ms`, so a delay can always be changed again. Readers need no Clock.

Source: https://github.com/interest-protocol/blast-v2-contracts/blob/main/sui/governance/admin/sources/delayed/delayed.move

### `blast_admin::package_admin`

One package's sealed Publisher and UpgradeCap, its delayed upgrade decisions, and the role-gated pause controls of its `PackageVersion`, typed by the package's one-time witness.  The native capabilities never leave the shared `PackageAdmin`: only the package itself, with its package witness, borrows the Publisher by immutable reference, nothing lends the UpgradeCap, and the cap acts only through a scheduled upgrade or the one terminal `make_immutable`. Each role is generic over the package's OTW, so the ACL stores `UpgradeAdmin<A>` and `UpgradeAdmin<B>` as distinct grants and one package's administrator never reaches another's PackageAdmin. This package is immutable: no consumer bytecode version gates these calls, and a consumer whose new bytecode compiles the wrong version can still schedule a repair.

Source: https://github.com/interest-protocol/blast-v2-contracts/blob/main/sui/governance/admin/sources/package/package_admin.move

```move
/// One package's shared administration, sealing its framework Publisher and UpgradeCap. It has no destructor:
/// deleting it would release or strand the native capabilities it seals.
public struct PackageAdmin<phantom OTW: drop> has key {
    id: UID,
    publisher: Publisher,
    /// Native upgrade authority; `none` once the package is immutable.
    upgrade_cap: Option<UpgradeCap>,
    upgrade: delayed_action::DelayedAction<UpgradeKey<OTW>, UpgradeAction>,
}

/// Schedules and executes the package's upgrades and immutability, and changes their delay.
public struct UpgradeAdmin<phantom OTW> {}

/// May set the package's pause bits immediately, never clear them.
public struct PauseAdmin<phantom OTW> {}

/// May clear the package's pause bits, only through the package's own unpause.
public struct UnpauseAdmin<phantom OTW> {}

/// May cancel the package's scheduled upgrade action or delay change.
public struct CancelAdmin<phantom OTW> {}
```

### `blast_admin::package_version`

One package's publication proof, version and pause bits, typed by its one-time witness.  The consumer's initializer turns its one-time witness into an owned `Publication`, which `package_admin::wrap` later converts into the shared `PackageVersion`, fully paused at version one. The consumer compiles its own version constant and checks it with `assert_current`; it also chooses which pause bits exist and pins its package witness, the one type whose value its own code passes to clear pause bits or to borrow its Publisher. Setting and clearing bits and advancing the version are sealed here and reached only through `package_admin`'s role-gated calls, so no package can build a second version or move a version by any other path.

Source: https://github.com/interest-protocol/blast-v2-contracts/blob/main/sui/governance/admin/sources/package/package_version.move
