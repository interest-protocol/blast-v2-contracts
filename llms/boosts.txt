# Blast contracts: Boosts integrator reference

> Everything an integrator needs to understand and call Boost leverage coins on Sui: mint and redeem leveraged long or short coins backed by Aftermath perpetuals. Sui mainnet only.

This file is self-contained: give it to an AI agent and ask it anything about Boosts. It also covers the packages its calls depend on: `blast_core`, `blast_partners`, `blast_admin`. Other products are in [llms-full.txt](https://github.com/interest-protocol/blast-v2-contracts/blob/main/llms-full.txt), which joins every product in one file.

How it is organized:

1. **Packages and deployment status**: each package, whether it is live on Sui mainnet, and its IDs.
2. **Guides**: how each product works end to end, starting with the calling conventions every product shares. Each product guide opens with its deployment status. Use them for behavior, flows, economics, and pitfalls.
3. **API reference**: generated from the Move source. Every public function and type with its doc comment, every event, every abort code, and the package constants. Use it for exact signatures and field layouts.

When the guides and the reference disagree, the reference is right: it is generated from the source on every change. When this file does not say a behavior exists, treat it as unsupported. Source for every module is linked from the reference ([repository](https://github.com/interest-protocol/blast-v2-contracts)).

Conventions: amounts are atomic units of the coin named; rates are basis points (BPS) out of 10,000; timestamps are Unix milliseconds from Sui's shared `Clock` at `0x6`, while durations and delays are elapsed milliseconds. Types are written as Move: `module::Type` names a type in another module of the same package, `package::module::Type` one in another Blast package, and well-known Sui framework types appear bare.

## Calling Blast contracts

Every Blast product is a set of Sui Move packages called from programmable
transaction blocks (PTBs). This section covers what every product shares. Each
product guide below assumes it.

### Products and packages

| Product | What users do | Packages |
| --- | --- | --- |
| Presale | commit Quote to a capped or overflow sale, claim tokens or refunds, earn LP fees and holder rewards after migration | `blast_presale`; the shared venues `blast_migrators`; one-off partner venues such as `blast_aftermath_dao_presale`; `blast_vault` (LP vault, holder rewards) |
| Launchpad | launch a coin on a bonding curve, trade it, graduate it into a DEX pool | `blast_fun` (curve, lifecycle, fees), a generated coin package per launch, `blast_migrators` (Cetus and Bluefin venues for both products: venue start, migration, LP fees), `blast_vault` (LP vault, holder rewards) |
| Partner codes | earn a share of Blast's fee on the flow an app brings | `blast_partners` |
| Boosts | hold a leveraged long or short coin backed by Aftermath perpetuals | `blast_boosts_core`, `blast_boosts_products`, `blast_boosts_aftermath` |
| blastSUI | stake SUI with one validator through funSUI and blastSUI | `blast_sui` |
| Administration | Blast's operators manage roles, fees, and upgrades | `blast_admin` |

Each package and what it depends on:

```text
blast_migrators              -> blast_core, blast_vault, blast_admin, Cetus, Bluefin
blast_aftermath_dao_presale  -> blast_core, Aftermath AMM
blast_fun                    -> blast_core, blast_partners, blast_admin
blast_presale                -> blast_core, blast_partners, blast_admin
blast_vault                  -> blast_core, blast_partners, blast_admin
blast_core                   -> blast_partners, blast_admin, blast_fun_vesting
blast_partners               -> blast_admin
blast_boosts_aftermath       -> blast_boosts_core, blast_partners, blast_admin, Aftermath perpetuals
blast_boosts_core            -> blast_admin
blast_sui                    -> blast_admin, Sui system
blast_admin                  -> Sui framework only
```

No product imports a venue or the vault, and no venue imports a product. They
compose inside one PTB through `blast_core` values: a venue's `prepare` returns
the `VenueTicket` the product's creation call redeems, and at migration the
product's `migrate` returns the `Migration` that the next command passes to the
stored venue's `migrate`, which locks the liquidity in a
`blast_vault::vault::Vault`.
Use the presale guide for presale calls.

`blast_fun_vesting` (used by `blast_core` for vesting payouts) lives in this repository at
`sui/utilities/vesting` and is immutable on mainnet. The standalone
OTC package lives at `sui/utilities/otc`. See the [utility integration guide](https://github.com/interest-protocol/blast-v2-contracts/blob/main/docs/utilities.md).

### Time values

Timestamp parameters ending in `_at_ms` are points in time measured in Unix
milliseconds. Duration parameters ending in `_duration_ms` are lengths of time;
`_delay_ms` parameters are offsets from the documented anchor. For example,
`commitment_starts_at_ms + commitment_duration_ms` is the commitment window's
end timestamp. Stored fields and event payloads retain their published names;
read their documented meaning rather than assuming every `_ms` value is a
timestamp. Framework calls such as `Clock::timestamp_ms` retain their native
names.

### Building a call

- **Target.** A call is `moveCall` with target
  `<package-id>::<module>::<function>`. Use the package ID (`published-at`) from
  the deployment table.
- **Type arguments.** Pass fully qualified type strings. A Blast type is named by
  the package that first defined it (`original-id`), even after an upgrade.
- **`TxContext`.** A trailing `ctx: &TxContext` or `&mut TxContext` parameter is
  supplied by Sui. Leave it out of the arguments.
- **Shared objects.** Pass a shared object by ID. A `&` parameter takes it
  read-only, `&mut` or by value takes it mutably; mutable access orders the
  transaction through consensus with every other writer of that object.
- **System objects.** `Clock` is `0x6` (always `&Clock`), the Sui system state is
  `0x5`, and the Coin Registry is `0xc`.
- **Coins in.** A function that takes `Coin<T>` by value consumes it whole. Split
  the exact amount first (`SplitCoins`; for SUI, split from the gas coin) and
  merge several coins first when needed (`MergeCoins`).
- **Values out.** Most Blast functions return coins and objects instead of
  transferring them. Every returned value without the `drop` ability must be used
  before the PTB ends: transfer it (`TransferObjects`), pass it to a later call,
  or merge it. A value with no abilities at all (a "hot potato", such as a
  launch initializer or a migration handoff) can only be consumed by the specific
  later call that accepts it, so the whole sequence must sit in one PTB.
- **Basis points.** The launch products and the vault share one validated
  `Bps` type, `blast_core::bps::Bps`. Build one inside the PTB with
  `blast_core::bps::new`, which aborts above 10,000.
- **Options.** Pass `Option<T>` arguments with `0x1::option::some` or
  `0x1::option::none` calls, or as pure BCS-encoded options.

### Reading state

- **Getters** are public functions that take `&` objects and return values. Run
  them through a dev-inspect or simulated transaction to read without signing
  or paying.
- **Object fields** can be read directly from a full node and decoded with BCS.
  The API reference prints every struct with its fields in declaration order,
  which is the BCS order. Fields are readable on chain even though Move code
  outside the module cannot access them.
- **Per-user records** (commitments, claims) usually live in dynamic fields
  keyed by a small key struct the reference lists; read them with the
  dynamic-field RPC calls.
- **Events** reconstruct history; contract state and completed events are the
  source of truth, and any off-chain preview is an estimate.

### Versions and upgrades

Upgrade rules depend on the package lineage.

| Posture | Packages | What callers do |
| --- | --- | --- |
| Shared UpgradeCap manager | `blast_admin`, `blast_partners`, `blast_core`, `blast_aftermath_dao_presale` | The manager holds the compatible UpgradeCaps. Each upgrade or immutability request waits 48 hours. The Blast multisig holds the controller. |
| Immutable | `blast_boosts_core`, `blast_upgrade_cap_manager` | The code never changes. |
| Dependency-only | Historical presale publications | These older lineages can relink venue packages and do not use a version object. |
| Version-gated | `blast_presale`, `blast_fun`, `blast_vault`, `blast_migrators`, `blast_sui`, `blast_boosts_aftermath` | Mutating calls take the package's shared version object (for the launch packages, `blast_admin::package_version::PackageVersion<OTW>`). After an upgrade advances it, calls through an older package ID abort with a version mismatch, so always call the current ID. `blast_vault` is made immutable after its audit. |
| Additive | `blast_boosts_products` | Upgrades only add product tags; it holds no state. |

### Events

- Query events by their Move type, named with the `original-id`.
- `blast_sui` and `blast_boosts_aftermath` wrap every payload in the `Event<T>`
  envelope of their own `blast_events` module (for example
  `blast_sui::blast_events::Event`), so the event type is
  `<original-id>::blast_events::Event<<original-id>::<module>::<Payload>>`.
  Every other package, the launchpad included, emits payload structs directly.
- Sui orders events by checkpoint, transaction, and event index within the
  transaction; payloads carry no sequence numbers of their own.
- The reference lists every event struct under its module with its fields.

### Errors

A failed call returns a Move abort naming the module and function that aborted
and a `u64` code. Blast uses two styles:

- **Named errors** (`#[error]` constants): `blast_aftermath_dao_presale`. Sui's RPC and SDKs
  decode these into the constant's name and message; the reference lists each
  module's constants with their messages.
- **Numeric codes**: `blast_admin`, `blast_partners`, `blast_core`, `blast_vault`,
  `blast_fun`, `blast_presale`, `blast_migrators`, `blast_sui`, `blast_boosts_core`,
  and `blast_boosts_aftermath` abort with small integers. Look the
  number up in that package's abort-code table in the reference.

The abort names the module where it happened, which may be a package called
underneath the one you called: a migrator call can abort inside `blast_core`,
`blast_vault` or `blast_admin`, and an abort in a Cetus, Bluefin, or Aftermath
module comes from the venue. Simulate a transaction before signing to see its abort without
spending gas.

### Network

Blast deploys only to Sui mainnet. There is no testnet deployment, faucet, or
test address. Try a transaction with a mainnet simulation (dev-inspect or dry
run) before signing it.

## Boosts

> **Deployment status:** `blast_boosts_core` and `blast_boosts_products` are live on mainnet, published from an earlier revision; the source described here has changed since, so confirm signatures against the live package. `blast_boosts_aftermath` is not yet published on mainnet; its interface may change before publication.

### What it is

A Boost is a leveraged coin. Each Boost is one Sui coin type,
`Coin<BlastBoost<Product>>`, backed by a single isolated Aftermath perpetuals
position that targets a fixed leverage, for example 2x long NVDA. A user mints
by paying collateral (a six-decimal coin, USDC at launch) and receives shares;
the Vault opens the matching extra position in the same transaction. A user
redeems by burning shares; the Vault closes the proportional position and pays
collateral in the same transaction. Leverage drifts as the price moves; once it
leaves a public band, anyone may call a permissionless rebalance that trades
back toward target. Holders pay all trading costs and funding, a maintenance
reserve inside the venue account absorbs funding costs first, and Blast may
shut a Boost down, after which holders claim the recovered cash pro rata.
Boosts can lose value quickly, and the venue position can be liquidated.

Three packages implement it:

- `blast_boosts_products`: one empty struct per product tag, for example
  `blast_boosts_products::blast_boosts_products::NVDA_BULL_2X`. No state, no
  authority.
- `blast_boosts_core`: venue-neutral policy, lifecycle and accounting
  (`state`, `policy`, `lifecycle`, `observation`). Integrators never call it
  directly; its `State` lives inside the adapter's Vault and only the adapter
  can reach it.
- `blast_boosts_aftermath`: the Aftermath adapter. It owns the share currency,
  the shared `Vault`, the venue account, and every function integrators call
  (the `operations` module and the adapter's `vault` module).

### Objects and authority

#### Product tags and the share coin

- Product tag: an empty struct named `<TICKER>_<SIDE>_<LEVERAGE>` in
  `blast_boosts_products`, for example `NVDA_BULL_2X`, `BTC_BEAR_2X`,
  `XAUT_BULL_2X`. `BULL` means the Vault holds a perp long; `BEAR` means it
  holds a perp short (the inverse). The ticker is the Aftermath base asset
  without its USD suffix. A bull and a bear 2X tag exist for every Aftermath
  market listed on 2026-09-18 (crypto, equities, commodities). A declared tag
  is not a live product until Blast issues its currency.
- Share coin: `Coin<BlastBoost<Product>>`, where `blast_boost::BlastBoost` is
  defined in the adapter. Wallets show it as
  `…::blast_boost::BlastBoost<…::blast_boosts_products::NVDA_BULL_2X>`.
  Shares have **9 decimals**. They are ordinary coins: transferable, splittable,
  usable in any later PTB command. Coin Registry admits one currency per tag.
- The tag name is a label. The Vault's immutable `VaultPolicy` is what fixes
  the side (`policy::PositionSide`, `Long` or `Short`) and the target leverage.
  Read those from the Vault, not from the name.

#### Shared objects

| Object | Type | Created by | Role |
| --- | --- | --- | --- |
| Vault | `blast_boosts_aftermath::vault::Vault<Product, Collateral>` | Blast issuer, once per product | Custody of the core `State`, the bound venue account, the share `TreasuryCap` and `MetadataCap` (dynamic object fields under `TreasuryKey<Product>` and `MetadataKey<Product>`), the locked seed count, earned admin cash, post-shutdown holder cash, and protected cash with no exposed withdrawal path from a size-locked exit. |
| Protocol | `blast_boosts_aftermath::blast_boosts_aftermath::Protocol` | package publish | The adapter's operational generation (ordinary calls require the current generation; upgrade activation requires exactly the next one) and the Boosts acceptance list of canonical Blast partner objects. |
| PackageAdmin | `blast_admin::package_admin::PackageAdmin` | deployment | Sealed Publisher and UpgradeCap of the adapter. |
| Package version | `blast_admin::package_version::PackageVersion` for the adapter | custody wrap | Gates issuance and minting with the deposit pause bit. |
| Blast ACL | `blast_acl::ACL` | `blast_admin` | Role membership for every Blast admin. |

`Vault` fields: `state` (core `state::State<Product>`), `venue_account`
(`venue_account::VenueAccount`: the immutable `binding`, the last accepted
`checkpoint`, and the Aftermath account admin cap, which never leaves),
`locked_shares`, `admin_cash`, `terminal_cash`, and `protected_cash`
(the three cash fields are `Balance<Collateral>`).

#### Aftermath objects a PTB must supply

These are Aftermath's shared objects, not Blast code. Every venue-touching
call takes all of them. The account, registry and clearing house must be
exactly the objects bound at activation (see `venue_account::Binding`); the
two price-feed storages are not bound, and must instead be the storages the
clearing house's market parameters name right now, so a venue-side oracle
re-pointing never strands a Vault:

| Argument | Aftermath type (package `perpetuals` or `oracle_aggregator`) | Binding field |
| --- | --- | --- |
| `account` | `Account<Collateral>`, the Vault's own isolated Aftermath account, created and shared at activation | `account_object_id`, `account_number` |
| `registry` | Aftermath perpetuals `Registry` | `registry_id` |
| `clearing_house` | `ClearingHouse<Collateral>`, the market | `clearing_house_id` |
| `base_oracle` | `PriceFeedStorage` holding the market's base price feed | none; its `storage_id` must equal the market's `base_storage_id` |
| `collateral_oracle` | `PriceFeedStorage` holding the collateral price feed | none; its `storage_id` must equal the market's `collateral_storage_id` |

Pass the shared `ClearingHouse` as a normal shared-object input. Several
functions take it by value and return it after settling the required Aftermath
session. Reuse that result in later PTB commands, then call Aftermath
`clearing_house::share` once after its final use. `operations::realize_profit`,
`operations::rebalance` and `operations::unwind` instead share it internally
and return nothing. These
private `entry` calls accept the shared market directly, never a market returned
by an earlier trading session, and end that market's use in the PTB.
Also pass the `Clock` (`0x6`)
everywhere a call takes one. This ABI requires a fresh publication.

#### Roles

The launchpad and Boosts use the same ACL, fee administrator, treasury administrator, and cancellation role. A Blast admin holding a
`blast_acl::AdminCap` that the ACL granted the role calls
`blast_acl::sign_in<Role>` and passes the returned `blast_acl::AdminWitness<Role>`
to the call. Integrators cannot obtain these witnesses.

| Role | Authorizes |
| --- | --- |
| `blast_boosts_core::blast_boosts_core::VaultIssuer` | `blast_boosts_aftermath::vault::issue` (new Boost), `blast_boosts_aftermath::vault::update_metadata` |
| `blast_boosts_core::blast_boosts_core::RiskAdmin` | Schedule NAV and order caps and rebaseline the venue checkpoint. |
| `blast_core::blast_domain::FeeAdmin` | Schedule vault fees and manage the Boosts list of accepted Blast partners. |
| `blast_core::blast_domain::TreasuryAdmin` | Pay earned collateral to the shared treasury destination. |
| `blast_core::blast_domain::CancelAdmin` | Cancel a pending fee or cap change. |
| `blast_boosts_core::blast_boosts_core::ShutdownAdmin` | `blast_boosts_aftermath::vault::begin_shutdown` |
| Adapter-scoped `blast_admin::package_admin::UpgradeAdmin`, `PauseAdmin`, `UnpauseAdmin`, and `CancelAdmin` | Schedule and execute upgrades, pause deposits, release deposits, or veto a package proposal according to the grant. |

Everything else (mint, redeem, realize profit, rebalance, donate, sync, unwind, finalize,
shutdown claims) is *anyone*. No keeper role, keeper reward, or caller-chosen
trade size exists anywhere.

#### Policy (immutable per Vault)

`policy::VaultPolicy`, fixed at issuance:

- `side`: `Long` or `Short`.
- `rebalance_policy` (`policy::RebalancePolicy`), leverage fields in leverage
  basis points where 10,000 = 1x: `rebalance_below_bps < target_leverage_bps <
  rebalance_above_bps < max_leverage_bps <= 1,000,000`; `max_slippage_bps`
  (ordinary execution bound, in bps of the oracle price)
  `<= emergency_max_slippage_bps < 10,000`;
  `min_leverage_improvement_bps > 0`. Issuance and either live cap update also
  require `min_leverage_improvement_bps * nav_cap <= 16 * max_order_notional *
  10,000` (core code 69). This optimistic bound does not guarantee execution
  after costs or lot rounding. A zero `rebalance_below_bps` disables
  increase-rebalancing. Every order the Vault places is an immediate-or-cancel
  limit order whose price is the oracle price moved by the applicable bound
  against the order and rounded to the market tick back toward the oracle, so
  no fill can cross the bound; the fill's average price is then checked against
  the same bound.
  Each active or unwind market-order fill also creates an internal receipt
  with no abilities. Its checkpoint proof consumes the receipt before the
  operation can finish and returns the checked amounts used for progress.
  This adds no transaction argument or result.
- `price_policy` (`policy::PricePolicy`): `max_price_age_ms > 0`,
  `max_price_ahead_ms <= max_price_age_ms`, `max_confidence_bps < 10,000`,
  `max_mark_divergence_bps < 10,000`.
- Fees: `initial_mint_fee_bps <= mint_fee_cap_bps < 10,000`,
  `initial_redeem_fee_bps <= redeem_fee_cap_bps < 10,000`,
  `admin_share_cap_bps <= 10,000`.
- `min_order_lots`: 2 to 1,000,000; the minimum proportional order in venue lots.
  Two is only the structural floor; each product needs a simulated minimum.
- `max_reserve_bps`: 1 to 10,000; ceiling on the reserve as a share of notional.

Live, adjustable values in `State`: `mint_fee_bps`, `redeem_fee_bps`,
`admin_share_bps` (starts at **0** at activation), `nav_cap`,
`max_order_notional`. Other `State` fields: `maintenance_reserve`,
`uncovered_deficit`, `base_unit` (`10^9`), `collateral_unit` (`10^6`),
`lifecycle`.

### Lifecycle

`lifecycle::Lifecycle` has three states and only moves forward. A Vault exists
only from activation, so it is born `Active`.

| State | Entered by | Allowed |
| --- | --- | --- |
| `Active` | `operations::initialize` | mint, redeem (plain and partner), `realize_profit`, rebalance, `needs_rebalance`, donate, `sync_health`, RiskAdmin `rebaseline`, all admin settings, `begin_shutdown`, `begin_protected_shutdown` |
| `Unwinding` | `blast_boosts_aftermath::vault::begin_shutdown` (ShutdownAdmin) or `operations::begin_protected_shutdown` (anyone, proven size lock) | `operations::unwind`, `operations::sync_health`, `operations::finalize_shutdown`, `apply_nav_cap`, `apply_max_order_notional`, `update_metadata`, `withdraw_admin_fees` |
| `Settled` | `operations::finalize_shutdown` (anyone) | `blast_boosts_aftermath::vault::redeem_shutdown`, `apply_nav_cap`, `apply_max_order_notional`, `update_metadata`, `withdraw_admin_fees` |

`apply_fees` works only in `Active`. Nothing reopens a Vault. Health reporting
(`sync_health`, `CheckpointDrifted`) never changes lifecycle. ShutdownAdmin or
an explicit, proven permissionless size-lock trigger moves `Active` to
`Unwinding`. Entry seals whether settlement protects the seed and reserves.

### Flows

#### Issue and activate a Boost (Blast admin: VaultIssuer)

One PTB, signed by the issuer. `VaultIssuance` has no abilities, so issuance
and activation succeed or fail together.

1. `blast_acl::sign_in` with type argument `VaultIssuer`, the shared `ACL` and
   the issuer's owned `AdminCap` returns the witness.
2. `policy::new_rebalance_policy(...)`, `policy::new_price_policy(...)`, and
   `policy::long()` or `policy::short()` build the parts;
   `policy::new_vault_policy(side, rebalance_policy, price_policy,
   initial_mint_fee_bps, initial_redeem_fee_bps, mint_fee_cap_bps,
   redeem_fee_cap_bps, admin_share_cap_bps, min_order_lots, max_reserve_bps)`
   returns the `VaultPolicy`.
3. `blast_boosts_aftermath::vault::issue<Product, Collateral>` takes `Protocol`, the adapter’s shared `PackageVersion`,
   the witness, the Coin Registry (`0xc`), the policy, `max_order_notional`,
   `nav_cap`, and the coin's `symbol`, `name`, `description`, `icon_url`.
   `Product` must be a non-primitive type. It registers the 9-decimal currency,
   emits `VaultIssued`, and returns a `VaultIssuance<Product, Collateral>`.
4. Split the seed `Coin<Collateral>`.
5. `operations::initialize<Product, Collateral>` takes the issuance, `Protocol`,
   the collateral's Coin Registry `Currency<Collateral>`, the Aftermath
   `Registry` (mutable), the `ClearingHouse`, both `PriceFeedStorage` objects,
   the seed coin, `seed_reserve` (atoms of the seed kept as reserve; must be
   below the seed), `position_imr` (the Aftermath position initial margin
   ratio, a positive IFixed `u256` no greater than one), and the `Clock`.
   Before creating the account it requires that ratio to meet the live market
   minimum and pass a policy-owned safety budget. The budget accounts for the
   live collateral haircut, ordinary plus configured priority trading fees,
   emergency price limit and allowed mark divergence. It assumes fully realized,
   fully allocated equity at the hard cap, with no reserve credit; it is not a
   guarantee against accumulated losses or later exchange changes. It creates and binds
   the Aftermath account, deposits and allocates the whole seed, sets the
   margin ratio, requires the order cap to cover `min_order_lots` live lots
   including price headroom, buys or sells whole lots until the position reaches target
   leverage on the seed NAV (at most 16 limit orders priced inside the
   ordinary bound, each filled completely and within the order cap), settles
   funding, checks the
   activation invariants (positive NAV, fresh prices, matching side, NAV at or
   under `nav_cap`, leverage inside the band, reserve at or under its ceiling,
   base above `lot_size * min_order_lots`), mints the locked seed shares to
   `0x0`, shares the account, and returns `(Vault, ClearingHouse)`. Emits
   `OrderFilled` per seed order and `VaultInitialized`.
6. `blast_boosts_aftermath::vault::share(vault)` shares the Vault. Reuse the
   returned market as needed, then call Aftermath `clearing_house::share`.

Locked seed shares: `locked_shares = seed_shareholder_nav * 1,000` (six-decimal
NAV atoms scaled to nine-decimal share atoms), so the opening price is exactly
1 collateral unit per whole share. They sit at `0x0` forever, count in total
supply, and never redeem.

#### Mint (anyone)

PTB:

1. `SplitCoins` the user's `Coin<Collateral>` into the deposit `cash` (any
   positive amount).
2. `operations::mint<Product, Collateral>(vault, protocol, package_version, account, registry,
   clearing_house, base_oracle, collateral_oracle, cash, minimum_shares,
   deadline_ms, clock)`. Objects: `Vault` (shared, mutable), `Protocol`
   (shared, read), `Account<Collateral>` (shared, mutable), `Registry` (shared,
   read), `ClearingHouse<Collateral>` (shared, by value), both
   `PriceFeedStorage` (shared, read), `Clock`. Returns
   `(Coin<BlastBoost<Product>>, ClearingHouse<Collateral>)`.
3. Reuse the returned market, then call Aftermath `clearing_house::share`.
   `TransferObjects` the shares to the user, or pass them to the next command.
   The coin cannot be dropped.

Parameters: `minimum_shares` is the share floor in share atoms (0 disables it;
set it). `deadline_ms` is inclusive against `Clock`.

What happens, in order, all atomic:

1. Generation, `Active`, positive deposit, and deadline checks.
2. Synchronize: refresh Aftermath's cumulative funding if due, settle the
   position's funding, book it to the reserve (see Funding), and require that
   the venue still matches the accepted checkpoint. Any unexplained change
   aborts (adapter code 31).
3. Price the position at the bound oracle pair; reject stale, future-dated or
   divergent prices, unsafe margin, resting orders, or a paused or frozen
   market.
4. Require leverage **inside** the band, except for a below-band position
   whose fee-aware standalone increase sizes zero even after considering a
   one-lot landing inside the band. This exception cannot bypass cap, margin,
   price or market admission. Other outside-band deposits abort (core code 49).
5. Fee: `fee = ceil(deposit * mint_fee_bps / 10,000)`,
   `admin_fee = floor(fee * admin_share_bps / 10,000)`,
   `reserve_fee = fee - admin_fee`. Expected contribution
   `C_exp = deposit - fee`.
6. Size the order: `base_to_buy = floor(base * C_exp / N0)` rounded down to
   whole lots, where `base` is the current absolute position and `N0` the
   shareholder NAV. The unrounded figure must be at least
   `lot_size * min_order_lots` (core code 12). For the exceptional below-band
   recovery, use a sealed catch-up buy toward target after adding the expected
   contribution, at most one ordinary order cap, and at least the proportional
   amount. Reject a deposit that cannot produce an in-band projected result.
   Actual contribution must still fund the proportional minimum. All catch-up
   execution costs reduce the depositor's credited contribution and shares;
   `minimum_shares` limits that cost. A priority-gas surcharge, if charged by the
   venue, also reduces actual contribution; the sizing projection uses the ordinary
   taker fee. Ordinary deposits retain proportional sizing.
7. Keep `admin_fee` as Vault admin cash; deposit and allocate the rest
   (`deposit - admin_fee`) to the position.
8. Place immediate-or-cancel limit orders in the Vault's direction, priced at
   the oracle moved by `max_slippage_bps` against the order, until exactly
   `base_to_buy` is filled: each order at most the whole-lot base worth
   `max_order_notional` at the highest admitted execution price (with one
   extra normalized price atom for sell rounding), at most 16 orders, each fill
   checked for no resting order, no liquidation, whole lots, actual collateral
   notional at or under `max_order_notional`, and execution price within
   `max_slippage_bps` of the oracle price. A thin book fills part of an order
   and the next order carries the rest; an order that fills nothing aborts
   inside Aftermath.
9. Re-price at the same oracle pair and credit shares (see Economics). Check
   `shares >= minimum_shares`, post-mint NAV at or under `nav_cap`, post-mint
   leverage inside both inclusive rebalance-band edges, using final equity and
   the final reserve after fee credit and clamping, and
   that existing holders' NAV per share did not fall.
10. Mint shares, store the new checkpoint, emit `Minted`.

#### Redeem (anyone)

PTB:

1. Select the `Coin<BlastBoost<Product>>` to burn (split or merge first; any
   positive amount below total supply).
2. `operations::redeem<Product, Collateral>(vault, protocol, account, registry,
   clearing_house, base_oracle, collateral_oracle, shares, minimum_collateral,
   deadline_ms, clock)`. Returns `(Coin<Collateral>, ClearingHouse<Collateral>)`.
3. Reuse the returned market, then call Aftermath `clearing_house::share`.
   `TransferObjects` the collateral to the user.

What happens: the same generation, lifecycle, deadline, synchronize and price
checks as mint (no band check: redemptions work outside the band). The Vault
sells the proportional position reduce-only:
`max_final_base = floor(base * (S - x) / S)`,
`required = base - max_final_base` (at least `lot_size * min_order_lots`
unless `max_final_base` is 0), and `base_to_sell = min(required rounded up to
whole lots, base)`. Orders are limit orders priced inside the ordinary bound
and face the order cap, with an exception for exactly one live venue lot
when closing (see Caps).
It then prices the payout (see Economics), checks `net >= minimum_collateral`
and that the venue can release `net + admin_fee` (adapter code 36 otherwise),
withdraws `net + admin_fee` from the venue (free collateral first, then
deallocation), keeps `admin_fee` as admin cash, burns the shares, emits
`Redeemed`, and returns `net`.

#### Mint or redeem with a partner code (anyone)

`operations::mint_with_partner` and `operations::redeem_with_partner` take the
same arguments as their plain counterparts. Insert the shared `Partner` before the
Aftermath account. On mint the adapter’s `PackageVersion` precedes the partner.
On redemption the protocol precedes the partner.

1. The call first requires the partner to be accepted by Boosts at
   `Clock` time (code 4 in `blast_partners::partner_list` otherwise).
2. It runs the plain operation unchanged: same shares, same payout, same
   reserve fee.
3. It then pays the partner from the admin fee this operation just retained:
   `partner_fee = floor(admin_fee * share_bps / 10,000)`, where `share_bps` is
   the partner's share in force (at most 8,000), through
   `blast_partners::blast_partners::pay`, which sends it to the partner's
   recipient address and emits `blast_partners::blast_partners::PartnerPaid`
   when nonzero. Blast keeps the rest as admin cash. Emits `PartnerFeePaid`
   (even when the payment is zero).

Before building a partner trade, read the acceptance end time for the partner ID in the `Protocol` partner list. The partner is accepted
while the field exists and `now_ms < value` (the value is `u64::MAX` until
Blast removes the partner). Otherwise use the plain calls. While a Vault's
`admin_share_bps` is 0 the partner earns nothing.

#### Realize profit before redemption (anyone; keepers)

`operations::realize_profit<Product, Collateral>(vault, protocol, account,
registry, clearing_house, base_oracle, collateral_oracle, clock)` is a private
`entry` call. Pass the shared market directly; the call shares it internally
and returns nothing. Submit at or below reference gas price. The keeper builder
accepts `operation: 'realize_profit'` with the same bound objects as `rebalance`.

Share value includes paper gains; Aftermath excludes them from cash available
for withdrawal. When free and allocated cash cannot cover the live initial
margin requirement, this operation closes and reopens exactly the same bounded
portion to turn gains into cash. It selects size from authenticated shortfall,
positive profit, live fee, lot size and the existing cap. The caller chooses no
trade size or price bound and receives no reward.

The full cash gap plus rounding headroom must fit within total profit minus a
full-position cost allowance, or recovery is refused before trading. Both orders
must fill fully within ordinary price limits and the opening-order cap. Either failure rolls back everything. Estimated realized profit must exceed
twice the worst-case trading cost; completion requires a smaller cash shortfall,
an allocated-cash gain greater than actual cost, unchanged position size and
side, and final leverage at or below the hard cap. Supply, reserve, funding
deficit, admin cash and lifecycle are unchanged after initial funding settlement.
Actual costs reduce share value for all holders before a fresh redemption quote.

Repeat in separate transactions if the cap requires several steps. Each step
spends cost headroom; a later code 65 stops the sequence until cash, prices or
exposure improve, and raising the cap alone does not remove that check. Quote and
submit redemption afterward with a fresh minimum payout; it still closes exactly
the holder's proportional position and pays the full agreed amount. The cash
check never silently reduces that payout. Recovery may fail for insufficient
two-sided depth, uneconomic profit, inadequate opening margin, emergency leverage
or stale prices. Prices, funding and cash requirements can change before the
later redemption. Reducing maintenance and initial-margin admission are separate from this round trip;
this call does not bypass either. See ADR 0122 and its live execution release gate.

#### Rebalance (anyone; keepers)

`operations::rebalance<Product, Collateral>(vault, protocol, account, registry,
clearing_house, base_oracle, collateral_oracle, clock)`. Anyone can submit this
private `entry` call directly in a PTB. It shares the clearing house internally
and returns nothing; no earlier trading session may supply its market and no
later command may reuse that market. Use a separate transaction for another
rebalance or a mint on the same market. No reward, direction or size argument.
Ordinary rebalances require a gas price **at or below the reference gas
price** (adapter code 34 otherwise). A rebalance whose authenticated starting
leverage is strictly above `max_leverage_bps` may use a higher gas price.
Holders pay Aftermath's configured priority trading surcharge on those fills.
The caller pays the network gas bill. The extra trading rate is set by the
venue; it does not grow with the gas bid.

1. Generation, `Active`; synchronize the checkpoint and validate prices,
   side, positive shareholder NAV, no resting orders and an operational venue.
   The core chooses the direction. An increase requires opening margin; a
   reduction does not, including an ordinary reduction below the hard cap.
2. Read the ordinary market taker fee, rounded up to whole bps (rebates count
   as zero), and prepare the plan. Require leverage strictly outside the band
   (core code 54 otherwise): `notional * 10,000 < N * rebalance_below_bps`
   (increase) or `notional * 10,000 > N * rebalance_above_bps` (reduce).
   Band edges are healthy. A position with no sizeable first order
   aborts early with core code 67 (`rebalance_not_actionable`).
   Mark-versus-oracle divergence is checked only for ordinary plans. Emergency
   status is derived after validating the oracle pair, side and positive NAV;
   the keeper readiness hint uses the same rule.
3. Check the gas price against that prepared plan. Only a plan starting
   strictly above the hard cap is exempt; exactly at the cap is ordinary.
   The decision is fixed for the transaction: its own fills cannot promote an
   ordinary plan into an emergency. Invalid observations and inside-band
   positions can therefore abort before the gas-price check.
4. Up to 16 limit orders, using the core-owned rebalance budget (core code 70
   rejects an additional accepted fill), each priced at the oracle moved by its bound
   against the order. Increase: each order is the largest whole-lot buy that
   keeps post-cost leverage at or under target, using the reserve admitted at
   the resulting total notional and reserving adverse slippage
   (`max_slippage_bps`) and the taker fee on it, capped at
   `max_order_notional`; each fill must leave leverage at or under target and
   under max. If no whole lot fits under target while the position is below
   the band, exactly one lot may instead land inside the full band. Conservative
   cost and resulting-reserve sizing must admit it, and the actual fill must pass both band edges
   (core code 68 otherwise).
   This exception retains the ordinary price bound and order cap.
   Each increase fill and completion recomputes the admitted reserve at its
   actual notional before checking target or the sealed one-lot band exception.
   The recorded reserve is not clamped by rebalance.
   Reduce: size toward target using the reserve admitted at the remaining
   position, capped per order and rounded to whole lots, under
   `max_slippage_bps`. A plan starting above `max_leverage_bps` instead sizes
   toward that hard cap under `emergency_max_slippage_bps`. Target sizing
   uses current equity without a projected cost deduction to avoid excess
   selling on cheaper fills; every subsequent order uses actual fill equity.
   Each emergency order also limits bounded price cost plus the ordinary
   taker fee below current admitted NAV, protecting partial fills as well as
   full fills. The cost allowance also covers one normalized oracle-price
   atom per base unit, its fee, and three collateral atoms for equity capture
   rounding. Recompute that limit after every fill. If no lot fits that
   conservative limit, exactly one lot may use its own reserve release only
   when its resulting NAV remains positive. Stop when no affordable lot
   remains, or when actual leverage is no longer above max; a later ordinary
   call reduces toward target. A final close to zero must leave
   positive holder value after reserving adverse slippage, the ordinary taker
   fee, the same oracle-price precision and capture-rounding allowances, and
   the full recorded reserve. These allowances apply to ordinary flat closes too. Otherwise leave one lot and stop when
   no further close is sizeable; priority-gas costs can still prevent a fill.
5. Before accepting a fill, core requires the order's direction and emergency
   status to match the plan (core code 72 otherwise). The plan determines
   expected position movement and which safety checks apply.
   Every fill repeats the corresponding admission: increases require opening
   margin; reductions may remain below it. An emergency plan keeps its mark-
   divergence exemption through the final cap-restoring fill; fresh oracle
   prices, side and positive NAV are still required. An ordinary plan cannot
   gain this exemption through its own fills, and a later ordinary call must
   pass the divergence check again. Exact fill and checkpoint proofs,
   price limits and execution caps remain enforced. A bounded reduction may
   commit partial recovery without restoring opening margin in one call.
   Require at least one fill. An increase must raise base and actual leverage.
   An emergency plan must lower both base and oracle-valued notional; partial
   fills may complete while still above the hard cap even if actual costs
   worsen leverage. Positive holder value remains required against the reserve
   admitted at the final position. Ordinary reductions must lower base and
   move leverage at least `min_leverage_improvement_bps` toward target or land
   within one lot of target without moving away (core code 55).
   An ordinary reduction may instead fill all 16 orders in full and finish
   at least as close to target as a conservative projection, with strict net
   progress. Core records whether each fill matched its order and fresh
   sizing. The projection repeats sizing and charges adverse slippage and
   authenticated taker fees per order, repricing the admitted reserve at each
   remaining position. Exact comparisons preserve progress below one basis
   point. Tiny ordinary partial fills do not qualify simply by exhausting
   the order count; a smaller retained order cannot misrepresent a full fill.
   Emergency exposure reduction does not guarantee better leverage or margin.
   An order with no fill still aborts the adapter transaction, including its
   earlier fills; the progress rule does not guarantee liquidity.
6. Store the checkpoint; emit `Rebalanced`. Reserve, supply and admin cash do
   not change; execution cost lowers NAV.

Dry run: `operations::needs_rebalance<Product, Collateral>(vault, protocol,
account, registry, clearing_house, base_oracle, collateral_oracle, clock)`
takes every object by immutable reference and returns `bool`. Run it with
dev-inspect. It returns true for a needed, sizeable reduction even below opening
margin, and for an increase only with opening margin and a nonzero fee-aware
order. Inside the band, when a proposed increase lacks opening margin, or when
whole-lot sizing cannot produce an order, it returns false. A final reduction
that cannot retain the full reserve and positive holder value is not sizeable;
neither is an emergency close with no affordable lot. Unexplained drift, invalid prices, unusable fees,
an insufficient opening cap and an unavailable venue still abort. Before pricing,
it classifies funding already settled since the stored checkpoint and projects
the reserve using the same allocation rules as real settlement: costs consume
reserve first, while credits repay uncovered losses before rebuilding reserve.
Positive holder value, band checks and all trade sizing use that projected
reserve, applying the ceiling at each candidate position. This changes no stored
balance, checkpoint or event. The hint does not settle additional funding or
prove gas admission, liquidity or fill progress; the real call checks them and
can still abort. Execution nets already-settled and newly settled raw funding
before rounding once, so additional settlement can also change the result.

The off-chain `keeperDecision` helper returns `inspect_rebalance` for an
outside-band observation. This is only a pre-filter: confirm the on-chain hint
before submitting; it does not authorize a rebalance.

Keeper loop: when dev-inspect returns `true`, submit ordinary `rebalance` at
the reference gas price. Above the hard cap, a higher bid can compete during
congestion. Eligibility is checked again on chain after funding synchronization:
if another keeper has restored the cap, a priority-priced call is refused.
Inside the band, the call aborts with core code 54; rebuild from current
objects. Resolve an uncertain digest before retrying. Ordinary rebalances can
still be delayed by higher-priced traffic.

#### Sync health (anyone)

`operations::sync_health<Product, Collateral>(vault, protocol, account,
registry, clearing_house, base_oracle, collateral_oracle, clock)` with the
`ClearingHouse` by mutable reference. Works in `Active` and `Unwinding`.

It refreshes due funding, settles the position's funding, and reconciles with
the accepted checkpoint without trading. It still reads venue prices for
funding and reconciliation. Stale feeds or a collateral index price too far
from its time-weighted average make the transaction abort. No synchronization
state changes or events are committed on failure; retry after the venue's
price checks can pass.

After the venue calls succeed, an explainable change books
funding to the reserve, adopts the new checkpoint and emits `FundingSettled`
(once per distinct checkpoint; an identical retry emits nothing). A change to
the market's pause mode, frozen flag or market-wide margin ratios is venue
policy, adopted the same way with a zero funding delta; the lot size and every
account, position, order and position-margin field must be exact. Anything
else leaves the accepted checkpoint in place and emits `CheckpointDrifted`;
every drifted sync emits it again. Blast's separate trade-price and opening-margin
checks do not apply here; binding mismatches and venue funding/price failures
still abort. A failed transaction does not emit `CheckpointDrifted`.

#### Recover a reviewed forced reduction (Blast admin: RiskAdmin)

`operations::rebaseline` takes the Vault, Protocol, a live
`AdminWitness<RiskAdmin>`, bound account, registry, clearing house, both current
oracle storages and Clock. The clearing house is borrowed mutably; no object or
coin is returned. An administrator obtains the witness through the shared ACL
earlier in the same PTB, then calls this function. Recovery is Active-only.

The call refreshes funding and captures immediately before and after settlement.
The final position must be strictly smaller on the same side or exactly flat
with zero entry quote. Allocated collateral may reflect realized profit or loss;
free cash, lot size and position IMR cannot change; stored and final checkpoints
must have no orders. Final funding snapshots must be current. Fresh-price,
representation, correct-side, operational-venue and positive shareholder-NAV
checks apply. Recording recovery needs no opening-margin headroom; normal
increasing trades retain their opening-margin checks; reducing rebalances use
the recovery admission described above.

The administrator supplies no replacement numbers and must review venue history:
the shape alone does not prove liquidation. `CheckpointRebaselined` records
stored state to the capture before local funding. Any local settlement must
match the ordinary funding calculation exactly; it is booked under normal
reserve/deficit rules and emitted as a following `FundingSettled` to the final
checkpoint. Process both events in transaction order. Historical mixed PnL,
fees and funding remain in holder NAV without inventing a reserve entitlement.
Supply, admin cash, fee settings and lifecycle stay unchanged. Subsequent
operations price the actual remaining position. An identical retry aborts.

A free-cash change, changed lot or position IMR, unexplained orders or a loss
without a position reduction is outside this recovery path. Insolvency, stale
prices and paused/frozen markets still block recovery. The independently
authorized shutdown path remains available. See ADR 0121 for the auditor
recommendation adopted, explicit extensions and release evidence limits.

#### Donate (anyone)

`operations::donate<Product, Collateral>(vault, protocol, account, registry,
clearing_house, base_oracle, collateral_oracle, cash, clock)`, `Active` only,
`cash` positive. It synchronizes (drift aborts), deposits the coin into the
Vault's Aftermath account and immediately allocates that amount to its
position, proves the exact allocated deposit, and
adds it to the maintenance reserve clamped to the reserve ceiling. Any excess
over the ceiling raises shareholder NAV. A partial donation can complete while
opening margin remains insufficient; valid prices, accounting and the other
active checks still apply. No shares, no fees. Emits `Donated`.

#### Shutdown

1. **Begin** (Blast admin: ShutdownAdmin).
   `blast_boosts_aftermath::vault::begin_shutdown(vault, protocol, witness,
   reason, clock)` with `reason` from `lifecycle::emergency_reason()` or
   `lifecycle::observed_venue_change_reason()` (an operator's label, never an
   on-chain liquidation verdict). Needs no venue or oracle object; the `Clock`
   fixes when shutdown began. Moves
   `Active` to `Unwinding`, emits `ShutdownBegun`. Mint, redeem, rebalance and
   donate stop.
   Alternatively, anyone may call `operations::begin_protected_shutdown(vault,
   protocol, account, registry, clearing_house, base_oracle, collateral_oracle,
   clock)`. It authenticates a raw, accepted, order-free checkpoint and native
   supply. If even burning all circulating shares fails the ordinary minimum
   order, it starts protected closure and emits `ProtectedShutdownBegun`. Flat,
   seed-only and ordinary-exitable positions are rejected. It reads no live
   prices and requires neither positive NAV nor opening margin; unexplained
   account drift must first be reconciled. Market pause/freeze, margin policy
   and cumulative rates may change without synchronization; the trigger adopts
   them. If another caller has already settled account funding, run `sync_health`
   first while the venue permits it, then the trigger (in the same transaction
   if desired). The offline planner leaves this optional: unconditional sync
   would block closed markets. Entry places no trade and pays no reward.
2. **Unwind** (anyone, repeat until flat). `operations::unwind<Product,
   Collateral>(vault, protocol, account, registry, clearing_house, base_oracle,
   collateral_oracle, clock)`. Any gas price is allowed, including a higher
   bid to compete during congestion. Holders pay the venue's priority trading
   surcharge on those fills; the caller pays network gas. The call is refused
   while the clearing house is frozen (adapter code 32). This private `entry`
   call shares the clearing house internally and returns nothing. Pass the
   shared market directly, without a preceding trading session. Repeat unwind
   and finalize in separate transactions because the market cannot be reused
   after this call.
   - Live market: synchronize (drift is reported with `CheckpointDrifted` and
     the live venue state is adopted anyway), price at fresh oracles, then up
     to 16 reduce-only limit orders under the order cap (with the one-lot
     closing exception described in Caps) and a bound that
     starts at `max_slippage_bps` when shutdown begins and widens linearly to
     `emergency_max_slippage_bps` over the following 24 hours, where it stays.
     Emits `OrderFilled` per order and `UnwindProgress`. Positive NAV and the
     reserve do not gate it. A flat position aborts (adapter code 31): go to
     finalize.
   - Market paused by Aftermath: once Aftermath has enabled positive
     settlement prices, the step closes the position at those prices without a
     venue order (`UnwindProgress` with `market_orders = 0`,
     `filled_quote = none`). Before that it aborts (adapter code 30).
3. **Finalize** (anyone). `operations::finalize_shutdown<Product,
   Collateral>(vault, protocol, account, registry, clearing_house, base_oracle,
   collateral_oracle, clock)`. Requires exactly zero base and quote, no orders,
   position funding snapshots equal to the market's (funding fully settled),
   and nonnegative allocated collateral. It withdraws all free collateral plus
   the whole-atom floor of allocated collateral, leaving only a raw remainder
   below one atom at the venue. It sets `Settled`, zeroes the reserve book
   entry, and seals the holder allocation as `terminal_cash`. Protected closure
   first segregates reserve and seed cash with no exposed withdrawal path; administrator-approved
   closure retains its existing allocation, including admin cash when no
   eligible shares exist. Emits `ShutdownFinalized`, including both protected
   amounts (explicitly zero for admin shutdown). If position funding is
   not fully settled it aborts with adapter code 30; on a live market, settle
   it first, for example with `operations::sync_health` earlier in the same
   PTB.
4. **Claim** (any holder). `blast_boosts_aftermath::vault::redeem_shutdown<Product,
   Collateral>(vault, protocol, shares, minimum_collateral, deadline_ms,
   clock)` returns `Coin<Collateral>`. No venue, oracle or fee. Emits
   `ShutdownRedeemed`.

### Economics

Units: collateral amounts in collateral atoms (six decimals; 1 USDC =
1,000,000). Shares in share atoms (nine decimals). Base in base atoms
normalized to nine decimals. Oracle prices normalized to nine decimals. Rates
in basis points out of 10,000; leverage in basis points where 10,000 = 1x.

#### NAV

- `E`, venue equity: free collateral in the Vault's Aftermath account, plus
  collateral allocated to the position, plus unrealized PnL at the base oracle
  price, converted at the collateral oracle price. Assets round down,
  liabilities round up.
- `notional = ceil(base * base_price * 10^6 / (collateral_price * 10^9))`,
  the absolute position valued at the oracle pair (never the venue mark).
- Admitted reserve `R* = min(maintenance_reserve, floor(notional *
  max_reserve_bps / 10,000))`; when the position is flat, `R*` is the whole
  stored reserve.
- Shareholder NAV `N = E - R*`. Every priced operation requires `N > 0`.
- Leverage `= notional / N`. Band comparisons and the rebalance max and target
  checks cross-multiply exactly, without rounding. Mint must start and finish
  inside the band; the final comparison uses final equity and final reserve.
- NAV per share `= N / S`, where `S` is total share supply including the
  locked seed. A whole share is worth `N * 10^9 / S` collateral atoms.

#### Mint math

```text
fee          = ceil(deposit * mint_fee_bps / 10_000)
admin_fee    = floor(fee * admin_share_bps / 10_000)
reserve_fee  = fee - admin_fee
C_exp        = deposit - fee
R1           = min(R0* + reserve_fee, reserve ceiling at the new notional)
N1           = E1 - R1                    (after the fills, same oracle pair)
contribution = min(N1 - N0, C_exp)        (N1 <= N0 aborts, code 5)
shares       = floor(S0 * contribution / N0)   (zero aborts, code 6)
```

The depositor pays the venue's taker fees and slippage through a smaller
`N1 - N0`. A fill better than the oracle credits at most `C_exp`; the excess
stays with existing holders. Share rounding goes to existing holders.

Example (illustrative rates): deposit 1,000 USDC (1,000,000,000 atoms),
`mint_fee_bps = 30`, `admin_share_bps = 2,000`. Fee = 3,000,000; admin fee =
600,000 (kept by the Vault); reserve fee = 2,400,000 (deposited, credited to
the reserve); `C_exp` = 997,000,000. If execution costs 1,000,000, the
contribution is 996,000,000 and `shares = floor(S0 * 996,000,000 / N0)`.

#### Redemption math

```text
keep   = ceil(N0 * (S0 - x) / S0)
Nu     = E_after_sell - R0*
gross  = min(Nu, N0) - keep               (<= 0 aborts, code 7)
fee    = ceil(gross * redeem_fee_bps / 10_000)
net    = gross - fee                      (0 aborts, code 8)
admin  = floor(fee * admin_share_bps / 10_000)
reserve after = min(R0* + fee - admin, reserve ceiling at the new notional)
```

The Vault withdraws exactly `net + admin`. The redeemer pays the sell's cost;
a sell better than the oracle pays at most the proportional claim `N0 - keep`,
and the gain stays with remaining holders. The reserve fee stays in the venue
account.

#### Fees and who receives them

- Reserve fee: stays in the venue account as maintenance reserve. It protects
  holders and is never paid to anyone during normal operation.
- Admin fee: kept as native `admin_cash` in the Vault, never sent to the
  venue. TreasuryAdmin pays it to the shared treasury. With a partner code, up to 80% of each
  operation's admin fee goes to the partner, rounded down; Blast keeps the
  dust.
- Rounding: fees round up; the admin share rounds down, so the reserve gets
  the remainder.
- The user passes no fee argument. Execution uses the live rates; read them
  from the Vault before quoting.
- Fee ceilings: the live rates never exceed the policy caps set at issuance.

#### Funding and the maintenance reserve

Funding is booked only from authenticated Aftermath settlement. Each sync
classifies what moved since the accepted checkpoint: funding someone else
settled (permissionless on Aftermath) plus the settlement the Vault just ran,
netted into one credit or cost. Costs round up to atoms; credits round down.

```text
cost:   absorbed = min(reserve, cost); reserve -= absorbed;
        uncovered_deficit += cost - absorbed   (holders bore it)
credit: restored = min(credit, uncovered_deficit); uncovered_deficit -= restored;
        reserve += credit - restored           (restored stays in NAV)
```

A credit must leave the stored reserve within `u64`; the amount restored to
holders does not count against that reserve limit. The old reserve plus the
full credit may exceed `u64` when the restored amount makes the final reserve fit.

A credit may lift the stored reserve above its ceiling; priced operations
value shares against the admitted reserve `R*`, so the excess counts as NAV
from the next priced operation on. Mint, redeem and donate store the clamped
value. Trading losses, slippage, liquidation, ADL and socialized loss are never
treated as funding. The reserve is bookkeeping inside the margin account, not
separate custody: a non-funding loss can impair it, and a priced operation
refuses an account whose equity does not exceed the admitted reserve.

#### Caps

- NAV cap: post-mint `N1 <= nav_cap` (inclusive). Once active, only mints check it; profit
  can carry NAV above it, which blocks mints until NAV falls or RiskAdmin
  raises the cap.
- Increase sizing keeps the desired position in wide arithmetic even when
  profits make it exceed `u64`. Actual orders and resulting positions remain
  bounded. At the maximum supported position size, further increases stop;
  a large desired position does not relax the NAV cap on completed mints.
- Order cap: each order reserves the highest price allowed by its execution
  bound plus one normalized price atom to cover sell rounding, then rounds
  size down to whole lots. Each fill checks actual collateral notional
  (excluding fees) against `max_order_notional`. Opening orders obey the cap
  strictly. A reduce-only fill of exactly one live venue lot may exceed it;
  that fill must still pass the same execution-price check. With 16 orders per call,
  one mint can add at most about `16 * max_order_notional` of notional, so the
  largest single mint is roughly `16 * max_order_notional / leverage`.
- Rebalance progress: issuance and both cap setters reject a configured
  minimum larger than the optimistic effect of 16 cap-sized orders at
  `nav_cap`. Actual NAV can exceed that ceiling. The full-batch completion
  rule above permits smaller, cost-adjusted ordinary progress when capacity
  is the limit. Emergency progress requires actual exposure reduction and
  positive holder value, even if costs worsen leverage. Neither rule promises
  liquidity. A final lot that cannot retain the full reserve may need shutdown.
- Minimum size: a mint or a non-flat redemption must move at least
  `lot_size * min_order_lots` of base. At initialization and each cap change,
  the cap must cover that minimum in one order at current prices. Later price
  or lot growth can block openings (core code 63) or make a normal redemption
  exceed the 16-order budget. RiskAdmin can raise the cap. ShutdownAdmin can
  instead begin shutdown, after which anyone can repeat unwind calls in
  separate transactions. Closing still needs fresh prices and executable
  liquidity inside the bound; a venue freeze or other venue restriction can
  block it.

#### Shutdown payouts

```text
eligible = total_supply - locked_shares
payout   = floor(terminal_cash * shares / eligible)
```

For permissionless size-locked closure, finalization first allocates:

```text
protected_reserve = min(actual_recovered_cash, full_recorded_reserve)
share_cash = actual_recovered_cash - protected_reserve
terminal_cash = floor(share_cash * eligible / total_supply)
protected_seed = share_cash - terminal_cash
```

Both protected amounts stay in the upgradeable adapter's `protected_cash`,
including after all holder claims. No holder or admin withdrawal path exists
under this code; upgrade governance remains a trust assumption (ADR 0130).
Closing losses may exhaust holder cash; this does not guarantee seed capital.
The full recorded reserve is retained under the flat-position policy, rather
than releasing the last open position's excess reserve to holders (ADR 0130).
A closed-market direct close books funding at the enabled settlement
collateral price before finalization. Attributable earlier funding and the
close's funding are netted raw and converted to collateral atoms once. Trading
PnL, insurance and released cash are not funding. Unknown history emits
`CheckpointDrifted`; only proven local funding is then booked from that live
baseline (ADR 0132). Arithmetic limits can still abort. Already-settled account
funding followed by a market pause can block protected entry until
reconciliation becomes available.

No fee. The last claimant (shares equal to all eligible supply) receives all
remaining **holder-pool** cash, dust included. A partial claim that rounds to zero while cash
remains aborts; combine shares. If `terminal_cash` is zero, a burn with
`minimum_collateral = 0` succeeds and returns a zero coin. If no eligible
shares remain at administrator-approved finalization, recovered cash becomes
admin cash. Administrator-approved closure distributes recovered reserve and
seed-backed cash to circulating holders when any exist; protected closure
does not. Admin cash never enters the holder pool.

### Time rules

- `deadline_ms` (mint, redeem, partner variants, `redeem_shutdown`):
  inclusive; `Clock` time greater than it aborts (adapter code 25).
- Price freshness: each oracle's publish time must lie in
  `[now - max_price_age_ms, now + max_price_ahead_ms]`, inclusive. Older aborts
  with core code 27; further ahead aborts with core code 28. The confidence
  gate always passes because Aftermath feeds carry no confidence interval. The
  venue mark must be within `max_mark_divergence_bps` of the base oracle price
  (core code 31) for priced operations except emergency rebalance reductions.
  That exception lasts through the final cap-restoring fill; unwind also skips
  the mark check. Both oracle legs still require valid, fresh prices.
- Same oracle pair: every order and the final pricing of one operation use the
  oracle pair captured at its start; a change of pair or lot between plan and
  completion aborts (core code 50).
- Funding refresh: before settling, the adapter calls Aftermath's funding
  update only when the market's funding period has elapsed.
- Partner removal: accepted while `now_ms < accepted_until_ms`, where
  `accepted_until_ms = removal time + 7 days`
  (`blast_partners::blast_partners::delay_ms`).
  Partner share changes wait `blast_partners`' fixed seven-day notice and an explicit apply.
- Admin settings have no cooldown. Shutdown has no timer: unwind and finalize
  run whenever the venue allows.

### Pitfalls

- Passing an Aftermath object other than the bound one. Always read the binding.
- Setting `minimum_shares` or `minimum_collateral` to 0 in production. The
  mint floors shares and execution costs vary; set a floor from a fresh dry run.
- Expecting to mint at any time. Mints abort if starting or final leverage is
  outside the band (49), above the NAV cap (36), or while the checkpoint is
  drifted (adapter code 29). A minimum-sized mint is not guaranteed to pass. At an exact
  band edge, a rounded mint may fail while rebalance remains unavailable.
- Tiny trades. Mints and redemptions below `lot_size * min_order_lots` of base
  abort (12). If every accessible ordinary burn fails this size guard, anyone
  can begin protected closure with `begin_protected_shutdown`. Positive-cash
  shutdown claims that round to zero abort (8).
- Large trades. More than 16 orders, a fill outside `max_slippage_bps`, an
  order that finds nothing to fill inside its limit (Aftermath aborts the empty
  session), or a fill above the cap outside the one-lot closing exception
  aborts the whole transaction.
- Submitting an ordinary `rebalance` with a priority gas price (34).
  Emergency rebalances and `unwind` permit it, and holders bear the extra
  venue trading fee. Venue priority support, usable liquidity and the existing
  price, margin and progress checks still apply; permission to bid higher is
  not a guarantee of execution. For mint and redeem, a higher gas price is
  allowed and the user pays the extra trading fee through fewer shares or a
  lower payout.
- Reading `CheckpointDrifted` from a failed mint: aborted transactions emit
  nothing. Only `sync_health` and `unwind` record drift. Drift from a
  lasting account change does not clear on its own. RiskAdmin can recover an
  admitted forced reduction; other drift may require ShutdownAdmin to shut
  the Boost down. Market-wide margin changes are accepted automatically.
- Decoding an abort by code alone. Core and adapter codes overlap.
- Calling an old adapter generation after activation (adapter marker code 0). Types
  keep their original package IDs; calls must target the current package.
- Treating the tag name as the policy. `NVDA_BULL_2X` is a label; read `side`
  and `target_leverage_bps` from the Vault.
- Assuming NAV per share starts anywhere but 1. The seed mints exactly
  1 whole share per collateral unit of seed NAV.
- Counting locked shares as claimable. They count in total supply for mint and
  redeem math but are excluded from shutdown claims.
- Expecting partner revenue at activation: `admin_share_bps` starts at 0.

### Q&A

**How do I mint a Boost?** Split a collateral coin and call `operations::mint`
with the Vault, `Protocol`, adapter `PackageVersion`, the five bound Aftermath objects, the coin, a
`minimum_shares` floor, an inclusive `deadline_ms`, and the `Clock`. Transfer
the returned coin and re-share the returned clearing house after its final
use. With a partner code call
`operations::mint_with_partner` and put the `Partner` after the adapter’s `PackageVersion`.

**How many shares will I get?** `floor(S * contribution / N)`, where
`contribution` is your deposit minus the mint fee, reduced by any execution
cost, and `N` is shareholder NAV before your mint. The exact figure depends on
fills, so dry-run the PTB and set `minimum_shares` just below the result.

**What fees do I pay?** The live mint or redeem fee, rounded up, plus Aftermath
taker fees and slippage on the Vault's orders. The fee splits into a reserve
part (stays in the Vault for holders) and Blast's admin part. A partner code
changes nothing for the user.

**Why did my mint abort with code 49 in `state`?** Starting or final leverage
was outside the rebalance band. The whole transaction rolls back; gas is still
payable. Dry-run a different amount. Anyone can rebalance an already out-of-band
position first, but an exact band edge does not allow rebalance.

**Who rebalances, and is there a reward?** Anyone, through
`operations::rebalance`. Ordinary calls require a gas price at or below the
reference; emergency reductions starting strictly above the hard cap permit
higher bids. There is no reward, role or size argument; the chain derives
direction and size and holders pay the fills, including any priority trading
surcharge. Use `operations::needs_rebalance` in dev-inspect to decide when to
submit.

**How do I read NAV and leverage?** NAV is not stored. Compute
`N = E - min(maintenance_reserve, notional * max_reserve_bps / 10,000)` from
the Aftermath position at the oracle prices, and leverage as `notional / N`.
For an exact quote, dry-run the mint or redeem and read `Minted` or
`Redeemed`.

**What does the maintenance reserve do?** It is collateral in the venue account
that share pricing excludes. Funding costs consume it before holders bear
them, mint and redeem reserve fees refill it, and donations add to it. It is
capped at `max_reserve_bps` of notional; anything above counts as holder NAV.

**What happens on shutdown?** Blast's ShutdownAdmin calls `begin_shutdown`,
or anyone proves a size lock through `begin_protected_shutdown`. Anyone then calls `operations::unwind` until flat and
`operations::finalize_shutdown`. Holders call
`blast_boosts_aftermath::vault::redeem_shutdown` for a fee-free pro-rata share
of the holder cash pool. Permissionless size-locked closure
retains reserve and seed cash separately with no holder or admin withdrawal
path; the adapter remains upgradeable. The last claimant gets only the
holder pool's dust. Administrator-approved closure retains its original payout.

**Can a Boost be liquidated?** The Aftermath position can be. The Vault never
declares liquidation on chain; a liquidation appears as `CheckpointDrifted`,
priced operations stop, and RiskAdmin may recover the admitted reduction shape
once the remaining position is healthy. Otherwise ShutdownAdmin may shut the
Boost down so holders can claim what remains.

**Is there a testnet deployment?** No. Blast deploys Boosts on Sui mainnet only.

## Partner codes

> **Deployment status:** `blast_partners` is live on mainnet.

### What it is

A partner code lets an app that brings flow to Blast earn a share of the fee
Blast charges on that flow. Package `blast_partners` holds the codes for every
Blast product: Boosts, the launchpad (with its post-migration LP vaults), and
presales. A partner is one deal: a shared `Partner` object with a share of
Blast's fee (0% to 80%) and a recipient address. A company holds one
`PartnerCap` that controls the recipient of every deal registered under it.
Users never pay for a partner: a partner is only ever paid out of Blast's own
fee. Initial shares apply immediately. A later share or managing cap Blast
proposes applies only when someone applies it, at least seven days after the
proposal. The module never changes that notice. Canonical immutability is
deferred until final audit; a native compatible UpgradeCap remains at the
multisig without an enforced upgrade notice.

### Objects and authority

| Object | Kind | Held by | Authorizes |
| --- | --- | --- | --- |
| `blast_partners::blast_partners::Partner` | shared (`key` only, never transferable) | nobody; created by `blast_partners::blast_partners::register` | read by products on every trade; mutated only by the calls below |
| `blast_partners::blast_partners::PartnerCap` | owned (`key, store`; transferable, wrappable) | the partner company | `blast_partners::blast_partners::set_recipient` on every `Partner` whose applied cap is this cap's ID |
| `blast_partners::blast_partners::PartnerAdmin` | role type in Blast's ACL | a Blast `AdminCap` granted this role | `blast_partners::blast_partners::register`, `blast_partners::blast_partners::schedule_share`, `blast_partners::blast_partners::schedule_cap`, `blast_partners::blast_partners::cancel_share`, `blast_partners::blast_partners::cancel_cap` |

`Partner` fields:

- `recipient: address`: where payments go. Set by the live cap's holder, applies
  at once.
- `share_bps`: the share of Blast's fee, in basis points (BPS, out of 10,000),
  at most 8,000. A `delayed::Delayed<ShareKey, u64>` value.
- `cap_id`: the ID of the one `PartnerCap` that may set `recipient`. A
  `delayed::Delayed<CapKey, ID>` value.

A `delayed::Delayed<K, T>` comes from Blast's shared administration package
`blast_admin` and has five fields in BCS order: `parent` (the `Partner`'s ID),
`key` (`blast_partners::blast_partners::ShareKey` or
`blast_partners::blast_partners::CapKey`, each a one-byte unit struct), `value`
(the applied value), `delay_ms` (the notice), and `pending: Option<Proposal<T>>`.
A `delayed::Proposal<T>` holds `value`, `delay_ms` and `ready_at_ms`. The applied
value is always `value`; a proposal changes nothing until it is applied, even after
`ready_at_ms`. Both notices are 604,800,000 ms (seven days) and stay fixed:
`blast_partners` exposes no call that changes them.

Who may call: *anyone* may call `new_cap`, `destroy_cap` (on a cap they hold),
`pay`, `apply_share`, `apply_cap`, `delay_ms`, `max_share_bps`, and the readers
under Reading state; the *cap holder* (the applied
`PartnerCap`) may call `set_recipient`; a *Blast admin* with the `PartnerAdmin`
role (through `blast_acl::sign_in`) may call `register`, `schedule_share`,
`schedule_cap`, `cancel_share`, and `cancel_cap`.
Each product keeps its own list of the partners it accepts, managed by that
product's admin.

### Lifecycle

**Cap.** `blast_partners::blast_partners::new_cap` mints an inert cap: it
controls nothing until Blast registers a partner under its ID. It is *live* for
a partner while it is that partner's applied cap. After
`blast_partners::blast_partners::schedule_cap` proposes a different cap and seven
days pass, anyone may call `blast_partners::blast_partners::apply_cap`; only then
does the old cap stop working for that partner.
`blast_partners::blast_partners::destroy_cap` deletes a cap, live or not;
destroying a live cap leaves its partners with no working cap until a cap Blast
proposes with `blast_partners::blast_partners::schedule_cap` is applied, at
least seven days later.

**Partner.** `blast_partners::blast_partners::register` creates and shares the
partner with the agreed share and managing cap in force immediately. Registration
needs no `Clock`; there is no initial waiting period. From then on:

1. Blast proposes a new share or cap; the applied value stays in force.
2. A different proposal replaces the pending one and restarts the full seven
   days, even when the old proposal was already ready. Proposing the applied
   value, or the value already pending, aborts.
3. Blast may discard a proposal with `blast_partners::blast_partners::cancel_share`
   or `blast_partners::blast_partners::cancel_cap`, even after it is ready.
4. From `ready_at_ms`, anyone may call `blast_partners::blast_partners::apply_share`
   or `blast_partners::blast_partners::apply_cap`, the partner included. Nothing
   changes merely because time passes. `blast_partners::blast_partners::is_share_ready`
   and `blast_partners::blast_partners::is_cap_ready` say whether that call would
   succeed now.

There is no delete: a partner exists forever, because launches, presales, and
vaults bind its ID for good and pay Blast's held fees only with it. To switch it
off, Blast proposes and then applies a zero share; products that name it keep
working and simply pay it nothing.

**Product acceptance.** Each product accepts a partner in its own shared config,
mapping the partner's ID to the time it stops being accepted (`u64::MAX` until
removed) in the `acceptance_ends_at_ms` table of a `blast_partners::partner_list::PartnerList`:

| Product | Config object and key | Admin |
| --- | --- | --- |
| Boosts | `blast_boosts_aftermath::blast_boosts_aftermath::Protocol`, its embedded `PartnerList` | core `FeeAdmin` role (`operations::add_partner`, `operations::remove_partner`) |
| Launchpad | `launch_config::LaunchConfig`, its embedded `PartnerList` | core `FeeAdmin` role |
| Presale | `creation_policy::CreationPolicy`, its `partners` `blast_partners::partner_list::PartnerList` | core `FeeAdmin` role (`creation_policy::add_partner`, `creation_policy::remove_partner`) |

Adding applies at once (and cancels a pending removal). Removing sets the value
to `now` plus `blast_partners::blast_partners::delay_ms()`: the partner stays
accepted for seven more days. A partner is accepted while the field exists and
`now < value`.

**Shared acceptance list.** `blast_partners::partner_list::PartnerList` is the
same acceptance rule as one embeddable value, for a product to keep inside its
own config. The launchpad embeds one in `launch_config::LaunchConfig` (its
`partners` field), changed by the `FeeAdmin` role through
`launch_config::add_partner` and `launch_config::remove_partner`. It maps each partner's ID to the time, in Unix epoch milliseconds,
it stops being accepted (`u64::MAX` until removed), held in a `Table`, and
records the `parent` object that embeds it. It has no authority of its own: only
the embedding module can reach it mutably, so that product decides who may
change it.

- `blast_partners::partner_list::new` creates an empty list for a parent.
- `blast_partners::partner_list::add` accepts a `Partner` at once, cancelling a
  pending removal or accepting a removed partner again; it aborts when the
  partner is already accepted with no removal pending.
- `blast_partners::partner_list::remove` keeps a partner accepted until `now`
  plus `delay_ms()`; it aborts unless the partner is accepted now with no
  removal pending.
- `blast_partners::partner_list::assert_accepted` aborts unless the list
  accepts the partner now; `blast_partners::partner_list::is_accepted` returns
  the same answer as a `bool`.
- `blast_partners::partner_list::contains` says whether the list has an entry
  for a partner (accepted, removal pending, or removed);
  `blast_partners::partner_list::acceptance_ends_at_ms` returns that entry's end
  time and aborts in `sui::dynamic_field` without one;
  `blast_partners::partner_list::length` counts entries, removed ones included;
  `blast_partners::partner_list::parent` returns the embedding object's ID.
- `blast_partners::partner_list::destroy` deletes the list with every entry and
  emits `PartnerListDestroyed`. It ends every acceptance at once, without the
  notice, so a product destroys it only with the object that embeds it.

### Flows

#### Become a partner (company)

1. Call `blast_partners::blast_partners::new_cap` (*anyone*). It returns a
   `PartnerCap`; send it with a TransferObjects command to the address that will
   manage your deals (for example your multisig).
2. Give Blast the cap's object ID, the recipient address, and the agreed share.
3. Blast's partner admin, in one PTB: `blast_acl::sign_in` with type argument
   `blast_partners::blast_partners::PartnerAdmin`, passing the shared `ACL` and
   its owned `AdminCap`; then `blast_partners::blast_partners::register` with a
   reference to that `AdminWitness<PartnerAdmin>`, your cap ID, the recipient,
   and the share. The new `Partner` is shared; its ID is in the `PartnerUpdated`
   event and the transaction's created objects. Its initial share is active immediately.
   Registration also emits `delayed::DelayedCreated` for the share and for the cap.
4. Blast's admin for each product adds the partner to that product's list.

`blast_partners::blast_partners::register` accepts any ID as the cap. Confirm on
chain that the `Partner`'s applied `cap_id.value` equals your cap's ID; a wrong
ID can only be fixed by proposing a new cap and applying it seven days later.

#### Change where a partner pays you (cap holder)

1. Call `blast_partners::blast_partners::set_recipient` with the shared
   `Partner` (mutable), your owned `PartnerCap` (by reference), and the new
   address. It takes no `Clock`.
2. It applies at once and emits `PartnerUpdated`. One call per partner.

#### Change a share or replace a lost cap (Blast admin)

1. `blast_acl::sign_in` with `blast_partners::blast_partners::PartnerAdmin`.
2. `blast_partners::blast_partners::schedule_share` (new share) or
   `blast_partners::blast_partners::schedule_cap` (new cap ID), with the shared
   `Partner`, the witness, the value, and `Clock`.
3. Each emits `delayed::DelayedScheduled` (after `delayed::DelayedCancelled`
   when it replaces a pending proposal) with `ready_at_ms`, seven days later.
4. From `ready_at_ms`, *anyone* calls `blast_partners::blast_partners::apply_share`
   or `blast_partners::blast_partners::apply_cap` with the shared `Partner`
   (mutable) and `Clock` at `0x6`; each emits `delayed::DelayedApplied`. Until a
   cap change is applied, the old cap keeps working, including for a thief
   holding it.
5. Instead, Blast may sign in and call `blast_partners::blast_partners::cancel_share`
   or `blast_partners::blast_partners::cancel_cap` (no `Clock`), even after
   readiness; each emits `delayed::DelayedCancelled`.

#### Pay a partner (products, or anyone)

`blast_partners::blast_partners::pay<T>` takes the shared `Partner` by immutable
reference, a `&mut Balance<T>` holding Blast's fee on a trade, and the
transaction context; it takes no `Clock`. It splits off `floor(fee * applied_share / 10,000)`, sends it to the partner's
`recipient`, emits `PartnerPaid<T>`, and returns the amount. The rest stays in
the caller's balance. With a zero share (or a fee too small to round above zero)
it sends nothing, emits nothing, and returns 0. Each positive payment creates
a `Coin<T>` and transfers it to the recipient with `public_transfer`. Integrators
never call `pay` directly; products call it inside their own partnered functions.

### How each product uses a partner

| Product | When the partner is named | Blast fee divided | Payment |
| --- | --- | --- | --- |
| Boosts | on each trade: `operations::mint_with_partner` or `operations::redeem_with_partner`, passing the `Partner` immediately before the Aftermath account | Blast's admin fee that trade retained; never the reserve fee | push: paid in the same call |
| Launchpad | once, at creation: `launch::set_partner` on the `LaunchInitializer` before `launch::finalize`; fixed for good | Blast's whole fee ledger on the launch: the creation fee (SUI), Blast's share of every curve trade fee (Meme and Quote), and Blast's one-time migration fee | held in the launch; paid when anyone calls `launch::claim_protocol_fees_with_partner` |
| LP vault (launchpad and presale) | inherited from the launch or sale at migration, in its vault terms | Blast's LP fees on each collection, and protocol migration residuals | held in the vault; paid when anyone calls `blast_vault::vault::pay_protocol_fees_with_partner` |
| Presale | once, at creation: `blast_presale::blast_presale::set_partner` on the `PresaleInitializer` before `blast_presale::blast_presale::finalize`; fixed for good | Blast's raise fee (Quote) only; Blast's token fee is never divided | held at migration; paid when anyone calls `blast_presale::blast_presale::pay_protocol_fees_with_partner` (once) |

Rules common to every product:

- Naming a partner requires that the product accepts it at that moment;
  otherwise the call aborts. Launches and sales that already name a removed
  partner keep paying it.
- The claim and payment calls are *anyone*: both payees are fixed, so no caller
  chooses where money goes. Each checks that the `Partner` passed is the one the
  launch, sale, or vault named, and aborts otherwise.
- A launch that names a partner cannot use `launch::claim_protocol_fees`; it
  must use `launch::claim_protocol_fees_with_partner`.
- Held fees are divided at the share **applied when they are paid**, not when
  they accrued.
- The `Partner` is read by immutable reference, so naming a busy partner adds no
  contention of its own.

### Economics

- Partner amount per payment: `floor(fee * share_bps / 10,000)` in atomic units
  of `T`, where `share_bps` is the applied share when the payment executes.
  Blast keeps the remainder, including every rounding dust.
- `share_bps` is between 0 and 8,000 (80%). Blast always keeps at least 20% of
  its fee.
- Users, holders, creators, buyers, and pools receive exactly the same amounts
  with or without a partner.
- Example (Boosts): a mint retains a 15.00 USDC admin fee and the partner's
  share is 4,000 BPS. The partner receives 6.00 USDC; Blast keeps 9.00 USDC.
- Example (presale): Blast's raise fee is 2,000 USDC and the share is 4,000 BPS.
  The partner receives 800 USDC; Blast keeps 1,200 USDC and all of its token
  fee.

### Time rules

- Delay: `blast_partners::blast_partners::delay_ms()` returns 604,800,000 (seven
  days). It is a compile-time constant; current upgrade authority is recorded in the deployment record.
- The initial share and managing cap apply at registration, without a Clock.
- A proposed share or cap can be applied by the first transaction whose `Clock`
  reads `ready_at_ms` or later; it takes effect only when `apply_share` or
  `apply_cap` succeeds. A replacement restarts the full seven days.
- A recipient change applies in the same transaction.
- A product removal keeps the partner accepted until `now + delay_ms()`; a trade
  or creation at or after that time aborts.

### Reading state

Move callers read a partner with `blast_partners::blast_partners::recipient`,
`blast_partners::blast_partners::share_bps` (applied),
`blast_partners::blast_partners::pending_share_bps`,
`blast_partners::blast_partners::cap_id` (applied), and
`blast_partners::blast_partners::pending_cap_id`; each pending reader returns an
`Option<delayed::Proposal<T>>`. `blast_partners::blast_partners::is_share_ready`
and `blast_partners::blast_partners::is_cap_ready` take the `Clock` and return
whether `apply_share` or `apply_cap` would succeed now: a proposal is pending,
the clock reads its `ready_at_ms` or later, and the clock plus the seven-day
notice still fits in a `u64`. They return false with nothing proposed, before
`ready_at_ms`, and after a cancel or an apply. The share readers keep the field's name,
`share_bps`, the repository's term for a partner's share in basis points.
`blast_partners::blast_partners::max_share_bps` returns the 8,000 BPS ceiling
`register` and `schedule_share` enforce. Off chain, read the shared `Partner`
object's content over RPC, or replay the events below.

- Applied share: `share_bps.value`.
- Pending share: `share_bps.pending`, with its `value` and `ready_at_ms`;
  readiness does not clear it.
- Which cap controls the recipient: `cap_id.value`; its proposal is
  `cap_id.pending`.
- Whether a product's `PartnerList` accepts a partner now:
  `blast_partners::partner_list::is_accepted`.
- Whether a product accepts a partner: read the entry for `partner_id` in the product config’s
  embedded `PartnerList` table. Acceptance lasts while the entry exists and `now < value`.
- Which partner a launch, sale, or vault names: its `partner_id: Option<ID>`
  field; a vault's comes from its terms, recorded in
  `blast_vault::blast_vault_events::VaultCreated`.

### Events

Every event is emitted directly (no envelope).

- `blast_partners::blast_partners::PartnerUpdated`: emitted by
  `blast_partners::blast_partners::register` and
  `blast_partners::blast_partners::set_recipient`. Fields: `partner_id`,
  `recipient`. The latest one per `partner_id` gives the recipient.
- Share and cap lifecycle events come from `blast_admin`'s `delayed` module,
  generic in the key (`ShareKey` for the share, `CapKey` for the cap) and the
  value type (`u64` or `ID`), with `parent` set to the `Partner`'s ID:
  `delayed::DelayedCreated` (registration: initial value and notice),
  `delayed::DelayedScheduled` (proposal: value, notice, `ready_at_ms`),
  `delayed::DelayedCancelled` (a cancel, or a proposal a new one replaced) and
  `delayed::DelayedApplied` (previous and new value, notice). Replaying them per
  `parent` and key reconstructs the applied and pending terms; `blast_partners`
  emits no event of its own for them.
- `blast_partners::partner_list::PartnerAdded`: emitted by
  `blast_partners::partner_list::add`. Fields: `parent` (the object embedding
  the list), `partner_id`.
- `blast_partners::partner_list::PartnerRemoved`: emitted by
  `blast_partners::partner_list::remove`. Fields: `parent`, `partner_id`,
  `acceptance_ends_at_ms` (exclusive). Replaying both per `parent` gives that
  list's accepted partners.
- `blast_partners::partner_list::PartnerListDestroyed`: emitted by
  `blast_partners::partner_list::destroy`. Field: `parent`. From then on the
  parent's list accepts no partner.
- `blast_partners::blast_partners::PartnerPaid<T>`: emitted by
  `blast_partners::blast_partners::pay` when it sends a positive amount. Fields:
  `partner_id`, `amount` (atomic units of `T`). The product records the trade in
  its own event in the same transaction:
  `blast_boosts_aftermath::events::PartnerFeePaid` (Boosts),
  `blast_core::blast_core_events::ProtocolFeesPaid` (launch claims, LP vaults and presale fees).
  `blast_fun::events::LaunchCreated` and
  `blast_presale::events::PresaleOpened` record the partner a launch or
  sale names.

### Aborts

| Code | Constant | Raised by | Fix |
| --- | --- | --- | --- |
| 0 | `EInvalidRecipient` | `register`, `set_recipient` | use a non-zero recipient |
| 1 | `EShareAboveMax` | `register`, `schedule_share` | share at most 8,000 BPS |
| 2 | `EUnchanged` | `schedule_share`, `schedule_cap` (value equals the pending proposal), `set_recipient` (same recipient) | pass a different value; to restart a pending proposal with the same value, cancel it first |
| 3 | `ENotLiveCap` | `set_recipient` | use the partner's applied cap; a ready but unapplied cap is refused until `apply_cap` |
| 4 | `EPartnerNotAccepted` | `partner_list::assert_accepted`, `partner_list::remove` | name a partner the list accepts now |

The codes come from the package registry `blast_partners::errors`. Codes 0 to 3
are raised in module `blast_partners`; `partner_list::add` and
`partner_list::remove` also raise `EUnchanged` (adding an accepted partner, or
removing one whose removal is pending), and code 4 is raised in module
`partner_list`. The share and cap calls also
abort in module `blast_admin::delayed` with `blast_admin`'s error codes:
`ENotReady` (13, `apply_share` or `apply_cap` before `ready_at_ms`),
`ENoPending` (14, apply or cancel with nothing proposed), `EInvalidDelay` (15, a
`ready_at_ms` that would overflow) and `EUnchanged` (16, proposing the applied
value). A product call that names a
partner it does not accept, or passes the wrong `Partner` to a claim, aborts in
that product's module with that product's own error.

### Pitfalls

- `PartnerPaid` alone does not prove a Blast trade:
  `blast_partners::blast_partners::pay` is public, and anyone can pay a partner
  from their own balance. Pair it with the product event in the same
  transaction.
- Each positive payment arrives as an owned `Coin<T>` at the recipient address.
  Repeated payouts produce separate coins that the recipient can merge.
- On Boosts, check acceptance before building a partnered trade; otherwise call
  the plain `mint` or `redeem`.
- On the launchpad and presales the partner is fixed at creation. Forgetting
  `launch::set_partner` or `blast_presale::blast_presale::set_partner` cannot be
  fixed later.
- Held fees are divided at the share applied at payment time. An applied cut
  to zero also cuts fees accrued earlier but paid later.
- A ready proposal is not in force. Payments keep the old share and the old cap
  keeps working until someone calls `apply_share` or `apply_cap`; a partner
  waiting on a raise can apply it itself.
- Whoever holds the cap controls the recipient of every deal under it. A stolen
  cap can redirect payments until a `schedule_cap` replacement is applied.

### Q&A

**How much can a partner earn?** Up to 80% of Blast's fee on the flow that names
it, as agreed with Blast and set by `blast_partners::blast_partners::register`.
Users pay the same fee with or without a partner.

**When am I paid?** On Boosts, in the same transaction as each mint or redeem.
On the launchpad and presales, when anyone calls the product's `*_with_partner`
claim or payment call; you may call it yourself.

**In which asset am I paid?** In the asset of the fee divided: Boost collateral;
launch Meme, Quote, and SUI; presale Quote; LP fees in both pool assets.

**Can Blast change my share without notice?** No. Every share or cap change
waits seven days, visible on chain the moment it is proposed, and only then can
anyone apply it. The notice is fixed in the published code.

**Can I change my recipient myself?** Yes, with your `PartnerCap` through
`blast_partners::blast_partners::set_recipient`; it applies at once.

**I lost my cap. What now?** Mint a new cap with
`blast_partners::blast_partners::new_cap` and ask Blast to call
`blast_partners::blast_partners::schedule_cap` for each of your partners. After
seven days anyone, you included, calls `blast_partners::blast_partners::apply_cap`;
until then the old cap still works.

**Can one company have several deals?** Yes. Each deal is its own `Partner` with
its own share and recipient; one `PartnerCap` can manage all of them.

**Can another app use my partner code?** Yes. The `Partner` is a public shared
object; any app can name it on a product that accepts it, and you earn on that
flow.

**How do I reconcile income?** Sum `PartnerPaid<T>` by `partner_id` and coin
type, and join each with the product event in the same transaction for trade
detail.

**Can I charge my own users an extra fee?** Not through `blast_partners`. Take
your own fee in your own PTB commands (split it from the user's coin and send it
where you like); Blast takes no cut of it.

### `blast_boosts_core::constants`

Package-wide immutable core numeric constants.

Source: https://github.com/interest-protocol/blast-v2-contracts/blob/main/sui/defi/boosts/core/sources/lib/constants.move

#### Constants

- `basis_points_denominator: u64 = 10_000`: Returns the denominator for one basis-point rate.
- `leverage_ceiling_bps: u64 = 100 * basis_points_denominator!()`: Structural ceiling on any leverage threshold: 100x in leverage basis points.  No leveraged coin in this protocol targets more than a small multiple, and the mint-contribution allowance scales with target leverage, so an unbounded threshold would let a transposed or mistyped policy admit almost any contribution. The ceiling is a sanity fence, not a selected product value.
- `max_min_order_lots: u64 = 1_000_000`: Structural ceiling on the minimum operation size in live venue lots.  The minimum exists so a small holder can still exit; a million lots can never be small in collateral terms. The fence also catches a policy that swaps `min_order_lots` with an atomic-collateral value such as the NAV cap, which would otherwise brick every mint of an immutable policy.
- `max_asset_decimals: u8 = 18`: Widest asset precision the notional formulas support without overflow.
- `max_rebalance_orders: u64 = 16`: One rebalance's bounded execution and capacity projection share this budget.
- `unwind_bound_widening_duration_ms: u64 = 86_400_000`: How long after shutdown begins the close-only execution bound takes to widen, linearly, from the ordinary bound to the emergency one: 24 hours.  A permissionless close must stay as cheap for holders as honest depth allows, yet a book that stays thin must not refuse the exit forever, so the admitted execution widens with time instead of opening at the wide bound.

### `blast_boosts_products::blast_boosts_products`

Blast-owned product tags for Series1 Boost currencies.  A Boost currency is `blast_boost::BlastBoost<Product>` in the issuing adapter, and its `Product` argument is what a holder reads inside the coin type. Declaring every tag in this module keeps that inner type under the Blast name: `blast_boosts_products::NVDA_BULL_2X`.  Each product is one empty struct with no abilities named `<TICKER>_<SIDE>_<LEVERAGE>`, for example `public struct NVDA_BULL_2X {}`. `BULL` tracks the perp long and `BEAR` the inverse; the ticker is the Aftermath base asset without its USD suffix. A tag carries no authority and no state: Coin Registry admits one currency per tag type, and the Series1 issuer role is the only authority that can issue it. Adding a tag is a compatible upgrade of this package; nothing here is ever removed. A declared tag is not a live product until an adapter issues its currency.

Source: https://github.com/interest-protocol/blast-v2-contracts/blob/main/sui/defi/boosts/products/sources/blast_boosts_products.move

- `immediate_or_cancel_order_type: u64 = 3`: Aftermath's immediate-or-cancel order type for `clearing_house::place_limit_order`.  The deployed `execute_limit_order` (original id `0x3ec740df…`, now version 2 at `0xe5475743…`, interface revision `f62e74a`) admits types 0 to 3: 0 posts the unfilled remainder, 1 aborts unless the whole size fills, 2 aborts on any fill, and 3 fills what rests at or inside the limit and drops the rest without posting. Every order the adapter places is the last kind, so a session never leaves a resting order and a thin book fills less rather than worse.

## API reference: `blast_core` (Shared core)

Live on mainnet. This reference matches the published source.

Events: payload structs are emitted directly, each under its own type.

Abort codes: this package aborts with the numeric codes below from whichever module detects the failure; the abort location names that module.

| Code | Constant | Meaning |
| --- | --- | --- |
| 0 | `EInvalidBps` | A basis-points rate must be at most 10,000. |
| 1 | `EInvalidApportionment` | Apportioned rates must sum to 10,000 and name a rounded-up part inside them. |
| 2 | `EInvalidVestingTerms` | Vesting needs positive steps whose total and cliff fit the technical bound. |
| 3 | `EInvalidRoute` | A route needs a positive share and a nonzero address. |
| 4 | `EInvalidFeeSplit` | A fee split needs at most 20 distinct routes summing to 10,000. |
| 5 | `EInvalidTreasury` | The treasury must be a nonzero address. |
| 6 | `EInvalidPair` | The Meme and Quote types must differ. |
| 7 | `EPartnerMismatch` | Blast's fees pay with exactly the partner the sale named, or with none. |
| 8 | `EWrongVenue` | Only the venue the sale stored can redeem its migration. |
| 9 | `EWrongOwner` | The owner proof must name the vault's package witness and sale. |
| 10 | `EWrongPackageWitness` | The package witness must be the one that sealed the vault terms or the treasury cap. |
| 11 | `EInvalidLpFeeBps` | Blast's LP-fee share of each asset must be at most 3,000 basis points. |
| 12 | `EInvalidRecipient` | A payout recipient must be a nonzero address. |
| 13 | `ELedgerNotEmpty` | A ledger must hold no fees to be destroyed. |
| 14 | `EVenueNotAdmitted` | A venue borrows a sealed treasury cap only with the sealing product's admission of that venue. |

### `blast_core::migration`

The sealed contract between a sale and the venue that migrates it.  Before supply leaves the sale's `TreasuryCap`, a venue prepares the coin and returns a `VenueTicket` sealed by its witness; the product admits and stores the ticket's venue. At migration the product creates a `Migration` sealed by its own witness, carrying the pool's balances and the new vault's terms, and only the stored venue's witness can redeem it. Neither the ticket nor the migration can be dropped, copied, or stored, so a transaction completes the migration whole or aborts.  Every witness is identified by `type_name::with_original_ids`, which stays fixed across upgrades of the venue or product package; allowlists that admit these names must use the same form.  The module also derives the price a concentrated-liquidity venue seeds the pool at, and whether both such venues can seed it, so a product can refuse a sale that could never migrate.

Source: https://github.com/interest-protocol/blast-v2-contracts/blob/main/sui/launch/core/sources/migration/migration.move

### `blast_core::sealed_treasury_cap`

A coin's `TreasuryCap` sealed by the product that created the currency, from publication until that product's `new` opens it.  The seal closes the window in which a coin's creator could mint before a sale starts: between publication and the venue's preparation of the coin, which borrows the cap to reserve the pair's pool creation, the holder of a sealed cap can only hand it to a venue the sealing product admits. The product checks its own venue allowlist and issues a `VenueAdmission` under its package witness; the venue presents the admission with its own witness to borrow the cap. Only the sealing product's witness opens the seal, so the raw cap never reaches a creator's transaction, and a venue reaches it only through code the product admitted. ## API reference: `blast_partners` (Partner codes)

Live on mainnet. This reference matches the published source.

Events: payload structs are emitted directly, each under its own type.

Abort codes: this package aborts with the numeric codes below from whichever module detects the failure; the abort location names that module.

| Code | Constant | Meaning |
| --- | --- | --- |
| 0 | `EInvalidRecipient` | A partner's recipient must not be the zero address. |
| 1 | `EShareAboveMax` | A partner's share must be at most 80% of Blast's fee. |
| 2 | `EUnchanged` | An update must change the value it sets or proposes. |
| 3 | `ENotLiveCap` | Only the partner's applied cap may set its recipient. |
| 4 | `EPartnerNotAccepted` | The partner list does not accept the partner now. |

### `blast_partners::blast_partners`

Blast partner codes, shared by every Blast product.  A partner is one deal: it is paid a share of the fee Blast charges on every trade that names it, in the same transaction. A company holds one `PartnerCap` for all its deals, each a separate partner with its own share. Blast's partner administrator registers partners under a cap, proposes each one's share, and can propose moving a partner to another cap; the cap's holder sets where each of its partners is paid. Initial terms apply at registration. A later share or cap applies only when someone applies it, no sooner than `PARTNER_CHANGE_DELAY_MS` after it was proposed. That delay is fixed: this module never changes it, and the package is published immutable. The recipient the cap holder sets applies at once.  Products call `pay` with Blast's own fee on a trade. `pay` emits `PartnerPaid` for what the partner received; the product records the trade and the amount in its own event. Share and cap lifecycle events come from `blast_admin::delayed`, keyed by `ShareKey` and `CapKey` and owned by the partner.

Source: https://github.com/interest-protocol/blast-v2-contracts/blob/main/sui/launch/partners/sources/blast_partners.move

### `blast_partners::partner_list`

The partners one Blast product accepts, one list per product.  A product embeds a `PartnerList` in the object holding its policy and alone decides who may change it: the list has `store` and no authority of its own, so only the embedding module can reach it mutably. Adding a partner accepts it at once. Removing one keeps it accepted for the fixed delay Blast gives for every change to a partner, `blast_partners::delay_ms()`, so anything built to name it keeps working that long. Sales and trades that already name a removed partner keep paying it; the list only gates naming it anew. Destroying the list ends every acceptance at once, without the delay, so a product destroys it only with the object that embeds it.

### `blast_admin::delayed`

Settings that change only after their applied delay, and the deadline rules every delayed type shares.  A timelock in the Compound/OpenZeppelin sense: schedule, wait the applied delay, then apply; cancellable until applied. Settings live here; one-shot actions in `delayed_action`, allowlists in `delayed_set` and keyed values in `delayed_map`.  Every value carries a module-defined key `K` and the ID of the object that stores it. Constructors take that object's `&UID`, which only the code creating or holding the object has, so no package can attribute a value or its events to another's object. Embedding modules use a struct without a public constructor as `K`, so only their module can pack it. Each delayed module emits every lifecycle fact of its type, generic in `K` and carrying `parent`; embedding modules emit only their own side effects.  Every change, a shorter delay included, waits the delay applied when it was scheduled. A delay can start at zero, so a schedule and its apply in one transaction then act as a setter; there is no other mutation path. No delay exceeds `max_delay_ms`, so a delay can always be changed again. Readers need no Clock.

Source: https://github.com/interest-protocol/blast-v2-contracts/blob/main/sui/governance/admin/sources/delayed/delayed.move

### `blast_admin::package_admin`

One package's sealed Publisher and UpgradeCap, its delayed upgrade decisions, and the role-gated pause controls of its `PackageVersion`, typed by the package's one-time witness.  The native capabilities never leave the shared `PackageAdmin`: only the package itself, with its package witness, borrows the Publisher by immutable reference, nothing lends the UpgradeCap, and the cap acts only through a scheduled upgrade or the one terminal `make_immutable`. Each role is generic over the package's OTW, so the ACL stores `UpgradeAdmin<A>` and `UpgradeAdmin<B>` as distinct grants and one package's administrator never reaches another's PackageAdmin. This package is immutable: no consumer bytecode version gates these calls, and a consumer whose new bytecode compiles the wrong version can still schedule a repair.

Source: https://github.com/interest-protocol/blast-v2-contracts/blob/main/sui/governance/admin/sources/package/package_admin.move

### `blast_admin::package_version`

One package's publication proof, version and pause bits, typed by its one-time witness.  The consumer's initializer turns its one-time witness into an owned `Publication`, which `package_admin::wrap` later converts into the shared `PackageVersion`, fully paused at version one. The consumer compiles its own version constant and checks it with `assert_current`; it also chooses which pause bits exist and pins its package witness, the one type whose value its own code passes to clear pause bits or to borrow its Publisher. Setting and clearing bits and advancing the version are sealed here and reached only through `package_admin`'s role-gated calls, so no package can build a second version or move a version by any other path.
