# Blast contracts: Launchpad integrator reference

> Everything an integrator needs to understand and call bonding-curve coin launches on Sui: launch a coin, trade it on the curve, graduate it into a Cetus or Bluefin pool, and collect LP fees and holder rewards from the LP vault. Sui mainnet only.

This file is self-contained: give it to an AI agent and ask it anything about Launchpad. It also covers the packages its calls depend on: `blast_partners`, `blast_admin`. Other products are in [llms-full.txt](https://github.com/interest-protocol/blast-v2-contracts/blob/main/llms-full.txt), which joins every product in one file.

How it is organized:

1. **Packages and deployment status**: each package, whether it is live on Sui mainnet, and its IDs.
2. **Guides**: how each product works end to end, starting with the calling conventions every product shares. Each product guide opens with its deployment status. Use them for behavior, flows, economics, and pitfalls.
3. **API reference**: generated from the Move source. Every public function and type with its doc comment, every event, every abort code, and the package constants. Use it for exact signatures and field layouts.

When the guides and the reference disagree, the reference is right: it is generated from the source on every change. When this file does not say a behavior exists, treat it as unsupported. Source for every module is linked from the reference ([repository](https://github.com/interest-protocol/blast-v2-contracts)).

Conventions: amounts are atomic units of the coin named; rates are basis points (BPS) out of 10,000; times are Unix milliseconds from Sui's shared `Clock` at `0x6`. Types are written as Move: `module::Type` names a type in another module of the same package, `package::module::Type` one in another Blast package, and well-known Sui framework types appear bare.

## Calling Blast contracts

Every Blast product is a set of Sui Move packages called from programmable
transaction blocks (PTBs). This section covers what every product shares. Each
product guide below assumes it.

### Products and packages

| Product | What users do | Packages |
| --- | --- | --- |
| Presale | commit Quote to a capped or overflow sale, claim tokens or refunds, earn LP fees and holder rewards after migration | `blast_presale`; one-off partner migrators such as `blast_aftermath_dao_presale` |
| Launchpad | launch a coin on a bonding curve, trade it, graduate it into a DEX pool | `blast_fun` (curve, lifecycle, fees), a generated coin package per launch, `blast_fun_migrators` (venue start, migration, LP vault, LP fees, holder rewards) |
| Partner codes | earn a share of Blast's fee on the flow an app brings | `blast_partners` |
| Boosts | hold a leveraged long or short coin backed by Aftermath perpetuals | `blast_boosts_core`, `blast_boosts_products`, `blast_boosts_aftermath` |
| blastSUI | stake SUI with one validator through funSUI and blastSUI | `blast_sui` |
| Administration | Blast's operators manage roles, fees, and upgrades | `blast_admin` (the presale has its own admin caps) |

Each package and what it depends on:

```text
blast_fun_migrators          -> blast_fun, blast_admin, Cetus, Bluefin
blast_fun                    -> blast_partners, blast_admin
blast_partners               -> blast_admin, blast_fun_timelock
blast_presale                -> blast_partners, blast_fun_vesting, Cetus, Bluefin
blast_aftermath_dao_presale  -> blast_presale, Aftermath AMM
blast_boosts_aftermath       -> blast_boosts_core, blast_partners, blast_admin, Aftermath perpetuals
blast_boosts_core            -> blast_admin
blast_sui                    -> blast_admin, Sui system
blast_admin                  -> blast_fun_timelock
```

The launchpad imports no DEX. A migrator package depends on the launchpad and
composes with it inside one PTB. The presale is a separate product: it shares
no state or code with the launchpad or the migrators, keeps its own admin caps
instead of `blast_admin`, and holds migrated liquidity in its own
`presale_vault::Vault`. Answer presale questions from the presale guide alone.

`blast_fun_timelock` and `blast_fun_vesting` come from Blast's public utility
repository (`interest-protocol/blast-util-contracts`); both are immutable on
mainnet.

### Building a call

- **Target.** A call is `moveCall` with target
  `<package-id>::<module>::<function>`. Use the package ID (`published-at`) from
  the deployment table.
- **Type arguments.** Pass fully qualified type strings. A Blast type is named by
  the package that first defined it (`original-id`), even after an upgrade.
- **`TxContext`.** A trailing `ctx: &TxContext` or `&mut TxContext` parameter is
  supplied by Sui. Leave it out of the arguments.
- **Shared objects.** Pass a shared object by ID. A `&` parameter takes it
  read-only, `&mut` or by value takes it mutably; mutable access orders the
  transaction through consensus with every other writer of that object.
- **System objects.** `Clock` is `0x6` (always `&Clock`), the Sui system state is
  `0x5`, and the Coin Registry is `0xc`.
- **Coins in.** A function that takes `Coin<T>` by value consumes it whole. Split
  the exact amount first (`SplitCoins`; for SUI, split from the gas coin) and
  merge several coins first when needed (`MergeCoins`).
- **Values out.** Most Blast functions return coins and objects instead of
  transferring them. Every returned value without the `drop` ability must be used
  before the PTB ends: transfer it (`TransferObjects`), pass it to a later call,
  or merge it. A value with no abilities at all (a "hot potato", such as a
  launch initializer or a migration handoff) can only be consumed by the specific
  later call that accepts it, so the whole sequence must sit in one PTB.
- **Basis points.** Each package that takes rates defines its own validated
  `Bps` type in its `bps` module. Build one inside the PTB with that package's
  constructor, for example `blast_presale::bps::new` or `blast_fun::bps::new`,
  which aborts above 10,000. A `blast_fun` `Bps` is a different type from a
  `blast_presale` `Bps`.
- **Options.** Pass `Option<T>` arguments with `0x1::option::some` or
  `0x1::option::none` calls, or as pure BCS-encoded options.

### Reading state

- **Getters** are public functions that take `&` objects and return values. Run
  them through a dev-inspect or simulated transaction to read without signing
  or paying.
- **Object fields** can be read directly from a full node and decoded with BCS.
  The API reference prints every struct with its fields in declaration order,
  which is the BCS order. Fields are readable on chain even though Move code
  outside the module cannot access them.
- **Per-user records** (commitments, claims) usually live in dynamic fields
  keyed by a small key struct the reference lists; read them with the
  dynamic-field RPC calls.
- **Events** reconstruct history; contract state and completed events are the
  source of truth, and any off-chain preview is an estimate.

### Versions and upgrades

Each package has one upgrade posture:

| Posture | Packages | What callers do |
| --- | --- | --- |
| Immutable | `blast_admin`, `blast_partners`, `blast_boosts_core`, `blast_aftermath_dao_presale` | Nothing: the code never changes. |
| Dependency-only | `blast_presale` | Presale logic is sealed; Blast can only relink newer Cetus and Bluefin versions, and every generation runs identical code with no version gate. Call the latest package ID, because a venue rejects calls linked to a version it retired. |
| Version-gated | `blast_fun`, `blast_fun_migrators`, `blast_sui`, `blast_boosts_aftermath` | Mutating calls take the package's shared version object. After an upgrade advances it, calls through an older package ID abort with a version mismatch, so always call the current ID. |
| Additive | `blast_boosts_products` | Upgrades only add product tags; it holds no state. |

### Events

- Query events by their Move type, named with the `original-id`.
- `blast_fun`, `blast_sui`, and `blast_boosts_aftermath` wrap every payload in
  the `Event<T>` envelope of their own `blast_events` module (for example
  `blast_fun::blast_events::Event`), so the event type is
  `<original-id>::blast_events::Event<<original-id>::<module>::<Payload>>`.
  Every other package emits payload structs directly.
- Sui orders events by checkpoint, transaction, and event index within the
  transaction; payloads carry no sequence numbers of their own.
- The reference lists every event struct under its module with its fields.

### Errors

A failed call returns a Move abort naming the module and function that aborted
and a `u64` code. Blast uses two styles:

- **Named errors** (`#[error]` constants): `blast_presale`, `blast_partners`,
  `blast_fun_migrators`, and `blast_aftermath_dao_presale`. Sui's RPC and SDKs
  decode these into the constant's name and message; the reference lists each
  module's constants with their messages.
- **Numeric codes**: `blast_fun`, `blast_sui`, `blast_boosts_core`,
  `blast_boosts_aftermath`, and `blast_admin` abort with small integers. Look the
  number up in that package's abort-code table in the reference.

The abort names the module where it happened, which may be a package called
underneath the one you called: a migrator call can abort inside `blast_fun` or
`blast_admin`, and an abort in a Cetus, Bluefin, or Aftermath module comes from
the venue. Simulate a transaction before signing to see its abort without
spending gas.

### Network

Blast deploys only to Sui mainnet. There is no testnet deployment, faucet, or
test address. Try a transaction with a mainnet simulation (dev-inspect or dry
run) before signing it.

## Launchpad

> **Deployment status:** `blast_fun` is not yet published on mainnet; its interface may change before publication.

### What it is

The Blast launchpad (package `blast_fun`) launches a new coin on a bonding curve. A creator
publishes a small generated coin package, which mints exactly one billion whole tokens into a
`launch_ticket::LaunchTicket`. The creator turns the ticket into a `launch::Launch<Meme, Quote>`
through a migration adapter (Cetus or Bluefin), choosing the curve's starting price, the Quote
amount at which the curve closes (the graduation target), how the supply and the final Quote are
split at migration, and how the future pool's LP fees are split. Anyone then buys and sells `Meme`
against `Quote` on a constant-product curve. When the curve's real Quote reserve reaches the
target, trading stops and the launch becomes `MigrationReady`; the adapter then moves the pool's
share of Meme and Quote into a new Cetus or Bluefin pool. `Meme` is the generated coin type and
`Quote` is the coin it trades against (for example SUI). Blast takes a share of every trade fee, a
SUI creation fee, and an optional one-time share of the supply and of the final Quote; a Blast partner named at
creation earns a cut of Blast's fees.

This guide covers everything up to and including `MigrationReady`, and what the launchpad itself
does when an adapter migrates. The pool, the `blast_fun_migrators::vault::LpVault`, LP-fee
collection, auto-LP, buyback, and holder rewards are in the migrators guide.

### Objects and authority

#### Shared objects

| Object | Created | Holds | Who writes it |
| --- | --- | --- | --- |
| `blast_fun::blast_fun::PackageVersion` | `blast_fun::package_admin::wrap` | the active package generation | upgrade admin only |
| `launch_config::LaunchConfig` | package publish | policy that new launches snapshot: admitted Meme decimals, admitted Quote types, trade fees, admitted adapters, Blast's migration allocation, the creation fee, accepted partners | Blast admins |
| `runtime_config::RuntimeConfig` | package publish | settings read live: the account-claim signer key, Blast's share of every trade fee, the treasury address | Blast admins |
| `launch::Launch<Meme, Quote>` | `launch::finalize`, shared by `launch::share` | one launch: lifecycle, curve reserves, settings, fee ledger, opening-round pot, migration allocations | trades, claims, migration |
| `blast_fun::package_admin::PackageAdmin` | `blast_fun::package_admin::wrap` | the package's `Publisher` and `UpgradeCap` | upgrade admin only |
| `Currency<Meme>` | `0x2::coin_registry::finalize_registration` | the coin's name, symbol, decimals, description, icon URL, and supply state (Sui Coin Registry) | the launch, through its internal `MetadataCap<Meme>` |

`launch::new` and configuration setters require the shared `PackageVersion`. It does not exist
until `blast_fun::package_admin::wrap` consumes the publication bootstrap and the matching,
never-upgraded native UpgradeCap. That transaction seals both native capabilities in
`PackageAdmin` and creates `PackageVersion` atomically. A rejected wrap leaves the bootstrap
intact and the launchpad inactive. After activation, version-guarded calls abort when the caller
links old bytecode after an upgrade (see Aborts).

#### Owned objects and capabilities

- `blast_fun::blast_fun::Bootstrap` (`key` only): created once at package publication and sent
  to the deployer. It holds the canonical Publisher and initial operational generation. Its
  only production consumer is `blast_fun::package_admin::wrap`; it cannot be transferred by
  another package, shared, or used in place of `PackageVersion`.
- `launch_ticket::LaunchTicket<Meme>` (`key, store`): created when the generated coin package is
  published and sent to the publisher. It holds the whole supply as a `Balance<Meme>`, the
  `TreasuryCap<Meme>`, the `MetadataCap<Meme>`, the creator recipient, the decimals, the supply
  mode (`burnable`), and the sell-burn rate. The holder starts a launch with it; the ticket can be
  transferred first. No call releases its contents except launch finalization.
- `creator_authority::CurveFeeCap<Meme>` (`key, store`): authority over the launch's creator trade
  fees, and after migration over the creator's LP-fee share and the LP-fee split in the
  migrators' vault. The launch honors only the cap ID it records in `curve_fee_cap_id`.
- `creator_authority::BlastMetadataCap<Meme>` (`key, store`): authority to change the coin's name,
  description, and icon URL through the launch. The launch honors only the cap ID in
  `blast_metadata_cap_id`.
- Both caps are issued once by `launch::claim_creator_caps` to the creator recipient, or reissued
  by a Blast creator admin. A holder may delete a cap with
  `creator_authority::destroy_curve_fee_cap` or `creator_authority::destroy_metadata_cap`;
  deleting the live cap leaves fees unclaimable (or metadata frozen) until an admin reassigns it.

The native `MetadataCap<Meme>` never leaves the launch, and finalization consumes the
`TreasuryCap<Meme>` into the Coin Registry, so no one can ever mint more Meme.

#### Creator recipient

`creator_authority::CreatorRecipient` names who may claim the creator caps. It is fixed in the
generated package and carried by the ticket into the launch. It may differ from the launcher (the
wallet that publishes and launches).

- `Address(address)`: built by `creator_authority::new_address` (non-zero). That wallet claims by
  sending the claim transaction itself.
- `Account(vector<u8>)`: built by `creator_authority::new_account` from a 32-byte opaque Blast
  account commitment. Any wallet claims by presenting an expiring signature from the Blast
  backend that binds the commitment to that wallet (see Flows).

#### Values built inside a PTB

These have `copy, drop, store` and cannot be passed as pure arguments; build them with their
constructors in the same PTB:

- `blast_fun::bps::Bps`: a rate from 0 to 10,000 basis points, built by `blast_fun::bps::new`
  (aborts above 10,000).
- `allocation::Recipient` (`allocation::recipient`), `allocation::AllocationPlan`
  (`allocation::plan`), `allocation::Route` (`allocation::route`), `allocation::FeeSplit`
  (`allocation::fee_split`).

`launch::LaunchInitializer<Meme, Quote>` has no abilities: it must be consumed by `launch::finalize`
in the PTB that created it. `launch::Launch` has only `key`: it must be shared with `launch::share`
in that same PTB.

#### Admin roles

Blast administration uses the shared ACL from `blast_admin`. A Blast admin holds a
`blast_acl::AdminCap` granted roles; in a PTB it calls `blast_acl::sign_in<Role>` with the shared
`blast_acl::ACL` to get a `blast_acl::AdminWitness<Role>`, which the setter takes by reference. A
role authorizes only the functions that name it. The roles are types in `blast_fun_domain`:

| Role | Launchpad functions it authorizes |
| --- | --- |
| `blast_fun_domain::UpgradeAdmin` | `blast_fun::package_admin::authorize_upgrade`, `blast_fun::package_admin::commit_upgrade_and_advance`, `blast_fun::package_admin::make_immutable` |
| `blast_fun_domain::CreatorAdmin` | `launch::reassign_curve_fee_cap`, `launch::reassign_metadata_cap` |
| `blast_fun_domain::TreasuryAdmin` | `launch_config::set_protocol_allocation`, `runtime_config::set_treasury` |
| `blast_fun_domain::FeeAdmin` | `launch_config::set_trade_fees`, `launch_config::set_creation_fee`, `launch_config::add_partner`, `launch_config::remove_partner`, `runtime_config::set_protocol_fee_share` |
| `blast_fun_domain::ListingAdmin` | `launch_config::set_meme_decimals_allowed`, `launch_config::set_quote_allowed` |
| `blast_fun_domain::AdapterAdmin` | `launch_config::set_migration_witness_allowed` |
| `blast_fun_domain::ClaimSignerAdmin` | `runtime_config::set_creator_claim_signer` |
| `blast_fun_domain::BuybackAdmin`, `blast_fun_domain::RewardsAdmin` | migrators only (buyback, holder-reward rounds) |

Integrators cannot call these. What each setter changes is under "Admin operations".

### Lifecycle

`launch::Lifecycle` has four states:

```text
[OpeningRound ->] Live -> MigrationReady -> Migrated
```

| State | Entered by | Allows |
| --- | --- | --- |
| `OpeningRound` | `launch::finalize` with a non-zero opening round | `launch::join_opening_round` until the round ends (the creator also before share); `launch::settle_opening_round` once it has ended |
| `Live` | `launch::finalize` without an opening round, or `launch::settle_opening_round` | `launch::buy` (also before share, so the creator can buy first); `launch::sell` only after share |
| `MigrationReady` | a buy, or the opening-round settlement, that leaves the real Quote reserve at or above the graduation target | migration by the launch's own adapter; no trading |
| `Migrated` | `launch::migrate` (called by the adapter) | nothing on the curve |

Separately, `public_start_ms` is set once by `launch::share`. In every state:
`launch::claim_creator_caps` (after share), `launch::claim_creator_fees`, metadata updates,
`launch::claim_protocol_fees` and `launch::claim_protocol_fees_with_partner`, and admin
reassignments. `launch::deliver_opening_round` works in every state after `OpeningRound`, including
`Migrated`. A launch that never reaches its target stays `Live` forever: there is no cancel,
expiry, or refund path.

### Flows

Creating a launch takes three transactions, because each step needs an object the previous one
creates.

#### Flow 1: publish the generated coin package (anyone; the publisher receives the ticket)

The coin is a one-module package built from the `launch_ticket_template` template. Its only code is an
initializer that runs at publish: it builds the creator recipient and calls `launch_ticket::new`
with the package's one-time witness, then transfers the ticket to the publisher. It exposes no
public functions. Patch these constants in the compiled template:

| Constant | Meaning | Checked |
| --- | --- | --- |
| `SYMBOL` | coin symbol | ASCII printable (Coin Registry); at most 32 bytes at finalization |
| `NAME`, `DESCRIPTION`, `ICON_URL` | coin metadata | valid UTF-8; changeable later with the metadata cap |
| `DECIMALS` | coin decimals | must be admitted in `LaunchConfig` when the launch starts; default admitted set is 6 and 9 |
| `BURNABLE` | `true`: supply becomes burn-only; `false`: supply becomes fixed | none |
| `SELL_BURN_BPS` | share of each sale's post-fee Meme set aside to burn | at most 5,000 (50%), at publish and again at finalization |
| `CREATOR_RECIPIENT_BYTES`, `CREATOR_IS_ACCOUNT` | 32 bytes: an account commitment, or an address when `CREATOR_IS_ACCOUNT` is `false` | address must be non-zero |

In the template the coin type is `<new package>::meme::MEME`. Blast's own launch tooling renames
the module and witness after the symbol, so take a coin's exact type from its publish effects or
from `blast_fun::events::LaunchTicketCreated` rather than assuming `meme::MEME`. Patch the dependency address to the launchpad's original
package ID and publish with every transitive dependency: `0x1`, `0x2`, and the current package IDs
of the launchpad, `blast_admin`, `blast_partners`, and `blast_fun_timelock` (Sui rejects a publish
whose dependency list misses one of the launchpad's own dependencies). Handle the `UpgradeCap` that the Publish command
returns (transfer it or make the package immutable); it grants no authority over the coin.

Publishing:

1. Creates the currency through the Coin Registry one-time-witness path and mints
   `1_000_000_000 * 10^decimals` atomic units (aborts on `u64` overflow, so decimals above 10
   fail).
2. Sends `LaunchTicket<Meme>` to the publisher and the unregistered `Currency<Meme>` to the Coin
   Registry address `0xc`.
3. Emits `blast_fun::events::LaunchTicketCreated`.

#### Flow 2: register the currency (anyone)

Call `0x2::coin_registry::finalize_registration<Meme>` with the shared `CoinRegistry` at `0xc`
and the pending `Currency<Meme>` as a `Receiving` argument. It re-creates the currency as a shared
object at a derived address. Use that shared `Currency<Meme>` in every later step.

#### Flow 3: create, configure, and share the launch (ticket holder, one PTB)

Type arguments are `<Meme, Quote>` on every adapter and `launch` call below. `Clock` is the shared
object at `0x6`.
`launch::new` needs the adapter's witness, which only the adapter module can construct, so a
launch always starts through an adapter's `new`; only that adapter can borrow the ticket's treasury
cap during the PTB (`launch::treasury_cap_mut`).

1. Start the launch through an admitted adapter. Both return a `LaunchInitializer<Meme, Quote>`:
   - Cetus: `blast_fun_migrators::cetus::new` takes the owned ticket, the migrators'
     `blast_fun_migrators::blast_fun_migrators::PackageVersion` (shared), the launchpad
     `PackageVersion` (shared), `LaunchConfig` (shared), the migrators'
     `blast_fun_migrators::venue_config::VenueConfig` (shared, mutable), Cetus's `GlobalConfig`
     (shared) and `Pools` (shared, mutable), and `tick_spacing: u32`. The fee rate is the one
     Cetus registers for that tick spacing; the call aborts when Cetus does not register the
     spacing or refuses the pair at it. It mints the Meme type's single Cetus `PoolCreationCap`
     from the ticket's treasury cap, registers the pair at the tick spacing, keeps the cap in
     `VenueConfig`, and emits `blast_fun_migrators::blast_events::CetusPoolReserved`. From then on
     only that cap or Cetus's own pool-manager role can create the pair's pool at that spacing, so
     no buyer can create the migration pool first.
   - Bluefin: `blast_fun_migrators::bluefin::new` takes the owned ticket, the migrators'
     `PackageVersion`, the launchpad `PackageVersion`, `LaunchConfig`, `tick_spacing: u32` (1 to
     400), and `fee_rate: u64` (1 to 20,000, Bluefin's units); otherwise it aborts with
     `blast_fun_migrators::bluefin::EInvalidTier`.

   Inside, `launch::new` checks that Meme and Quote differ, that `Quote`, the adapter's witness,
   and the decimals are admitted in `LaunchConfig`, and snapshots the trade fees. The pool tier
   (tick spacing, fee rate) is fixed from here on.
2. `launch::set_virtual_quote` with the initializer (mutable) and a `u64`: the virtual Quote
   reserve, in Quote atomic units. Required, non-zero. It sets the opening price.
3. `launch::set_graduation_target` with the initializer and a `u64`: the real Quote reserve at
   which trading closes. Required.
4. Build the allocation plan: one `blast_fun::bps::new` per share; one `allocation::recipient` per
   project recipient (address, Meme share, Quote share); a `MakeMoveVec` of type
   `allocation::Recipient` (may be empty); then `allocation::plan` with the curve Meme share, pool
   Meme share, pool Quote share, and the vector. Pass it to `launch::set_allocation_plan`.
   Required.
5. Build the LP-fee split: one `allocation::route` per extra recipient (address, share); a
   `MakeMoveVec` of type `allocation::Route`; then `allocation::fee_split` with the creator,
   auto-LP, rewards, and burn shares and the vector. Pass it to `launch::set_lp_fee_split`.
   Required.
6. Optional: `launch::set_opening_round` with a length in ms: 0 (default, no round) or 60,000 to
   300,000.
7. Optional: `launch::set_partner` with `LaunchConfig`, a `blast_partners::blast_partners::Partner`
   (shared, immutable), and `Clock`. The partner must be one `LaunchConfig` accepts now. This is the
   only time a launch can name a partner.
8. Pay the creation fee: `SplitCoins` from the gas coin for exactly `LaunchConfig.creation_fee`
   MIST (use `0x2::coin::zero<0x2::sui::SUI>` when it is zero).
9. `launch::finalize` consumes the initializer and takes the shared `Currency<Meme>` (mutable),
   `LaunchConfig`, and the fee coin. It returns the `Launch<Meme, Quote>` value. It checks every
   setting (see Aborts), copies Blast's current allocation into the plan and requires each asset to
   sum to 10,000, fixes the supply as burn-only or fixed in the Coin Registry (consuming the
   treasury cap), keeps the curve's Meme as `meme_reserve` and the rest as `allocated_meme`, stores
   the creation fee in the fee ledger, and emits `blast_fun::events::LaunchCreated`. The lifecycle
   is `OpeningRound` when an opening round was set, else `Live`.
10. Optional creator purchase before anyone else can trade:
    - without an opening round: `launch::buy` on the launch value (see Buy); transfer both returned
      coins. A buy here may even reach the target.
    - with an opening round: `launch::join_opening_round` on the launch value (see Opening round);
      the creator's bid joins the same pot at the same price as everyone's.
11. `launch::share` consumes the launch value and takes `Clock`: it records `public_start_ms`
    (now), shares the launch, and emits `blast_fun::events::LaunchShared`. The opening round, if
    any, ends `opening_round_ms` later. This must be the launch's last use in the PTB.

The creator caps cannot be claimed in this PTB; claim them in a later transaction.

#### Opening round (anyone)

1. Join: `launch::join_opening_round` with the shared launch, `PackageVersion`, a `Coin<Quote>`
   (non-zero), and `Clock`. It adds the coin to one pot and to the sender's bid, kept as a dynamic
   field `launch::OpeningRoundBidKey(sender)` on the launch. Repeated joins add up. Emits
   `blast_fun::events::OpeningRoundJoined`. Allowed until `public_start_ms + opening_round_ms`.
2. Settle: from that time on, anyone calls `launch::settle_opening_round` with the launch,
   `PackageVersion`, `RuntimeConfig`, and `Clock`. The lifecycle becomes `Live`, and the whole pot
   buys from the curve once, with the usual fees, the graduation cap, and no minimum output. The
   Meme bought and any Quote refunded stay in the launch for delivery. A zero-output pot is
   refunded whole unless its net Quote reaches the target. A target-reaching pot is charged even
   when it returns zero Meme. Emits `blast_fun::events::Bought` (when Quote enters the reserve) and `blast_fun::events::OpeningRoundSettled`. If the pot reached the target, the
   launch is `MigrationReady` at once.
3. Deliver: anyone calls `launch::deliver_opening_round` with the launch, `PackageVersion`, and the
   bidder's address. The bidder (not the caller) receives its pro-rata Meme and Quote as coins, and
   its bid record is removed. Emits `blast_fun::events::OpeningRoundDelivered`. One call per
   bidder; it works in any later state.

#### Buy (anyone)

Split the exact input from your Quote coins (from the gas coin when Quote is SUI). `launch::buy`
takes the shared launch, `PackageVersion`, `RuntimeConfig`, that `Coin<Quote>`, and
`min_meme_out: u64`. It returns `(Coin<Meme>, Coin<Quote>)`: the Meme bought (after the Meme fee)
and the Quote refunded past the graduation target. The refund coin is usually zero-valued; it has
no `drop`, so transfer it or destroy it with `0x2::coin::destroy_zero`. Emits
`blast_fun::events::Bought`. The buy that reaches the target makes the launch `MigrationReady`.
That final buy may return zero Meme because of rounding or Meme fees, but only with
`min_meme_out = 0`. A positive minimum still aborts; nonterminal zero-output buys abort too.
The target cap and fees still apply, and excess Quote is refunded.

#### Sell (anyone, after share)

Merge your Meme coins and split the amount to sell. `launch::sell` takes the shared launch,
`PackageVersion`, `RuntimeConfig`, that `Coin<Meme>`, and `min_quote_out: u64`, and returns the
Quote after fees as a `Coin<Quote>`. The Meme fee and the sell-burn share are taken from the input
first; the sell-burn Meme waits in `pending_burn` until migration. Emits
`blast_fun::events::Sold`. Trades take no deadline and no `Clock`: the minimum output is the only
price protection.

#### Claim the creator caps (creator recipient, after share)

`launch::claim_creator_caps` takes the shared launch, `PackageVersion`, `RuntimeConfig`, an
`Option<vector<u8>>` attestation, and `Clock`. It returns a `CurveFeeCap<Meme>` and a
`BlastMetadataCap<Meme>`; transfer both to the sender. It works once, in any state after share.
Emits `blast_fun::events::CreatorCapsClaimed`.

- Address recipient: the sender must be that address; pass `None`.
- Account recipient: pass `Some(attestation)`, obtained from the Blast backend for the sending
  wallet. The attestation is the BCS encoding of `(expiry_ms: u64, signature: vector<u8>)`, 73 bytes
  for a 64-byte signature, with nothing after it. The call checks `Clock` time `<= expiry_ms` and
  verifies the Ed25519 signature with `RuntimeConfig.creator_claim_signer_public_key` over the raw
  BCS bytes of `creator_authority::CreatorClaimMessage`, whose fields in order are `meme`,
  `account_commitment`, `claimant`, and `expiry_ms`. Here `meme` is the Meme `TypeName` with
  original package IDs (64 hex characters, no `0x`, then `::module::NAME`) and `claimant` is the
  sender. The signed bytes are: the type-name string's ULEB128 length and ASCII bytes, `0x20` and
  the 32-byte commitment, the 32-byte claimant address, then `expiry_ms` as 8 little-endian bytes.
  There is no intent prefix or extra hash.

#### Claim creator trade fees (CurveFeeCap holder)

`launch::claim_creator_fees` takes the shared launch, `PackageVersion`, and `&CurveFeeCap<Meme>`,
and returns `(Coin<Meme>, Coin<Quote>)` holding all creator fees accrued so far (one may be zero).
Works in any state, including after migration. Emits `blast_fun::events::CreatorFeesClaimed`.
Post-migration LP fees are claimed from the migrators' vault with the same cap.

#### Update coin metadata (BlastMetadataCap holder)

`launch::set_name`, `launch::set_description`, and `launch::set_icon_url` each take the launch (by
immutable reference), `PackageVersion`, `&BlastMetadataCap<Meme>`, the shared `Currency<Meme>`
(mutable), and the new `String`. The value must differ from the current one. Works in any state.
Each emits `blast_fun::events::MemeMetadataUpdated` with all three current values. Symbol and
decimals never change.

#### Claim Blast's fees (anyone)

Blast's fees on a launch (its trade-fee share, the creation fee, and the one-time migration
allocation) wait in the launch's fee ledger until anyone pays them out:

- Launch without a partner: `launch::claim_protocol_fees` with the launch, `PackageVersion`, and
  `RuntimeConfig`. Sends every Blast balance (Meme, Quote, SUI) to `RuntimeConfig.treasury`.
- Launch with a partner: `launch::claim_protocol_fees_with_partner` with the launch,
  `PackageVersion`, `RuntimeConfig`, the launch's `Partner` (shared), and `Clock`. Each balance
  first pays the partner its share through `blast_partners::blast_partners::pay`, then the rest goes
  to the treasury.

Both emit `blast_fun::events::ProtocolFeesClaimed`. Calling the wrong one aborts with
`EPartnerMismatch`. Zero balances send nothing.

#### Migration, launchpad side (anyone, through the adapter)

Anyone triggers migration of a `MigrationReady` launch through its adapter
(`blast_fun_migrators::cetus::migrate` or `blast_fun_migrators::bluefin::migrate`; arguments in the
migrators guide). The adapter calls `launch::migrate` with its witness, which checks the lifecycle
and that the witness is the one the launch stored, then:

1. Apportions the Meme supply and the final real Quote reserve by the allocation plan (see
   Economics).
2. Pays every project recipient its Meme and Quote as coins (zero amounts are skipped) and emits
   `blast_fun::events::MigrationAllocationPaid` for each recipient.
3. Moves Blast's Meme and Quote allocation into the launch's protocol fee ledger and, when either is
   non-zero, emits `blast_fun::events::ProtocolFeesAccrued`.
4. Disposes of the curve's unsold Meme plus `pending_burn`: burned through the Coin Registry when
   the supply is burn-only, otherwise sent to `@0x0`.
5. Sets `Migrated`, emits `blast_fun::events::Migrated`, and returns the pool's Meme and Quote
   balances to the adapter, which creates the pool and the vault in the same transaction.

Any failure aborts the whole transaction and leaves the launch `MigrationReady` with every balance
in place. The opening-round balances awaiting delivery are untouched.

#### Admin operations (Blast admin)

Each setter takes the object it changes, `PackageVersion`, and the role's `AdminWitness`, and
emits an event. Value setters abort with `blast_fun::errors::EUnchanged` when nothing would change. The
allow/remove toggles for Quotes, decimals, and adapters instead abort inside the Sui collection
(`sui::dynamic_field` or `sui::vec_set`) when the entry already has the requested state.

- `launch_config::set_quote_allowed<Quote>` (ListingAdmin), with `allowed: bool`: admits or removes
  a Quote for new launches; existing launches keep trading. Emits `blast_fun::events::QuoteSet`.
- `launch_config::set_meme_decimals_allowed` (ListingAdmin), with `decimals: u8` and `allowed`.
  Emits `blast_fun::events::MemeDecimalsSet`.
- `launch_config::set_migration_witness_allowed<Witness>` (AdapterAdmin), with `allowed`: admits or
  removes an adapter; rejects types defined at `0x1` or `0x2`. Existing launches keep their adapter.
  Emits `blast_fun::events::MigrationWitnessSet`.
- `launch_config::set_trade_fees` (FeeAdmin), with Quote and Meme fee `Bps`, each at most 1,000;
  only launches started afterward use them. Emits `blast_fun::events::LaunchTradeFeesChanged`.
- `launch_config::set_creation_fee` (FeeAdmin), with an amount in MIST. Emits
  `blast_fun::events::CreationFeeChanged`.
- `launch_config::set_protocol_allocation` (TreasuryAdmin), with Meme and Quote `Bps`: Blast's
  one-time share for launches finalized afterward; Meme at most 9,998 and Quote at most 9,999.
  Emits `blast_fun::events::ProtocolAllocationSet`.
- `launch_config::add_partner` (FeeAdmin), with a `Partner`: new launches may name it at once;
  cancels a pending removal. Emits `blast_fun::events::PartnerAdded`.
- `launch_config::remove_partner` (FeeAdmin), with a `Partner` and `Clock`: new launches may still
  name it for `blast_partners::blast_partners::delay_ms` (seven days); launches that already name it
  keep paying it. Aborts with `EPartnerNotAccepted` when it is not accepted now. Emits
  `blast_fun::events::PartnerRemoved`.
- `runtime_config::set_protocol_fee_share` (FeeAdmin), with a `Bps`: Blast's share of every trade
  fee on every launch, from the next trade. Emits `blast_fun::events::ProtocolFeeShareChanged`.
- `runtime_config::set_treasury` (TreasuryAdmin), with a non-zero address: every later Blast fee
  claim on every launch pays it. Emits `blast_fun::events::TreasuryChanged`.
- `runtime_config::set_creator_claim_signer` (ClaimSignerAdmin), with a 32-byte Ed25519 public key,
  or empty bytes to stop all account claims. Emits `blast_fun::events::CreatorClaimSignerSet`.
- `launch::reassign_curve_fee_cap` and `launch::reassign_metadata_cap` (CreatorAdmin), with a
  non-zero recipient: mint a fresh cap, record it as the live one, send it to the recipient, and
  cancel any unclaimed creator claim. The old cap stops working; unclaimed curve fees follow the
  new cap. Emit `blast_fun::events::CurveFeeCapReassigned` or
  `blast_fun::events::MetadataCapReassigned`.
- Upgrades (UpgradeAdmin): `blast_fun::package_admin::authorize_upgrade` returns an
  `UpgradeTicket` for an exact digest; after the Upgrade command,
  `blast_fun::package_admin::commit_upgrade_and_advance` commits the receipt and advances
  `PackageVersion` in the same transaction; `blast_fun::package_admin::make_immutable` ends
  upgrades for good.

### Economics

All amounts are atomic units. Rates are BPS out of 10,000. `ceil` rounds up, `floor` rounds down.

#### Supply

Every generated coin has exactly `1_000_000_000 * 10^decimals` atoms, minted once. Finalization
re-checks the ticket's balance and the treasury cap's supply against this amount and fixes the
supply in the Coin Registry. After that no one can mint. Under a burn-only supply anyone can burn
Meme through the Coin Registry; a fixed supply cannot be burned, so the launch sends its
disposals to `@0x0` instead.

#### Allocation plan

An `AllocationPlan` splits two totals at migration:

- Meme supply: `curve_meme_bps` (sold on the curve) + `lp_meme_bps` (seeds the pool) + Blast's
  `protocol_meme_bps` + each recipient's `meme_bps` = 10,000. Curve and pool Meme shares must be
  positive.
- Final real Quote reserve: `lp_quote_bps` (seeds the pool) + Blast's `protocol_quote_bps` + each
  recipient's `quote_bps` = 10,000.

The creator's plan leaves Blast's fields at zero; `launch::finalize` copies
`LaunchConfig.protocol_allocation` into them and then checks both sums. So the creator's shares
must sum to 10,000 minus Blast's current share for each asset. At most 16 recipients; each
destination is non-zero (`allocation::plan` does not reject repeated addresses). The plan is fixed
for the launch's life. Finalization also requires the pool's Quote share of the graduation target
to be at least one atom.

Apportionment (used for the Meme supply at finalization and migration, and for the Quote at
migration): each part's exact share is `total * bps / 10,000` in `u128`. Blast's part takes the
ceiling; every other part takes the floor; the leftover atoms go one each to the parts with the
largest remainders, earlier parts first on ties. Part order is curve, pool, Blast, recipients in
plan order for Meme, and pool, Blast, recipients for Quote. The parts sum exactly to the total.

At finalization the curve's part becomes `meme_reserve`; the pool, Blast, and recipient parts wait
in `allocated_meme`. At migration recipients are paid, Blast's parts enter the fee ledger, and the
pool's parts go to the adapter. Unsold curve Meme is disposed of, never paid to anyone.

#### Curve math

Let `M = meme_reserve`, `V = virtual_quote`, `Q = real_quote_reserve`, `T = graduation_target`,
`fq = quote_fee_bps`, `fm = meme_fee_bps`, `s = sell_burn_bps`. The curve is constant product over
`(V + Q) * M`; the virtual reserve never leaves the launch. Spot price in Quote atoms per Meme atom
is `(V + Q) / M`.

Buy with `q` Quote supplied:

1. Cap: `R = T - Q`. If `q - ceil(q * fq / 10,000) <= R`, the gross input is `q` and the refund 0.
   Otherwise gross `g = ceil(R * 10,000 / (10,000 - fq))` and refund `q - g`.
2. `quote_fee = ceil(g * fq / 10,000)`; `net = g - quote_fee`.
3. `meme_out_gross = floor(M * net / (V + Q + net))`.
4. `meme_fee = ceil(meme_out_gross * fm / 10,000)`; `meme_out_net = meme_out_gross - meme_fee`.
5. If `meme_out_net` is 0, `launch::buy` aborts with `EZeroTradeOutput` (settlement instead keeps
   the pot for refund). If it is below `min_meme_out`, abort `ESlippageExceeded`.
6. `Q += net`, `M -= meme_out_gross`. If `Q >= T`, the launch becomes `MigrationReady`. Because of
   rounding the final `Q` can sit a few atoms above `T`.

Sell with `m` Meme:

1. `meme_fee = ceil(m * fm / 10,000)`.
2. `burn = ceil((m - meme_fee) * s / 10,000)`, added to `pending_burn`.
3. `x = m - meme_fee - burn` reaches the curve: `quote_out_gross = floor((V + Q) * x / (M + x))`.
4. `quote_fee = ceil(quote_out_gross * fq / 10,000)`;
   `quote_out_net = quote_out_gross - quote_fee`. Abort `EZeroTradeOutput` when it is 0, and
   `ESlippageExceeded` when below `min_quote_out`.
5. `M += x`, `Q -= quote_out_gross`.

Every rounding favors the curve and the fee ledger over the trader.

#### Trade fees and Blast's share

`quote_fee_bps` and `meme_fee_bps` are copied from `LaunchConfig` when the launch starts and never
change (each at most 1,000). On every trade (and the settlement purchase) each fee splits as
`protocol = ceil(fee * p / 10,000)` and `creator = fee - protocol`, where `p` is
`RuntimeConfig.protocol_fee_share_bps` read live at that trade. Both parts stay in the launch's fee
ledger: the creator part until `launch::claim_creator_fees`, Blast's part until a permissionless
Blast fee claim.

#### Creation fee

Exactly `LaunchConfig.creation_fee` MIST of SUI, whatever the Quote, paid at finalization into the
ledger's `protocol_sui` balance. It is Blast's and is claimed with the other Blast fees.

#### Partner payouts

A partner named at creation is the launch's partner for good (`partner_id`), and its LP vault
inherits it after migration. When Blast's fees are claimed, each balance (Meme, Quote, SUI) pays the
partner `floor(balance * share_bps / 10,000)`, with `share_bps` the partner's share in force at the
claim (set by Blast, at most 8,000); Blast's treasury gets the rest. The partner's cut covers trade
fees, the creation fee, and the one-time migration allocation.

#### LP-fee split

The `FeeSplit` set at launch divides every future LP-fee collection, after Blast's LP-fee share,
into `creator_bps`, `auto_lp_bps`, `rewards_bps`, `burn_bps`, and up to 16 extra routes (non-zero,
distinct destinations), summing to exactly 10,000 and applied to both assets. The burn part's Meme
is burned at collection and its Quote buys Meme back to burn. The launch stores it unchanged and the
vault copies it at migration; after that the curve-fee cap holder changes it in the vault (migrators
guide).

#### Worked example

SUI Quote (9 decimals), Meme with 9 decimals (supply `10^18` atoms), plan 8,000 curve / 2,000 pool
Meme and 10,000 pool Quote, Blast allocation 0, `V = T = 8,000 SUI`. Ignoring fees and sells:

- The curve holds 800M tokens; opening price `8,000 / 800M = 0.00001` SUI per token (10,000 SUI for
  the whole supply).
- At the target the curve holds about `800M * 8,000 / 16,000 = 400M` tokens: 400M sold for
  8,000 SUI; closing price `16,000 / 400M = 0.00004` SUI per token.
- Migration seeds the pool with 200M tokens and 8,000 SUI (also 0.00004), and disposes of 400M
  unsold tokens; a burn-only supply ends at 600M tokens.

With a 1% Quote fee and no Meme fee, a first buy of 100 SUI pays a 1 SUI fee and receives
`floor(8 * 10^17 * 99 * 10^9 / (8 * 10^12 + 99 * 10^9)) = 9,778,985,059,883,936` atoms (about 9.78M
tokens). With `Q = 7,990 SUI` and the same fee, supplying 20 SUI uses `g = 10.101010102` SUI and
refunds 9.898989898 SUI; the net 10 SUI lands `Q` exactly on 8,000.

### Time rules

All times are `Clock` milliseconds.

- `public_start_ms` is the time of `launch::share`. Sells and creator-cap claims need it set;
  buys do not (only the creator's own PTB can reach the unshared launch).
- Opening round: joins are accepted while `now < public_start_ms + opening_round_ms` (and before
  share); settlement is accepted when `now >= public_start_ms + opening_round_ms`. At exactly the
  end, a join aborts and settlement succeeds. Settlement is never possible before share. Length is
  0 or 60,000 to 300,000 ms.
- Account claims: accepted while `now <= expiry_ms`.
- Partner acceptance: `set_partner` needs `now < accepted_until_ms`; removal sets
  `accepted_until_ms = now + 7 days`, and `add_partner` restores `u64::MAX`.
- Trades, claims, deliveries, and migration have no deadline. Settings snapshot at `new` and
  `finalize`; config changes made later never reach existing launches, except
  `protocol_fee_share_bps`, `treasury`, and the claim signer, which are read live.

### Reading state

The launchpad exposes few getters; read object fields through Sui RPC (object content, dynamic
fields), or dev-inspect a call.

Getters: `launch::pool_tier` returns `(tick_spacing, fee_rate)` in the adapter's venue units;
`launch::lp_fee_split` returns the `FeeSplit`; `launch::partner_id` returns `Option<ID>`;
`launch::assert_curve_fee_cap` aborts unless a cap is the live curve-fee cap; on a `FeeSplit`,
`allocation::recipients`, `allocation::destination` (of a `Route`), and
`allocation::apportion_fee_split(total)` returning `(creator, auto_lp, rewards, burn, per-route)`;
`blast_fun::bps::value` and `blast_fun::bps::apply_up` on a `Bps`.

`Launch<Meme, Quote>` fields: `lifecycle`; `public_start_ms`; `opening_round_ms`;
`opening_round_bids` (undelivered bids' total); `opening_round_quote` (the pot, then the refund
awaiting delivery); `opening_round_meme`; `sell_burn_bps`; `virtual_quote`; `graduation_target`;
`quote_fee_bps`; `meme_fee_bps`; `migration_witness` (adapter type); `pool_tick_spacing`;
`pool_fee_rate`; `lp_fee_split`; `atomic_supply`; `meme_reserve`; `real_quote_reserve`;
`pending_burn`; `allocation_plan`; `allocated_meme`; `fee_ledger` (`protocol_meme`, `creator_meme`,
`protocol_quote`, `creator_quote`, `protocol_sui`); `creator` (`Some` until claimed or reassigned);
`curve_fee_cap_id`; `blast_metadata_cap_id`; `partner_id`. The `Meme` and `Quote` types are the
object's type arguments.

| Question | Answer |
| --- | --- |
| Price | `(virtual_quote + real_quote_reserve) / meme_reserve` Quote atoms per Meme atom; scale by `10^meme_decimals / 10^quote_decimals` for whole tokens; times one billion tokens for fully diluted value |
| Progress to graduation | `real_quote_reserve / graduation_target` |
| Quote still needed | `ceil((graduation_target - real_quote_reserve) * 10,000 / (10,000 - quote_fee_bps))` gross |
| Tradeable? | buy: `lifecycle` is `Live`; sell: also `public_start_ms` is set |
| Opening round end | `public_start_ms + opening_round_ms` |
| One bidder's pending bid | dynamic field `launch::OpeningRoundBidKey(address)` on the launch (a `u64`); absent once delivered |
| Unclaimed creator / Blast fees | `fee_ledger` balances |
| Is this cap live? | its object ID equals `curve_fee_cap_id` or `blast_metadata_cap_id` |
| Coin metadata, supply mode, total supply | the shared `Currency<Meme>` |

`LaunchConfig` fields: `meme_decimals`, `quotes` (a `Table` keyed by the Quote `TypeName` with
original IDs), `quote_fee_bps`, `meme_fee_bps`, `migration_witnesses`, `protocol_allocation`
(`meme_bps`, `quote_bps`), `creation_fee` (MIST); accepted partners are dynamic fields
`launch_config::PartnerKey(ID)` holding `accepted_until_ms`. `RuntimeConfig` fields:
`creator_claim_signer_public_key`, `protocol_fee_share_bps`, `treasury`. Preview a trade exactly by
dev-inspecting `launch::buy` or `launch::sell` against the live launch.

### Aborts

Launchpad aborts carry a numeric code from `blast_fun::errors`; the abort location is the module
that detected it.

| Flow | Code, constant (module) | Fix |
| --- | --- | --- |
| any | 13 in `blast_admin::operational_version` | call the launchpad's current package ID |
| publish | 9 `blast_fun::errors::EInvalidSellBurnBps` (`launch_ticket`); 25 `blast_fun::errors::EInvalidCreatorRecipient`, 26 `blast_fun::errors::EInvalidAccountCommitment` (`creator_authority`); `EInvalidSymbol` in `sui::coin_registry`; arithmetic overflow | sell-burn at most 5,000; a non-zero address or a 32-byte commitment; an ASCII-printable symbol; decimals at most 10 |

### Pitfalls

- Building the plan to sum to 10,000 on its own. Blast's allocation is added at finalization, so
  read `LaunchConfig.protocol_allocation` and leave exactly that room in each asset.
- Passing the pre-registration `Currency<Meme>`. Finalization needs the shared one that
  `0x2::coin_registry::finalize_registration` creates, in a separate earlier transaction.
- Trying to claim the creator caps, or to use the launch, after `launch::share` in the creation
  PTB. The launch is consumed by `share`; claim in a later transaction.
- Paying a creation fee that is close but not exact, or forgetting the coin when the fee is zero.
- Expecting to add a partner later. Only `launch::set_partner` before `finalize` names one.
- Calling `launch::claim_protocol_fees` on a launch with a partner (or the reverse); it aborts.
- Dropping returned coins. `launch::buy` and `launch::claim_creator_fees` return two coins, either
  possibly zero; transfer or destroy both.
- Setting `min_meme_out` or `min_quote_out` to 0 in production: there is no other price protection.
- Forgetting the sell burn in sell previews: only `x` of the input reaches the curve.
- Indexing opening-round bidders from events alone: `blast_fun::events::OpeningRoundJoined` has no
  bidder field; use the transaction sender, or the launch's `launch::OpeningRoundBidKey` dynamic
  fields, to know whom to deliver to.
- Reassigning only one creator cap for an unclaimed launch. Either reassignment cancels the pending
  claim for both caps, so the other cap stays unissued until it is reassigned too.
- Deleting a live cap: curve fees or metadata stay locked until a creator admin reassigns it.
- Calling an old package ID after an upgrade: every protected call aborts. Call the current package
  ID; types and events keep the original ID.
- Choosing a Cetus tick spacing that Cetus does not register, or a Bluefin tier outside its bounds:
  the start aborts, and the tier can never change after creation.
- Filtering events by emitting module instead of by the full `blast_fun::blast_events::Event` type.

### Q&A

**How do I show a launch's current price and market cap?** Read `virtual_quote`,
`real_quote_reserve`, and `meme_reserve` from the launch (or the reserves from the latest
`blast_fun::events::Bought` or `blast_fun::events::Sold`). Price is
`(virtual_quote + real_quote_reserve) / meme_reserve` Quote atoms per Meme atom; adjust for both
decimals and multiply by one billion tokens for fully diluted value.

**How do I quote a buy or sell exactly?** Apply the formulas under Curve math with the launch's
snapshotted fee rates and sell-burn rate, or dev-inspect `launch::buy` / `launch::sell` with real
coins. Both round against the trader.

**What happens when a buy overshoots the graduation target?** The launch uses only the gross Quote
needed to bring the real reserve to the target and returns the rest as the second coin of
`launch::buy`. The launch becomes `MigrationReady` and all buys and sells stop.

**Who migrates the launch, and when?** Anyone, as soon as it is `MigrationReady`, through the
adapter it started with (`blast_fun_migrators::cetus::migrate` or
`blast_fun_migrators::bluefin::migrate`). Only that adapter's witness passes `launch::migrate`.

**What happens to unsold tokens and the sell burn?** Both are disposed of at migration: burned when
the supply is burn-only, or sent to `@0x0` when it is fixed. `blast_fun::events::Migrated` reports
`disposed_meme` and `total_supply_after`.

**Can the creator change the target, plan, fees, tier, or LP-fee split after launch?** No. They are
fixed at creation. Only the metadata (name, description, icon) changes, with the metadata cap;
after migration the curve-fee cap holder can change the LP-fee split in the migrators' vault.

**How does the creator get paid?** The creator recipient claims a `CurveFeeCap<Meme>` once with
`launch::claim_creator_caps`, then calls `launch::claim_creator_fees` at any time for its share of
every trade fee. After migration the same cap claims the creator's LP-fee share from the vault.

**How does the opening round treat early buyers?** Every bid, including the creator's before share,
joins one pot that buys once at settlement, so all bidders pay the same average price. Each bidder
receives Meme and refunded Quote in proportion to its bid, rounded down, with the last delivery
taking the remainder.

**Does a partner earn on a launch?** Only if named at creation with `launch::set_partner`. When
anyone claims Blast's fees with `launch::claim_protocol_fees_with_partner`, the partner receives its
share of Blast's trade fees, the creation fee, and the one-time migration allocation; the vault
inherits the partner for LP fees.

**Can a launch fail or be refunded?** No. There is no cancellation, expiry, or refund: a launch that
never reaches its target stays `Live`, and holders exit by selling to the curve.

## Migration and LP vaults

> **Deployment status:** `blast_fun_migrators` is not yet published on mainnet; its interface may change before publication.

### What it is

A Blast launch trades on a bonding curve until the curve fills and the launch becomes
`MigrationReady`. The `blast_fun_migrators` package then moves the launch's pool allocation into a
new full-range position on a DEX: Cetus or Bluefin, whichever the creator picked when the launch
started. The position goes into a per-launch shared vault, `blast_fun_migrators::vault::LpVault`,
and no function can take it out again. From then on anyone can collect the position's trading fees.
Each collection pays Blast its LP-fee share, then splits the rest by the vault's `FeeSplit` (the
launch's until the creator changes it) into five parts: creator, auto-LP (added back to the pool),
holder rewards, burn, and fixed recipients. This guide covers how a launch starts on a venue, the
migration itself, and everything the vault does afterwards.

| `lp_fee_policy::LpFeePolicy` | singleton | Blast's LP-fee share (a default pair and optional per-coin pairs) and the address Blast's share is paid to. |

#### Capabilities and roles

- `creator_authority::CurveFeeCap` (`CurveFeeCap<Meme>`, owned, transferable). The launch records
  the ID of the one live cap. Its holder claims the creator's LP fees and changes the fee split. The
  creator gets it from `launch::claim_creator_caps`. A Blast admin with
  `blast_fun_domain::CreatorAdmin` can retire it and issue a new one with
  `launch::reassign_curve_fee_cap`; the new cap then controls the vault too.
- Blast admin roles. An admin calls `blast_acl::sign_in` (type argument `Role`) with the shared
  `blast_acl::ACL` and its own `blast_acl::AdminCap`, which yields a droppable
  `blast_acl::AdminWitness` (`AdminWitness<Role>`). Each admin call takes the witness for exactly
  one role:
  - `blast_fun_domain::BuybackAdmin`: buyback and burn.
  - `blast_fun_domain::RewardsAdmin`: publish holder-reward rounds.
  - `blast_fun_domain::TreasuryAdmin`: claim migration residuals; set the LP-fee destination.
  - `blast_fun_domain::FeeAdmin`: set Blast's default and per-coin LP-fee shares.
  - `blast_fun_domain::UpgradeAdmin`: authorize and commit package upgrades.

  These role types belong to the launchpad; this package declares no roles of its own. Integrators
  cannot call admin functions.

#### What an `LpVault` holds

- The venue position, as a dynamic object field under `blast_fun_migrators::vault::PositionKey`
  (`PositionKey<Venue>`), where `Venue` is `blast_fun_migrators::cetus::Venue` or
  `blast_fun_migrators::bluefin::Venue`. On Cetus this is the `CetusLPBurnProof` of the burned
  migration position; on Bluefin it is the Bluefin `Position`.
- On Cetus only, from the first collection that finds both auto-LP balances nonzero: a second
  full-range Cetus `Position` under `blast_fun_migrators::vault::AutoLpPositionKey`
  (`AutoLpPositionKey<Venue>`).
- `protocol_meme_residual`, `protocol_quote_residual`: what the venue did not take when seeding the
  position at migration. Blast's; only `TreasuryAdmin` claims them.
- `unpaid_protocol_meme`, `unpaid_protocol_quote`: Blast's LP-fee share held for the partner payout
  (partnered vaults only).
- `creator_meme`, `creator_quote`: creator LP fees not yet claimed.
- `auto_lp_meme`, `auto_lp_quote`: auto-LP amounts the pool has not taken yet.
- `rewards_meme`, `rewards_quote`: holder-reward funds not yet reserved by a round.
- `burn_quote`: Quote waiting for a buyback.
- `fee_split` and `generation`: the current split and its generation (0 at migration).
- `pool_id`, `partner_id` (copied from the launch, never changes), `next_round`, `last_checkpoint`.

No function removes or transfers a position. No function withdraws the auto-LP, rewards, or burn
balances except the flows below.

#### Trust assumptions

- **Upgradeable package.** `UpgradeAdmin` can authorize compatible upgrades of this package through
  `PackageAdmin`. An upgrade can add functions to these modules, so the vault's custody and routing
  rules hold only as long as Blast's upgrade governance keeps them. The Cetus migration liquidity is
  different: Cetus LP Burn has burned it, and its `CetusLPBurnProof` can only collect fees. The
  Bluefin position, the Cetus auto-LP position, and every vault balance depend on this package's
  code.
- **Blast sets its own share at any time.** `FeeAdmin` can set Blast's LP-fee share anywhere from 0
  to 10,000 BPS per asset, by default or per coin, with no delay. It applies from the next
  collection. `TreasuryAdmin` can redirect Blast's share at any time.
- **The admin can publish any round.** Merkle proofs enforce the published allocation, not the truth
  of Blast's off-chain holder accounting. `RewardsAdmin` can assign unreserved rewards to any
  recipient in a new round. Rounds never expire, and nothing cancels a round or sweeps its funds, so
  a wrong root or an over-sized budget cannot be recovered through the current functions.
- **Auto-LP price-move skim.** Auto-LP adds at the pool's current price. A caller can move the price
  in the same transaction, collect, and move it back, skimming part of that call's auto-LP amount.
  Frequent collection keeps each exposed slice small. Buybacks are admin-only with a minimum out for
  the same reason.
- **Venue operators.** Cetus's pool-manager role can create a reserved pair's pool without the
  `PoolCreationCap`. If it does so first, Cetus migration aborts, and only a package upgrade could
  recover the launch. If Cetus stops registering the launch's tick spacing, migration aborts and the
  launch stays `MigrationReady`.
- **Buyback timing.** Burn Quote waits until a `BuybackAdmin` acts; nothing forces a buyback.

### Lifecycle

- **Launch.** `MigrationReady` → `migrate` → `Migrated`. Only the adapter whose `Witness` the launch
  recorded at start can migrate it. A failed migration aborts the whole transaction and leaves the
  launch `MigrationReady`.
- **Vault.** Created and shared inside `migrate`, at generation 0 with the launch's `FeeSplit`. Each
  `settle_and_update_fee_split` adds 1 to `generation`. On Cetus, the auto-LP position appears the
  first time a collection finds both auto-LP balances nonzero, even if nothing is then added. The
  vault never closes.
- **Rounds.** `next_round` starts at 0 and rises by 1 per published round. Each round's checkpoint
  interval must start where the previous one ended. A round stays claimable forever.

### Flows

Every public call in this package except the one-time `wrap` takes
`blast_fun_migrators::blast_fun_migrators::PackageVersion` (shared) and checks it before anything
else. Calls whose launchpad step checks the launchpad generation (`new`, `migrate`) take the
launchpad's `blast_fun::blast_fun::PackageVersion` as well, because each package checks only its own
generation.

#### Starting a launch on a venue

The launchpad guide covers building a launch. The adapter call is its first step: it starts the
`launch::LaunchInitializer` hot potato (`LaunchInitializer<Meme, Quote>`), which the same PTB must
complete with `launch::finalize` and then `launch::share`. The adapter records its `Witness` type in
the launch, so only that venue can migrate it later.

`blast_fun_migrators::cetus::new` (type arguments `<Meme, Quote>`; anyone holding the ticket) takes,
in order: the `LaunchTicket<Meme>` by value, the migrators `PackageVersion`, the launchpad
`PackageVersion`, `LaunchConfig`, `VenueConfig` (mutable), Cetus `GlobalConfig`, Cetus `Pools`
(mutable), and `tick_spacing: u32`. It:

1. Reads the fee rate Cetus registers for `tick_spacing`. Cetus aborts if it registers none.
2. Calls `launch::new` with `blast_fun_migrators::cetus::Witness`, which checks the launchpad
   generation and that `LaunchConfig` admits the adapter, the Quote, and the Meme's decimals, and
   records the tier `(tick_spacing, fee_rate)`.
3. Mints the Meme type's single Cetus `PoolCreationCap` from the ticket's treasury capability,
   before any Meme can leave the ticket, and registers the pair at `tick_spacing`. Cetus aborts if
   it refuses the pair there.
4. Stores the cap in `VenueConfig` under `CreationCapKey<Meme>`, with no path to remove it, and
   emits `blast_fun_migrators::blast_events::CetusPoolReserved`.

After this, only that cap (or Cetus's pool-manager role) can create the pair's Cetus pool at that
tick spacing, so no buyer can pre-create the migration pool at a price of their choosing.

`blast_fun_migrators::bluefin::new` (type arguments `<Meme, Quote>`; anyone holding the ticket)
takes, in order: the ticket, the migrators `PackageVersion`, the launchpad `PackageVersion`,
`LaunchConfig`, `tick_spacing: u32`, and `fee_rate: u64`. It aborts with `EInvalidTier` unless
`tick_spacing` is in 1..=400 and `fee_rate` is in 1..=20,000 (Bluefin's own pool-creation bounds),
then calls `launch::new` with `blast_fun_migrators::bluefin::Witness`. It needs no Bluefin objects.
Tiers are in each venue's own units.

#### Migrating to Cetus

Anyone may migrate once the launch is `MigrationReady`. Nothing requires a separate transaction, so
the PTB that graduates the curve can migrate too.

1. Work out Cetus's coin order. Cetus orders a pool's coins `CoinA` and `CoinB` by type name, and
   Blast checks the order with Cetus's own `is_right_order<CoinA, CoinB>` (in Cetus's `factory`
   module), which returns `true` for the accepted order. Dev-inspect it, or dry-run `migrate` with
   either order: the wrong one aborts with `EInvalidCoinOrder`.
2. Call `blast_fun_migrators::cetus::migrate` with type arguments `<Meme, Quote, CoinA, CoinB>` and,
   in order: the `Launch<Meme, Quote>` (mutable), the migrators `PackageVersion`, the launchpad
   `PackageVersion`, the Meme's `Currency<Meme>` (mutable), `VenueConfig`, Cetus `GlobalConfig`,
   Cetus `Pools` (mutable), LP Burn `BurnManager` (mutable), and `Clock`. It returns nothing; the
   caller receives no object.

Inside the call, in order:

1. Checks the migrators generation, then `CoinA`/`CoinB` order (`EInvalidCoinOrder`), then that
   `{CoinA, CoinB}` is exactly `{Meme, Quote}` (`EWrongCoinPair`).
2. Reads the launch's tier and Cetus's full-range ticks for its tick spacing.
3. Calls `launch::migrate`, which checks the launchpad generation, `MigrationReady`, and the adapter
   witness; pays the allocation plan's recipients; accrues Blast's one-time migration fee in the
   launch; burns the unsold curve Meme and pending sell-burn (or sends them to `@0x0` under a fixed
   supply); marks the launch `Migrated`; and hands the pool's Meme and Quote to the adapter.
4. Computes the opening price from those atomic amounts (see Economics), creates the pool with the
   reserved `PoolCreationCap` at the launch's tick spacing, and seeds full-range liquidity with
   exactly the handed-off balances. It never adopts an existing pool.
5. Burns the position through Cetus LP Burn. Cetus records the liquidity as permanently locked.
6. Creates and shares the `LpVault` holding the `CetusLPBurnProof` and Cetus's leftover coins as
   protocol residuals, and emits `VaultCreated`. It aborts with `EZeroLiquidity` if the position
   holds no liquidity.

#### Migrating to Bluefin

Anyone may call `blast_fun_migrators::bluefin::migrate` once the launch is `MigrationReady`. Bluefin
pools always have Meme as coin A: `Pool<Meme, Quote>`.

1. Split a `Coin<SUI>` worth exactly the SUI pool-creation fee Bluefin currently configures. Bluefin
   aborts on any other amount, and the whole coin is paid.
2. Call `blast_fun_migrators::bluefin::migrate` with type arguments `<Meme, Quote>` and, in order:
   the `Launch` (mutable), the migrators `PackageVersion`, the launchpad `PackageVersion`,
   `Currency<Meme>` (mutable), `Currency<Quote>`, Bluefin `GlobalConfig` (mutable), the `Coin<SUI>`
   fee (by value), and `Clock`.

Inside the call: it runs `launch::migrate` as above; creates `Pool<Meme, Quote>` at the launch's
tier, named `MEME-QUOTE` from the two Coin Registry symbols, with no Meme icon and the Quote's icon;
opens a position across the widest tick range Bluefin's configured bounds allow at that spacing;
seeds it with the handed-off balances; creates and shares the `LpVault` with the position and
Bluefin's leftovers as protocol residuals (`VaultCreated`); and shares the pool. The caller receives
no object, but Bluefin records the caller as the new pool's manager, a Bluefin role limited to the
pool's reward emissions and to handing the role on.

#### Collecting LP fees

Anyone may collect, as often as they like. A collection that finds no fees is valid.

- Cetus: `blast_fun_migrators::cetus::collect_fees`, type arguments `<Meme, Quote, CoinA, CoinB>`,
  with the `LpVault` (mutable), migrators `PackageVersion`, `LpFeePolicy`, `Currency<Meme>`
  (mutable), Cetus `GlobalConfig`, LP Burn `BurnManager`, the vault's Cetus `Pool<CoinA, CoinB>`
  (mutable), and `Clock`.
- Bluefin: `blast_fun_migrators::bluefin::collect_fees`, type arguments `<Meme, Quote>`, with the
  `LpVault` (mutable), migrators `PackageVersion`, `LpFeePolicy`, `Currency<Meme>` (mutable),
  Bluefin `GlobalConfig`, the vault's `Pool<Meme, Quote>` (mutable), and `Clock`.

Exact order of operations:

1. Check the migrators generation. On Cetus, prove the coin pair (`EWrongCoinPair`).
2. Check the pool is the vault's own (`EPositionPoolMismatch`).
3. Collect fees. Cetus: from the burned position through LP Burn, plus the auto-LP position's fees
   once it exists. Bluefin: from the migration position.
4. Split (if either amount is nonzero; otherwise skip to step 5 with no event):
   1. Read Blast's live share for this Meme from `LpFeePolicy` and take `ceil(gross × bps / 10,000)`
      of each asset.
   2. Apportion the rest of each asset by the vault's `FeeSplit` (see Economics).
   3. Pay Blast's share to the policy's current destination, or, on a partnered vault, add it to
      `unpaid_protocol_meme`/`unpaid_protocol_quote`.
   4. Add the creator, auto-LP, and rewards parts to their vault balances.
   5. Burn the burn part's Meme; add the burn part's Quote to `burn_quote`.
   6. Transfer each recipient its Meme and Quote as coins, in the split's order. Zero amounts send
      nothing.
   7. Emit `FeesCollected`.
5. Auto-LP: take all of `auto_lp_meme` and `auto_lp_quote` (this call's part plus anything left from
   earlier calls) and add what the pool takes at its current price. Keep the rest in the vault. Emit
   `AutoLiquidityAdded` only if something was added.

Auto-LP per venue:

- Cetus burned the migration position, so it cannot take liquidity. The first time both auto-LP
  balances are nonzero, the vault opens a second full-range position in the same pool (emitting
  `AutoLpPositionOpened`) before deciding the add, and keeps it with no removal path. Each add
  fixes all of coin A if Cetus's liquidity math says the coin B balance covers it, else all of coin
  B if the coin A balance covers that, else adds nothing.
- Bluefin adds to the migration position. Blast's own math picks the fixed side from the pool price
  and the position's bound prices, keeping a 2-atom margin on the other side.
- Both add nothing while either side is empty, so a one-sided auto-LP balance waits until the other
  asset arrives. The unfixed side's excess always waits for a later call.

#### Paying a partnered vault's Blast LP fees

When the launch named a partner, collections hold Blast's share in the vault instead of paying it.
Anyone may pay it out with `blast_fun_migrators::vault::claim_protocol_lp_fees_with_partner`
(`<Meme, Quote>`), passing the `LpVault` (mutable), migrators `PackageVersion`, `LpFeePolicy`, the
vault's `blast_partners::blast_partners::Partner`, and `Clock`. It aborts with `EPartnerMismatch`
unless the partner is the one the vault inherited (so it also aborts on a vault without a partner).
If nothing is held it returns without moving anything or emitting an event. Otherwise it takes
everything held, pays the partner its cut of each asset through
`blast_partners::blast_partners::pay` (which emits `blast_partners::blast_partners::PartnerPaid` for
each nonzero amount and sends the funds to the partner's recipient), pays the rest to the policy's
current destination, and emits `ProtocolLpFeesClaimed`. Compose it after `collect_fees` in one PTB
to settle both at once.

#### Claiming creator LP fees

1. Optionally call `collect_fees` first in the same PTB, so the latest fees are included.
2. Call `blast_fun_migrators::vault::claim_creator_fees` (type arguments `<Meme, Quote>`) with the
   `LpVault` (mutable), migrators `PackageVersion`, the `Launch<Meme, Quote>` (read-only), and the
   live `CurveFeeCap<Meme>` (owned, by reference). It returns `(Coin<Meme>, Coin<Quote>)` holding
   all of `creator_meme` and `creator_quote`, and emits
   `blast_fun_migrators::blast_events::CreatorFeesClaimed`.
3. Transfer or use both coins; coins cannot be dropped, so the PTB must consume them, even a
   zero-value one.

It aborts in the launchpad with code 22 if the cap is not the launch's live cap, and with
`ENoCreatorFees` if both balances are zero. This is separate from `launch::claim_creator_fees`,
which pays the creator's bonding-curve trade fees.

#### Changing the fee split

The live `CurveFeeCap` holder replaces the split. Fees already in the pool settle under the old
split first, so every fee follows the split it accrued under.

1. Build the new split in the PTB: one `allocation::route` (destination, BPS) per recipient, a
   `MakeMoveVec` of those routes, then `allocation::fee_split` (creator, auto-LP, rewards, and burn
   BPS, then the routes), with each `Bps` from `blast_fun::bps::new`. The parts must sum to exactly
   10,000; at most 16 recipients; destinations nonzero and distinct.
2. Call `blast_fun_migrators::cetus::settle_and_update_fee_split` with `<Meme, Quote, CoinA, CoinB>`
   or `blast_fun_migrators::bluefin::settle_and_update_fee_split` with `<Meme, Quote>`. Arguments,
   in order: the `LpVault` (mutable), migrators `PackageVersion`, `LpFeePolicy`, the `Launch`
   (read-only), the live `CurveFeeCap<Meme>`, `Currency<Meme>` (mutable), the venue objects exactly
   as in that venue's `collect_fees` (Cetus `GlobalConfig`, `BurnManager`, pool; or Bluefin
   `GlobalConfig`, pool), the new `FeeSplit` from step 1, and `Clock`.

Order: generation check; (Cetus) pair proof; live-cap check (launchpad code 22); proposal differs
from the current split (`EFeeSplitUnchanged`); a full collection exactly as above under the old
split; then the new split commits with `generation + 1` and emits `FeeSplitChanged`. A settlement
that finds no fees still commits. Balances already in the vault (creator, auto-LP leftovers,
rewards, burn Quote) stay where they are; auto-LP leftovers keep being added on later collections
even if the new split has no auto-LP part.

#### Buyback and burn (Blast admin)

A `BuybackAdmin` calls `blast_fun_migrators::cetus::buyback_and_burn` (`<Meme, Quote, CoinA,
CoinB>`) or `blast_fun_migrators::bluefin::buyback_and_burn` (`<Meme, Quote>`) with the vault, the
migrators `PackageVersion`, `&AdminWitness<BuybackAdmin>`, `Currency<Meme>`, the venue
`GlobalConfig`, the vault's pool, `min_meme_out` (atomic Meme units), and `Clock`. It checks the
pool is the vault's (`EPositionPoolMismatch`), takes all of `burn_quote` (`ENoBuybackQuote` if
zero), swaps it for Meme in the vault's pool up to the widest price limit, aborts with
`EBuybackBelowMinimum` if the Meme bought is below `min_meme_out`, burns that Meme (or sends it to
`@0x0` when the supply is not burn-only, as collections do), returns any Quote the pool did not
take to `burn_quote`, and emits `BuybackBurned`. The admin sets `min_meme_out` from an off-chain
price, because anyone can move the pool price inside a transaction.

#### Holder-reward rounds

Blast's off-chain system turns holder balances between checkpoints into a Merkle allocation. The
contract enforces only the published allocation, not how it was computed.

Publishing (Blast admin, `RewardsAdmin`): `blast_holder_rewards::publish_round` (`<Meme, Quote>`)
with the vault (mutable), migrators `PackageVersion`, `&AdminWitness<RewardsAdmin>`, `number`,
`start_checkpoint`, `end_checkpoint`, `root`, `manifest_digest`, `leaf_count`, `meme_amount`,
`quote_amount`. Checks, in order: `number` equals the vault's `next_round` (`EWrongRound`);
`start_checkpoint < end_checkpoint` and, after the first round, `start_checkpoint` equals the
previous `end_checkpoint` (`EInvalidInterval`); `root` and `manifest_digest` are 32 bytes each
(`EInvalidCommitment`); `leaf_count` is 1..=65,536 (`EInvalidLeafCount`); at least one amount is
nonzero (`EEmptyBudget`). It moves the budget out of `rewards_meme`/`rewards_quote` (a Sui balance
abort if the vault holds less), shares a new `Round`, and emits `RoundPublished`. The contract never
checks that the leaves sum to the budget. Checkpoints are opaque u64 values to the contract.

Claiming (anyone): `blast_holder_rewards::claim` (`<Meme, Quote>`) with the `Round` (mutable),
migrators `PackageVersion`, `index`, `beneficiary`, `meme_amount`, `quote_amount`, and `proof`
(`vector<vector<u8>>`, leaf to root). Checks, in order: `index < leaf_count` (`EInvalidIndex`); the
leaf is unpaid (`EAlreadyClaimed`); `beneficiary` is not `@0x0` (`EInvalidBeneficiary`); an amount
is nonzero (`EEmptyBudget`); the proof verifies (`EInvalidProof`). It marks the leaf paid, transfers
the nonzero amounts as coins to `beneficiary` (never to the sender; a Sui balance abort if the round
holds less), and emits `RewardPaid`. Anyone can relay a claim; the beneficiary receives the same
coins either way. There is no deadline.

Leaf and proof format (Blake2b-256 throughout, BCS encoding):

- Leaf: `blake2b256(0x00 || "blast-holder-rewards-v1" || vault_id || round || index || beneficiary
  || meme_amount || quote_amount)`. `vault_id` is the `LpVault` ID (32 bytes), not the `Round` ID.
  `round`, `index`, and the amounts are u64 little-endian (8 bytes each). `beneficiary` is 32
  bytes. The tag is the ASCII string after one zero byte.
- Internal node: `blake2b256(0x01 || left || right)`.
- Tree: leaves in index order. At any level with an odd count, the last node pairs with itself.
- Proof: exactly as many 32-byte siblings as the tree has levels (`leaf_count` 1 needs none, 2 needs
  one, 3 or 4 need two, and so on). At each level, if the current index is even the node is
  `node(current, sibling)`, otherwise `node(sibling, current)`; then the index halves.
- Test vector: with the vault ID and beneficiaries written as small numbers left-padded to 32
  bytes, vault `0xd`, round 0, and leaves (index, beneficiary, Meme, Quote) `(0, 0xa, 10, 20)`,
  `(1, 0xb, 30, 40)`, `(2, 0xc, 50, 60)` give leaf 0
  `18ba1db53bc0da39eb6f1f00df49fa5be0932e85ca8f8257f4d278edea7f1aa8` and root
  `93f46ab27a1d3a5def3379afd0a3b02cc149d6fa03b7105b2697deba8c12cb2d`. Leaf 2's proof is
  `[leaf 2 itself, node(leaf 0, leaf 1)]`.

#### Claiming migration residuals (Blast admin)

A `TreasuryAdmin` calls `blast_fun_migrators::vault::claim_protocol_fees` (`<Meme, Quote>`) with the
vault, migrators `PackageVersion`, and `&AdminWitness<TreasuryAdmin>`. It returns `(Coin<Meme>,
Coin<Quote>)` holding both residuals, emits `ProtocolFeesClaimed` with the sender as `claimant`, and
aborts with `ENothingClaimable` when both are zero. Blast's one-time migration fee is not here; it
sits in the launch and is claimed through the launchpad.

#### LP-fee policy (Blast admin)

- `lp_fee_policy::set_default_shares` (`FeeAdmin`): sets the default Meme and Quote BPS for every
  coin without its own pair. Aborts with `EProtocolFeeSharesUnchanged` if unchanged.
- `lp_fee_policy::set_coin_shares` (type argument `Meme`; `FeeAdmin`): sets this Meme's own pair,
  keyed by its original type name. A pair equal to the defaults is still a real entry: later default
  changes skip that coin. Aborts if it equals the coin's current pair.
- `lp_fee_policy::clear_coin_shares` (type argument `Meme`; `FeeAdmin`): removes the coin's pair so
  the defaults apply again. Aborts in Sui's table code if the coin has no pair.
- `lp_fee_policy::set_protocol_destination` (`TreasuryAdmin`): redirects every later Blast payout.
  Aborts with `EProtocolDestinationUnchanged` for `@0x0` or the current address.

Each takes effect from the next collection or partner payout. At publication the defaults are 0 BPS
for both assets and the destination is the publishing address; read the live object for current
values.

#### Package upgrades (Blast admin)

`blast_fun_migrators::package_admin::authorize_upgrade` returns an upgrade ticket for an exact
digest; `blast_fun_migrators::package_admin::commit_upgrade_and_advance` commits the receipt and
moves `PackageVersion` to the next generation in the same call. From then on, every call to the old
package's code aborts the generation check, so integrators must call the current package address.
Type names keep the original package address. Upgrading this package leaves the launchpad on its own
generation.

### Economics

All amounts are atomic units. BPS are out of 10,000.

#### Blast's LP-fee share

For each collection, with the Meme's own pair if `FeeAdmin` set one, otherwise the defaults:

- `protocol_meme = ceil(gross_meme × meme_bps / 10,000)`
- `protocol_quote = ceil(gross_quote × quote_bps / 10,000)`

Blast's share rounds up, so it takes the rounding dust of its own part. The pair and the destination
are read live at each collection. This share is separate from Blast's one-time migration allocation,
which the launchpad takes from the supply and the final reserve at migration.

#### Partner cut

On a partnered vault, Blast's share waits in `unpaid_protocol_*`. At payout the partner receives
`floor(held × share_bps / 10,000)` of each asset, using the partner's share in force at payout time
(the partners package caps it at 8,000 BPS and delays Blast's changes to it by seven days). Blast's
destination receives the rest. The creator, recipients, auto-LP, rewards, and burn receive exactly
what they would without a partner.

#### The fee split

`net = gross − protocol`, per asset. The vault's `FeeSplit` divides each asset's `net` independently
into parts in this fixed order: creator, auto-LP, rewards, burn, then each recipient in the split's
order. Apportionment is largest-remainder and exact:

1. Each part gets `floor(net × part_bps / 10,000)`.
2. The units left over go one each to the parts with the largest remainders (`net × part_bps mod
   10,000`), ties going to the earlier part.

The parts always sum to `net`. Anyone can preview a split with the public, pure
`allocation::apportion_fee_split` in a dev-inspect.

Worked example (Blast at 1,000 BPS Meme and 2,500 BPS Quote; split creator 2,000, auto-LP 2,000,
rewards 1,000, burn 1,000, recipient B 2,500, recipient A 1,500; gross 11 Meme and 7 Quote):

| | Blast | Creator | Auto-LP | Rewards | Burn | B | A |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Meme (net 9) | 2 | 2 | 2 | 1 | 1 | 2 | 1 |
| Quote (net 5) | 2 | 1 | 1 | 1 | 0 | 1 | 1 |

#### Where each part goes

| Part | Destination |
| --- | --- |
| Blast | Policy destination at once, or held for the partner payout. |
| Creator | `creator_meme`/`creator_quote`, until the live `CurveFeeCap` claims it. |
| Auto-LP | Added back to liquidity in the same call; what the pool does not take waits in `auto_lp_*`. |
| Rewards | `rewards_meme`/`rewards_quote`, until a round reserves it. |
| Burn, Meme | Burned at once if the Meme's Coin Registry supply is burn-only; otherwise sent to `@0x0`. |
| Burn, Quote | `burn_quote`, until a buyback swaps it for Meme and disposes of that Meme as above. |
| Recipients | Coins transferred to each destination in the same call. |

#### Auto-LP math

Auto-LP never swaps. It fixes all of one side and pays what the venue asks of the other at the
current price; the rest of the other side waits. Bluefin's side choice, with `P`, `L`, `U` the
current, lower, and upper sqrt prices (Q64.64) and a 2-atom margin: fix Meme when `liquidity = a ×
(P × U / 2^64) / (U − P)` is positive and below 2^128 and `ceil(liquidity × (P − L) / 2^64) + 2 ≤
quote balance`; otherwise fix Quote when `liquidity = b × 2^64 / (P − L)` is positive and
`ceil(liquidity × 2^64 / P) − floor(liquidity × 2^64 / U) + 2 ≤ meme balance`; otherwise wait. A
price at or outside the range adds nothing. Cetus uses Cetus's own liquidity math with no margin.

#### Migration seed and residuals

The opening sqrt price is `floor(sqrt(coin_b / coin_a) × 2^64)` from the handed-off atomic amounts:
Quote/Meme when Meme is coin A, Meme/Quote otherwise. Display decimals never enter it. The seed
fixes the side with more atoms (Meme on a tie), unless the venue's math says that would overdraw the
other side by rounding, in which case it fixes the other side. Whatever the venue does not take
becomes the vault's protocol residuals. Position principal plus residuals equals the hand-off.

### Time rules

- No deadlines exist in this package. Collections, payouts, claims, and buybacks work at any time.
- Policy changes apply from the next collection; there is no delay.
- A partner payout uses the partner's share in force at payout, not at collection.
- Holder-reward rounds never expire. Their checkpoint intervals must be contiguous and nonempty.
- `migrate`, `collect_fees`, `settle_and_update_fee_split`, and `buyback_and_burn` take `Clock`
  (`0x6`) for the venue's own use (`new` takes none); the partner payout takes it for the partner's
  timelocked share.

### Reading state

This package has no public getters for its objects. Read object fields over RPC or GraphQL.

- **Vault** (`LpVault<Meme, Quote>`): the fields listed under "What an `LpVault` holds". Each
  `Balance` shows its value. `fee_split` holds `creator_bps`, `auto_lp_bps`, `rewards_bps`,
  `burn_bps` (each a `Bps` wrapping one u64) and `recipients` (each with `destination` and `bps`).
  The position is a dynamic object field of the vault: list its dynamic fields, or read the child
  object by the ID in `VaultCreated.position_id`.
- **Find a launch's vault:** scan `VaultCreated` events for its `meme` type name, or read the
  objects the migrate transaction created. Each Meme type has exactly one launch, so `LpVault<Meme,
  Quote>` is unique per Meme.
- **Blast's live share for a coin:** `LpFeePolicy.coins` is a table keyed by the standard library's
  `TypeName` holding the Meme's original type name (64 hex digits without `0x`, then the module and
  type names, each after two colons). If the coin has an entry, use its `meme_bps`/`quote_bps`;
  otherwise use `defaults`. `destination` is the current payee.
- **Round** (`Round<Meme, Quote>`): `vault`, `number`, `root`, `leaf_count`, `meme` and `quote`
  (funds left), and `claimed`, a bitmap of u256 words: leaf `i` is paid when bit `i mod 256` of word
  `i / 256` is set.
- **Cetus reservation:** `VenueConfig` has a dynamic object field `CreationCapKey<Meme>` holding the
  pair's `PoolCreationCap`.
- **Launch facts** (public launchpad getters): `launch::pool_tier` (tick spacing and fee rate),
  `launch::lp_fee_split` (the split at migration), `launch::partner_id`.
- **Generation:** `PackageVersion.generation`, an `OperationalVersion` whose own `generation` field
  holds the number.
- **Pending fees and the next split:** dry-run `collect_fees`; the emitted `FeesCollected` and
  `AutoLiquidityAdded` show exactly what a collection would do now.

### Events

This package emits its events directly, with no envelope. The launchpad wraps its own events in
`blast_fun::blast_events::Event`. All events below are in this package's `blast_events` module.

| Event | Emitted by | Fields |
| --- | --- | --- |
| `CetusPoolReserved` | Cetus `new` | `meme`, `quote` (type names), `pool_creation_cap_id`, `tick_spacing` |
| `VaultCreated` | `migrate` | `vault_id`, `pool_id`, `position_id`, `venue`, `meme`, `quote` (type names), `residual_meme`, `residual_quote`, `liquidity`, `fee_split` |
| `FeesCollected` | nonzero collection | `vault_id`, `generation`, `gross_meme`, `gross_quote`, `protocol_destination` (none when held for a partner), `protocol_meme`, `protocol_quote`, `creator_*`, `auto_lp_*`, `rewards_*`, `burn_meme` (burned), `burn_quote` (waits), `recipient_meme`, `recipient_quote` (split order) |
| `AutoLpPositionOpened` | first Cetus collection with both auto-LP balances nonzero | `vault_id`, `position_id` |
| `AutoLiquidityAdded` | auto-LP added something | `vault_id`, `meme_amount`, `quote_amount`, `meme_pending`, `quote_pending` |
| `FeeSplitChanged` | split update | `vault_id`, `old_generation`, `new_generation`, `old_fee_split`, `new_fee_split` |
| `CreatorFeesClaimed` | creator LP-fee claim | `vault_id`, `meme_amount`, `quote_amount` |
| `BuybackBurned` | buyback | `vault_id`, `quote_spent`, `meme_burned`, `quote_pending` |
| `RoundPublished` | round publish | `vault_id`, `round_id`, `number`, `start_checkpoint`, `end_checkpoint`, `root`, `manifest_digest`, `leaf_count`, `meme_amount`, `quote_amount`, `meme_unallocated`, `quote_unallocated` |
| `RewardPaid` | reward claim | `round_id`, `index`, `beneficiary`, `meme_amount`, `quote_amount`, `meme_remaining`, `quote_remaining` |
| `ProtocolFeesClaimed` | residual claim | `vault_id`, `meme`, `quote` (type names), `claimant`, `meme_amount`, `quote_amount` |
| `ProtocolLpFeesClaimed` | partner payout | `vault_id`, `protocol_destination`, `protocol_meme`, `protocol_quote`, `partner_meme`, `partner_quote` |
| `LpFeePolicyChanged` | policy share change | `meme` (none for defaults), `old_meme_bps`, `old_quote_bps`, `new_meme_bps`, `new_quote_bps` (the old pair is none when a coin pair is created, the new pair none when it is removed) |
| `LpFeeDestinationChanged` | destination change | `old_destination`, `new_destination` |

Event order inside one call: a collection emits `FeesCollected`, then possibly
`AutoLpPositionOpened`, then possibly `AutoLiquidityAdded`; a split update adds `FeeSplitChanged`
last. Venue events from Cetus or Bluefin appear alongside. A partner payout emits
`blast_partners::blast_partners::PartnerPaid` (per nonzero asset) before `ProtocolLpFeesClaimed`. A
migrate transaction carries the launchpad's wrapped `blast_fun::events::MigrationAllocationPaid` (one
per allocation recipient), `blast_fun::events::ProtocolFeesAccrued` (only when Blast's migration fee
is nonzero), and `blast_fun::events::Migrated` before `VaultCreated`.

#### Replaying a vault from events

Start a vault at `VaultCreated`: generation 0, its `fee_split`, residuals, `pool_id`, `position_id`.
`VaultCreated` has no launch ID; link it through `Migrated.launch_id` in the same transaction, or
through the `meme` type. On Cetus, `position_id` is the `CetusLPBurnProof`, not the burned Cetus
position. Position principal is `Migrated.meme − residual_meme` and `Migrated.quote −
residual_quote`. Then reduce:

- `FeesCollected`: add `creator_*`, `auto_lp_*`, `rewards_*`, and `burn_quote` to their balances;
  `burn_meme` left the supply (or went to `@0x0`); if `protocol_destination` is none, add
  `protocol_*` to the held partner balance; recipient `i` of the split at `generation` received
  `recipient_meme[i]` and `recipient_quote[i]`.
- `AutoLiquidityAdded`: auto-LP balances become `meme_pending`/`quote_pending`; principal rises by
  the added amounts. It can appear without `FeesCollected`, when only earlier leftovers were added.
- `FeeSplitChanged`: adopt `new_generation` and `new_fee_split`.
- `CreatorFeesClaimed`, `ProtocolFeesClaimed`, `ProtocolLpFeesClaimed`: the matching balances become
  zero (each claim takes everything). `CreatorFeesClaimed` names no recipient; the coins go wherever
  the PTB sends them.
- `BuybackBurned`: `burn_quote` becomes `quote_pending`; `meme_burned` left the supply (or went to
  `@0x0`).
- `RoundPublished`: rewards balances become `meme_unallocated`/`quote_unallocated`; `next_round`
  becomes `number + 1` and `last_checkpoint` becomes `end_checkpoint`; record the round's budget
  under `round_id`.
- `RewardPaid`: find the round by `round_id`; its funds become `meme_remaining`/`quote_remaining`;
  mark `index` paid.

A collection that finds no fees emits no `FeesCollected` and changes no balance except through
auto-LP. The replay reproduces every vault balance exactly.

### Aborts

Codes are per module. This package's errors carry their constant name and code; the launchpad and
Blast admin abort with plain numeric codes from the named module.

| Flow | Abort | Fix |
| --- | --- | --- |
| any | code 13 from Blast admin's `operational_version` module | Call the current package address with the current `PackageVersion` objects; pass the launchpad's too on `new`/`migrate`. |
| Cetus `migrate` | `EInvalidCoinOrder` (0, module `cetus`) | Swap `CoinA` and `CoinB`. |
| Cetus routes | `EWrongCoinPair` (2, module `cetus`) | `CoinA`/`CoinB` must be exactly the launch's Meme and Quote. |
| collect, settle, buyback | `EPositionPoolMismatch` (Cetus 1, Bluefin 0) | Pass the pool whose ID is the vault's `pool_id`. |
| Bluefin `new` | `EInvalidTier` (1, module `bluefin`) | Tick spacing 1..=400, fee rate 1..=20,000. |
| `migrate` | code 15 from the launchpad's `launch` module | The launch is not `MigrationReady` (not graduated, or already migrated). |
| `migrate` | code 21 from the launchpad's `launch` module | Use the venue the launch started with. |
| `migrate` | `EZeroLiquidity` (3, module `vault`) | The seed produced no liquidity; nothing to fix by retrying. |
| creator claim, split update | code 22 from the launchpad's `launch` module | Use the launch's live `CurveFeeCap`. |
| creator claim | `ENoCreatorFees` (2, module `vault`) | Collect first, or wait for fees. |
| split update | `EFeeSplitUnchanged` (1, module `vault`) | Propose a different split. |
| split construction | codes 6, 7, 8, 24 from the launchpad's `allocation` module; 0 from its `bps` module | Nonzero destination, sum exactly 10,000, at most 16 recipients, no duplicates, each BPS ≤ 10,000. |
| partner payout | `EPartnerMismatch` (6, module `vault`) | Pass the `Partner` whose ID is the vault's `partner_id`; vaults without a partner have no payout. |
| buyback | `ENoBuybackQuote` (4), `EBuybackBelowMinimum` (5), module `vault` | Wait for burn Quote; lower `min_meme_out` or retry at a better price. |
| residual claim | `ENothingClaimable` (0, module `vault`) | Nothing left to claim. |
| publish round | `EWrongRound` (0), `EInvalidInterval` (1), `EInvalidCommitment` (2), `EInvalidLeafCount` (3), `EEmptyBudget` (4) in `blast_holder_rewards` | Use `next_round`, a contiguous interval, 32-byte digests, 1..=65,536 leaves, a nonzero budget within the rewards balance. |
| reward claim | `EInvalidIndex` (5), `EAlreadyClaimed` (6), `EInvalidBeneficiary` (7), `EEmptyBudget` (4), `EInvalidProof` (8) in `blast_holder_rewards` | Pass the leaf exactly as committed with its full-depth proof; each leaf pays once. |
| policy | `EProtocolDestinationUnchanged` (0), `EProtocolFeeSharesUnchanged` (1) in `lp_fee_policy` | Change the stored value. |

Venue-side aborts (Cetus or Bluefin refusing a tier, a pair, or a fee amount) carry the venue's own
codes.

### Pitfalls

- **Cetus coin order.** Every Cetus route after `new` takes `<Meme, Quote, CoinA, CoinB>`, with
  `CoinA`/`CoinB` in Cetus's order, not launch order. On routes that take a pool, the pool's type
  already fixes the order. Bluefin routes take only `<Meme, Quote>`.
- **Two version objects.** `new` and `migrate` need both this package's `PackageVersion` and the
  launchpad's. Other calls need only this package's.
- **Two kinds of creator fees and protocol fees.** `launch::claim_creator_fees` pays bonding-curve
  fees; `blast_fun_migrators::vault::claim_creator_fees` pays LP fees. Each package has its own
  `CreatorFeesClaimed` and `ProtocolFeesClaimed` event; decode by full type.
- **Partnered vaults do not pay Blast at collection.** `FeesCollected.protocol_destination` is none
  and the share waits until someone calls the partner payout.
- **Not every call emits `FeesCollected`.** A collection that finds no fees emits none, but auto-LP
  can still add earlier leftovers with only `AutoLiquidityAdded`.
- **Auto-LP leftovers are normal.** One side always has excess after an add, and a one-sided balance
  waits for the other asset. Leftovers are not lost.
- **`claim_creator_fees` aborts on an empty balance.** Check `creator_meme`/`creator_quote` or
  collect in the same PTB first.
- **Bluefin migration costs SUI and sets a manager.** The caller supplies the exact Bluefin creation
  fee and becomes the pool's Bluefin manager.
- **Merkle details.** Leaves bind the vault ID (not the round ID) and the round number; the odd last
  node pairs with itself; proof length must equal the tree depth exactly.
- **Holder rewards are paid only to the beneficiary.** A relayer pays gas and receives nothing.
- **Upgrades.** After an upgrade, calls to the old package address abort; type names still use the
  original address, so per-coin policy keys and event filters do not change.

### Q&A

**Who triggers migration, and is there a reward?** Anyone, once the launch is `MigrationReady`, by
calling the venue's `migrate`. The caller pays gas (and on Bluefin the SUI creation fee) and
receives no object or reward. On Bluefin the caller becomes the pool's Bluefin manager.

**Can the creator or Blast withdraw the liquidity?** No function removes a position from the vault.
The Cetus migration liquidity is burned through Cetus LP Burn. The Bluefin position and the Cetus
auto-LP position have no removal path in the current code, which an upgrade of this package could
change.

**How do I find a launch's vault and pool?** Scan `VaultCreated` events for the `meme` type name;
the match gives `vault_id`, `pool_id`, and `position_id`. The vault's type is
`LpVault<Meme, Quote>`, and its `pool_id` field also names the pool.

**How does a creator get LP fees?** Call `collect_fees` (anyone can), then
`blast_fun_migrators::vault::claim_creator_fees` with the launch and the live `CurveFeeCap`, in one
PTB if you like. The call returns two coins the PTB must transfer.

**How much does Blast take?** Read `LpFeePolicy`: the coin's own pair if present, else the defaults,
applied as `ceil(gross × bps / 10,000)` per asset before the split. Blast can change it at any time,
from the next collection.

**How often should fees be collected?** Any time; it is permissionless and a zero collection is
harmless. Frequent collection keeps each auto-LP add small, which limits what a price mover can
skim.

**What happens to the burn share?** The Meme part is burned in the same collection (or sent to
`@0x0` when the supply is not burn-only). The Quote part waits in `burn_quote` until a Blast
`BuybackAdmin` swaps it for Meme with a minimum out and disposes of that Meme the same way.

**How do holders claim rewards?** Blast publishes a round with a Merkle root; a holder (or any
relayer) calls `blast_holder_rewards::claim` with the leaf's index, beneficiary, amounts, and proof.
The coins go to the beneficiary. Claims never expire, and each leaf pays once.

**Can the fee split change after migration?** Yes. The live `CurveFeeCap` holder calls the venue's
`settle_and_update_fee_split`, which first collects and splits pending fees under the old split,
then commits the new one as the next generation.

**When does a partner get its cut of LP fees?** When anyone calls
`blast_fun_migrators::vault::claim_protocol_lp_fees_with_partner` on the vault. It pays the partner
its share in force at that moment, rounded down, and Blast's destination the rest.

## Partner codes

> **Deployment status:** `blast_partners` is live on mainnet.

### What it is

A partner code lets an app that brings flow to Blast earn a share of the fee
Blast charges on that flow. Package `blast_partners` holds the codes for every
Blast product: Boosts, the launchpad (with its post-migration LP vaults), and
presales. A partner is one deal: a shared `Partner` object with a share of
Blast's fee (0% to 80%) and a recipient address. A company holds one
`PartnerCap` that controls the recipient of every deal registered under it.
Users never pay for a partner: a partner is only ever paid out of Blast's own
fee. Every change Blast makes to a partner's share or managing cap waits seven
days, and the package is published immutable, so no one can shorten that delay.

### Objects and authority

| Object | Kind | Held by | Authorizes |
| --- | --- | --- | --- |
| `blast_partners::blast_partners::Partner` | shared (`key` only, never transferable) | nobody; created by `blast_partners::blast_partners::register` | read by products on every trade; mutated only by the calls below |
| `blast_partners::blast_partners::PartnerCap` | owned (`key, store`; transferable, wrappable) | the partner company | `blast_partners::blast_partners::set_recipient` on every `Partner` whose cap in force is this cap's ID |
| `blast_partners::blast_partners::PartnerAdmin` | role type in Blast's ACL | a Blast `AdminCap` granted this role | `blast_partners::blast_partners::register`, `blast_partners::blast_partners::schedule_share`, `blast_partners::blast_partners::schedule_cap` |

`Partner` fields:

- `recipient: address`: where payments go. Set by the live cap's holder, applies
  at once.
- `share_bps`: the share of Blast's fee, in basis points (BPS, out of 10,000),
  at most 8,000. A timelocked value.
- `cap_id`: the ID of the one `PartnerCap` that may set `recipient`. A
  timelocked value.

A timelocked value is a `Timelocked<T>` struct from Blast's immutable timelock
package with four fields: `before`, `after`, `at_ms`, `delay_ms`. The value in
force at time `t` (milliseconds) is `after` when `t >= at_ms`, otherwise
`before`. `delay_ms` is fixed at creation; for partners it is 604,800,000 ms
(seven days). Scheduling a value `v` at time `now` sets `before` to the value in
force at `now`, `after` to `v`, and `at_ms` to `now + delay_ms`. A change is
pending exactly when `at_ms > now` and `after` differs from the value in force.

Who may call: *anyone* may call `new_cap`, `destroy_cap` (on a cap they hold),
`pay`, and `delay_ms`; the *cap holder* (the `PartnerCap` in force) may call
`set_recipient`; a *Blast admin* with the `PartnerAdmin` role (through
`blast_acl::sign_in`) may call `register`, `schedule_share`, and `schedule_cap`.
Each product keeps its own list of the partners it accepts, managed by that
product's admin.

### Lifecycle

**Cap.** `blast_partners::blast_partners::new_cap` mints an inert cap: it
controls nothing until Blast registers a partner under its ID. It is *live* for
a partner while it is that partner's cap in force. After
`blast_partners::blast_partners::schedule_cap` names a different cap and seven
days pass, the old cap stops working for that partner.
`blast_partners::blast_partners::destroy_cap` deletes a cap, live or not;
destroying a live cap leaves its partners with no working cap until a cap Blast
schedules with `blast_partners::schedule_cap` takes effect, seven days later.

**Partner.** `blast_partners::blast_partners::register` creates and shares the
partner with its share and cap in force immediately (`before == after`,
`at_ms == 0`). From then on:

1. Blast schedules a new share or cap; the old value stays in force for seven
   days.
2. Scheduling again before then replaces the pending change and restarts the
   seven days.
3. Scheduling the value currently in force cancels a pending change.
4. At `at_ms` the new value is in force; nothing needs to be called.

There is no delete: a partner exists forever. To switch it off, Blast schedules
its share to zero; products that name it keep working and simply pay it nothing.

**Product acceptance.** Each product accepts a partner in its own shared config,
as a dynamic field keyed by `PartnerKey(partner_id)` whose `u64` value is the
time the partner stops being accepted (`u64::MAX` until removed):

| Product | Config object and key | Admin |
| --- | --- | --- |
| Boosts | `blast_boosts_aftermath::blast_boosts_aftermath::Protocol`, `blast_boosts_aftermath::blast_boosts_aftermath::PartnerKey` | `RiskAdmin` role (`operations::add_partner`, `operations::remove_partner`) |
| Launchpad | `launch_config::LaunchConfig`, `launch_config::PartnerKey` | `FeeAdmin` role (`launch_config::add_partner`, `launch_config::remove_partner`) |
| Presale | `creation_policy::CreationPolicy`, `creation_policy::PartnerKey` | presale `FeeAdmin` role (`creation_policy::add_partner`, `creation_policy::remove_partner`) |

Adding applies at once (and cancels a pending removal). Removing sets the value
to `now` plus `blast_partners::blast_partners::delay_ms()`: the partner stays
accepted for seven more days. A partner is accepted while the field exists and
`now < value`.

### Flows

#### Become a partner (company)

1. Call `blast_partners::blast_partners::new_cap` (*anyone*). It returns a
   `PartnerCap`; send it with a TransferObjects command to the address that will
   manage your deals (for example your multisig).
2. Give Blast the cap's object ID, the recipient address, and the agreed share.
3. Blast's partner admin, in one PTB: `blast_acl::sign_in` with type argument
   `blast_partners::blast_partners::PartnerAdmin`, passing the shared `ACL` and
   its owned `AdminCap`; then `blast_partners::blast_partners::register` with a
   reference to that `AdminWitness<PartnerAdmin>`, your cap ID, the recipient,
   and the share. The new `Partner` is shared; its ID is in the `PartnerUpdated`
   event and the transaction's created objects.
4. Blast's admin for each product adds the partner to that product's list.

`blast_partners::blast_partners::register` accepts any ID as the cap. Confirm on
chain that the `Partner`'s `cap_id` equals your cap's ID; a wrong ID can only be
fixed by `blast_partners::blast_partners::schedule_cap`, seven days later.

#### Change where a partner pays you (cap holder)

1. Call `blast_partners::blast_partners::set_recipient` with the shared
   `Partner` (mutable), your owned `PartnerCap` (by reference), the new address,
   and `Clock` at `0x6`.
2. It applies at once and emits `PartnerUpdated`. One call per partner.

#### Change a share or replace a lost cap (Blast admin)

1. `blast_acl::sign_in` with `blast_partners::blast_partners::PartnerAdmin`.
2. `blast_partners::blast_partners::schedule_share` (new share) or
   `blast_partners::blast_partners::schedule_cap` (new cap ID), with the shared
   `Partner`, the witness, the value, and `Clock`.
3. Each emits `PartnerUpdated` with the complete timelocked terms. The change
   takes effect seven days later. Until a cap change takes effect, the old cap
   keeps working, including for a thief holding it.

#### Pay a partner (products, or anyone)

`blast_partners::blast_partners::pay<T>` takes the shared `Partner` by immutable
reference, a `&mut Balance<T>` holding Blast's fee on a trade, `Clock`, and the
transaction context. It splits off `floor(fee * share_in_force / 10,000)`, sends it to the partner's
`recipient`, emits `PartnerPaid<T>`, and returns the amount. The rest stays in
the caller's balance. With a zero share (or a fee too small to round above zero)
it sends nothing, emits nothing, and returns 0. Each positive payment creates
a `Coin<T>` and transfers it to the recipient with `public_transfer`. Integrators
never call `pay` directly; products call it inside their own partnered functions.

### How each product uses a partner

| Product | When the partner is named | Blast fee divided | Payment |
| --- | --- | --- | --- |
| Boosts | on each trade: `operations::mint_with_partner` or `operations::redeem_with_partner`, passing the `Partner` right after the `Protocol` | Blast's admin fee that trade retained; never the reserve fee | push: paid in the same call |
| Launchpad | once, at creation: `launch::set_partner` on the `LaunchInitializer` before `launch::finalize`; fixed for good | Blast's whole fee ledger on the launch: the creation fee (SUI), Blast's share of every curve trade fee (Meme and Quote), and Blast's one-time migration fee | held in the launch; paid when anyone calls `launch::claim_protocol_fees_with_partner` |
| Launchpad LP vault | inherited from the launch at migration | Blast's LP fees on each collection | held in the vault; paid when anyone calls `blast_fun_migrators::vault::claim_protocol_lp_fees_with_partner` |
| Presale | once, at creation: `blast_presale::blast_presale::set_partner` on the `PresaleInitializer` before `blast_presale::blast_presale::finalize`; fixed for good | Blast's raise fee (Quote) only; Blast's token fee is never divided | held at migration; paid when anyone calls `blast_presale::blast_presale::pay_protocol_fees_with_partner` (once) |
| Presale LP vault | inherited from the sale at migration | Blast's LP fees on each collection | held in the vault; paid when anyone calls `presale_vault::pay_protocol_lp_fees_with_partner` |

Rules common to every product:

- Naming a partner requires that the product accepts it at that moment;
  otherwise the call aborts. Launches and sales that already name a removed
  partner keep paying it.
- The claim and payment calls are *anyone*: both payees are fixed, so no caller
  chooses where money goes. Each checks that the `Partner` passed is the one the
  launch, sale, or vault named, and aborts otherwise.
- A launch that names a partner cannot use `launch::claim_protocol_fees`; it
  must use `launch::claim_protocol_fees_with_partner`.
- Held fees are divided at the share **in force when they are paid**, not when
  they accrued.
- The `Partner` is read by immutable reference, so naming a busy partner adds no
  contention of its own.

### Economics

- Partner amount per payment: `floor(fee * share_bps / 10,000)` in atomic units
  of `T`, where `share_bps` is the share in force at the payment's `Clock`.
  Blast keeps the remainder, including every rounding dust.
- `share_bps` is between 0 and 8,000 (80%). Blast always keeps at least 20% of
  its fee.
- Users, holders, creators, buyers, and pools receive exactly the same amounts
  with or without a partner.
- Example (Boosts): a mint retains a 15.00 USDC admin fee and the partner's
  share is 4,000 BPS. The partner receives 6.00 USDC; Blast keeps 9.00 USDC.
- Example (presale): Blast's raise fee is 2,000 USDC and the share is 4,000 BPS.
  The partner receives 800 USDC; Blast keeps 1,200 USDC and all of its token
  fee.

### Time rules

- Delay: `blast_partners::blast_partners::delay_ms()` returns 604,800,000 (seven
  days). It is a compile-time constant of an immutable package.
- A scheduled share or cap is in force from the first transaction whose `Clock`
  reads `at_ms` or later.
- A recipient change applies in the same transaction.
- A product removal keeps the partner accepted until `now + delay_ms()`; a trade
  or creation at or after that time aborts.

### Reading state

`blast_partners` has no getters for a partner's fields; read the shared
`Partner` object's content over RPC (`recipient`, `share_bps`, `cap_id`) and
apply the timelock rule above, or replay `PartnerUpdated`. The only on-chain
read is `blast_partners::blast_partners::delay_ms`.

- Share in force now: `share_bps.after` if `now >= share_bps.at_ms`, else
  `share_bps.before`.
- Pending share change: `share_bps.at_ms > now` and `share_bps.after` differs
  from the share in force.
- Which cap controls the recipient: the same rule on `cap_id`.
- Whether a product accepts a partner: read the product config's dynamic field
  `PartnerKey(partner_id)`; accepted while it exists and `now < value`.
- Which partner a launch, sale, or vault names: its `partner_id: Option<ID>`
  field (`launch::partner_id` returns it for a launch).

### Events

Both events are emitted directly (no envelope).

- `blast_partners::blast_partners::PartnerUpdated`: emitted by
  `blast_partners::blast_partners::register`,
  `blast_partners::blast_partners::schedule_share`,
  `blast_partners::blast_partners::schedule_cap`, and
  `blast_partners::blast_partners::set_recipient`. Fields: `partner_id`,
  `recipient`, `share_bps` and `cap_id` (complete timelocked values). Each event
  is the full current state, so the latest one per `partner_id` reconstructs the
  partner.
- `blast_partners::blast_partners::PartnerPaid<T>`: emitted by
  `blast_partners::blast_partners::pay` when it sends a positive amount. Fields:
  `partner_id`, `amount` (atomic units of `T`). The product records the trade in
  its own event in the same transaction:
  `blast_boosts_aftermath::events::PartnerFeePaid` (Boosts),
  `blast_fun::events::ProtocolFeesClaimed` (launch claims),
  `blast_fun_migrators::blast_events::ProtocolLpFeesClaimed` (launchpad LP),
  `blast_presale::blast_presale::ProtocolFeesPaid` (presale raise fee), and
  `presale_vault::ProtocolLpFeesPaid` (presale LP).
  `blast_fun::events::LaunchCreated` and
  `blast_presale::blast_presale::PresaleOpened` record the partner a launch or
  sale names.

### Aborts

| Code | Constant | Raised by | Fix |
| --- | --- | --- | --- |
| 0 | `EInvalidRecipient` | `register`, `set_recipient` | use a non-zero recipient |
| 1 | `EShareAboveMax` | `register`, `schedule_share` | share at most 8,000 BPS |
| 2 | `EUnchanged` | `schedule_share`, `schedule_cap` (value equals the latest scheduled value), `set_recipient` (same recipient) | pass a different value; to restart a pending change with the same value, first schedule the value in force |
| 3 | `ENotLiveCap` | `set_recipient` | use the cap in force for this partner at the current `Clock` |

All four are raised in module `blast_partners`. A product call that names a
partner it does not accept, or passes the wrong `Partner` to a claim, aborts in
that product's module with that product's own error.

### Pitfalls

- `PartnerPaid` alone does not prove a Blast trade:
  `blast_partners::blast_partners::pay` is public, and anyone can pay a partner
  from their own balance. Pair it with the product event in the same
  transaction.
- Each positive payment arrives as an owned `Coin<T>` at the recipient address.
  Repeated payouts produce separate coins that the recipient can merge.
- On Boosts, check acceptance before building a partnered trade; otherwise call
  the plain `mint` or `redeem`.
- On the launchpad and presales the partner is fixed at creation. Forgetting
  `launch::set_partner` or `blast_presale::blast_presale::set_partner` cannot be
  fixed later.
- Held fees are divided at the share in force at payment time. A scheduled cut
  to zero also cuts fees accrued earlier but paid later.
- Whoever holds the cap controls the recipient of every deal under it. A stolen
  cap can redirect payments until a `schedule_cap` replacement takes effect.

### Q&A

**How much can a partner earn?** Up to 80% of Blast's fee on the flow that names
it, as agreed with Blast and set by `blast_partners::blast_partners::register`.
Users pay the same fee with or without a partner.

**When am I paid?** On Boosts, in the same transaction as each mint or redeem.
On the launchpad and presales, when anyone calls the product's `*_with_partner`
claim or payment call; you may call it yourself.

**In which asset am I paid?** In the asset of the fee divided: Boost collateral;
launch Meme, Quote, and SUI; presale Quote; LP fees in both pool assets.

**Can Blast change my share without notice?** No. Every share or cap change
waits seven days, visible on chain the moment it is scheduled, and the delay is
fixed in immutable code.

**Can I change my recipient myself?** Yes, with your `PartnerCap` through
`blast_partners::blast_partners::set_recipient`; it applies at once.

**I lost my cap. What now?** Mint a new cap with
`blast_partners::blast_partners::new_cap` and ask Blast to call
`blast_partners::blast_partners::schedule_cap` for each of your partners. The
new cap works seven days later; until then the old cap still works.

**Can one company have several deals?** Yes. Each deal is its own `Partner` with
its own share and recipient; one `PartnerCap` can manage all of them.

**Can another app use my partner code?** Yes. The `Partner` is a public shared
object; any app can name it on a product that accepts it, and you earn on that
flow.

**How do I reconcile income?** Sum `PartnerPaid<T>` by `partner_id` and coin
type, and join each with the product event in the same transaction for trade
detail.

**Can I charge my own users an extra fee?** Not through `blast_partners`. Take
your own fee in your own PTB commands (split it from the user's coin and send it
where you like); Blast takes no cut of it.

### `blast_fun_migrators::cetus`

Cetus launch start, pool-creation reservation, migration into vault custody, and collection.  Anyone holding Meme can create a Cetus pool, and Cetus allows one pool per pair and tick spacing, so a buyer could pre-create the migration pool at a price of their choosing. Starting the launch therefore mints the Meme type's single Cetus `PoolCreationCap` from the ticket's treasury capability, before any Meme can leave the ticket, and registers the pair at the creator's tick spacing; afterwards only that capability or Cetus's pool-manager role can create the pair's pool there. Trusting that role is a venue-operator assumption: a pool it creates first makes the pair's migration abort, and only a migrators upgrade could recover the launch. The capability stays in `VenueConfig` under a key only this module constructs, with no extraction or unregistration path.  Migration burns the full-range position through Cetus LP Burn, so Cetus itself records the launch liquidity as permanently locked; the vault keeps the `CetusLPBurnProof`, which can only collect fees. A burned position cannot receive liquidity, so auto-LP adds to a second full-range position the vault opens on first use and keeps with no removal path.  Cetus orders a pool's coin types by type name. Each route after `new` takes the pool's coin types as `CoinA` and `CoinB` beside the launch's `Meme` and `Quote`, proves they are the same pair, and retypes balances between the two orders through a checked dynamic-field round trip (ADR 0100).

### `blast_partners::blast_partners`

Blast partner codes, shared by every Blast product.  A partner is one deal: it is paid a share of the fee Blast charges on every trade that names it, in the same transaction. A company holds one `PartnerCap` for all its deals, each a separate partner with its own share. Blast's partner administrator registers partners under a cap, sets each one's share, and can move a partner to another cap; the cap's holder sets where each of its partners is paid. Everything Blast changes takes effect only `DELAY_MS` after it is scheduled, and this package is published immutable, so no one can shorten that delay. The recipient the cap holder sets applies at once.  Products call `pay` with Blast's own fee on a trade. `pay` emits `PartnerPaid` for what the partner received; the product records the trade and the amount in its own event.

Source: https://github.com/interest-protocol/blast-v2-contracts/blob/main/sui/partners/sources/blast_partners.move
