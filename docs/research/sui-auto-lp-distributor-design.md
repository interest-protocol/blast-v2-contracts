# Standalone auto-LP fee distributor

Design, 2026-09-05. The user approved the standalone, permanently committed
cap and LP custody design and confirmed the first release has no balancing
swaps: deposit the supported portion of both balances once, retain leftovers,
and leave any further handling of excess assets to a future design.
This document is not an implemented contract or verification of deployed packages.

Latest refinement: the user selected volume-driven fee rates, swap-time burns,
and **all fees held separately from reserves**, including LP fees. The
[volume-fee and burn design](blast-v2-volume-fees-and-burn-design.md) supersedes
this document's reserve-retained LP compounding descriptions. The auto-LP
vault instead claims its LP fees and reinvests them explicitly.

## Clarified destination: Blast V2 funded by creator fees

The user's latest proposal keeps migration on the selected external DEX and
uses a separate Blast-owned V2-style constant-product pool as the destination
for reinvested creator fees. The user subsequently added direct migration into
Blast V2 as an optional future route, while retaining external choices; it is
not a mandatory migration destination. This refinement supersedes the same-pool destination
recommendation below; the external-pool adapter comparison remains research.

The source flow is unchanged: collect fees on the existing locked migration
position, apply its existing fee split, and claim the creator entitlement with
the cap held in the auto-LP vault. Join those Meme/Quote coins with prior idle
balances, then deposit the supported pair into the bound Blast V2 pool. Retain
the LP shares permanently in vault custody and keep every unmatched unit for
later. Previously accrued curve creator fees can fund the same destination.
Neither original migration principal nor protocol-owned fee entitlement moves.

For an initialized V2 pool with reserves `(R_meme, R_quote)`, choose deposit
amounts proportional to those current reserves, bounded by both available
balances, using integer rounding that conserves assets and does not overmint
LP shares. Initial seeding needs its own explicit starting-price and initial
LP-issuance rules because an empty pool has no reserve ratio. No swaps or
excess-consumption loops are introduced.

Fees earned by the Blast V2 LP position can stay in reserves and compound as
swaps execute. The vault benefits according to its LP share. External fee
claims and new deposits still need submitted transactions. Aggregators would
need to integrate Blast V2 for routed trading; depositing fees alone does not
guarantee trade volume or give the vault fees from unrelated positions.

This separates two integration surfaces: fee collection for every supported
source DEX, and one deposit implementation for Blast V2. External DEX deposit
adapters are unnecessary for this destination. A new AMM still needs complete
swap, reserve, LP-issuance, custody and quote semantics; it is more than a
balance-holding fee vault. The proposal settles where to direct creator fees,
not an ability to capture all fees generated by the coin anywhere.

The [PumpSwap comparison](blast-v2-pumpswap-tradeoffs.md) evaluates that future
migration option, a possible zero SUI migration fee, native burns and dynamic
fees while retaining a small constant-product AMM scope. None requires a V3
or DLMM engine or changes the agreed absence of balancing swaps.

## Recommendation

Offer auto-LP alongside the proposed holder-rewards distributor. A creator
deposits the existing `CreatorCap<Meme>` into a shared vault. The vault claims
creator fees in Meme and Quote, adds usable amounts to its own locked position
in the selected migration pool, and retains unmatched balances for later.

Keep this a standalone package, consistent with the previously confirmed
boundary in [the holder-rewards proposal](sui-holder-rewards-architecture.md).
The launchpad and existing migrators need no new integration hooks. The new
package depends inward on their public claims and directly on its supported
venues. Cover all five current migration venues: Bluefin, MMT, Cetus, Turbos,
and Aftermath. Each requires deposit and collection verification; a single
venue implementation must not be presented as complete support.

The vault owns a second position in the same pool. The original migrated
position remains under its existing custody and fee split. The second position
adds liquidity to that same market and compounds its own net venue fees.

## Alternatives

| Approach | Tradeoff |
| --- | --- |
| Separate locked position, no swaps — recommended | Standalone custody; small execution surface; unmatched fees can sit idle |
| Increase the original migration position | Reuses one position, but requires new migrator deposit APIs and an amendment to its collection-only boundary; future fees follow the existing protocol/creator split |
| Separate position with automatic balancing swaps | Uses more one-sided fees, but adds execution fees, price impact, manipulation exposure, and a swap-pricing policy |

No-swap compounding is intentionally incomplete capital utilization. Repeated
calls cannot make a missing asset appear. An imbalanced fee stream may leave a
large balance idle indefinitely; the UI must show idle balances separately
from deployed liquidity. Swaps would be a separately reviewed extension.

## Deposit once and retain the excess

The [all-venue audit](sui-auto-lp-all-venue-audit.md) supersedes the earlier
two-venue feasibility evidence. All five expose suitable deposit primitives,
but Aftermath charges its DAO fee on offered balances before proportional
sizing. Size its offered coins before the call so leftover funds are not
repeatedly assessed. Existing interfaces need extensions for Turbos position
increases and Aftermath wrapper deposits. Bytecode verification is recorded;
full vault execution fixtures are still required.

Each compounding call considers both accumulated balances, including prior
leftovers, and deposits the largest supported portion using the destination
venue's deposit mechanism. Join returned excess back into the vault, or leave
unspent balances there when the venue instead requests exact payment. A
nonzero residual is a successful outcome, not a reason to reject the deposit.
Do not inherit migration's near-total-utilization requirement: recurring fees
need not match the pool's current deposit ratio.

The existing MMT adapter demonstrates a deposit returning both residual coins.
The Cetus interface instead fixes one input amount and returns a linear
receipt whose accessor gives both required payment amounts. The wrapper must
choose a supported amount and limiting side before creating that receipt,
then pay those exact amounts and keep the rest. It cannot abandon a receipt
or catch an abort and retry inside Move. Reuse venue sizing helpers where
available; verify rounding and both balance limits before executing a deposit.

Perform one deposit per invocation. Do not loop over the remainder or swap it.
When no positive liquidity can be funded, skip the deposit and retain the
balances. A later invocation includes new fees and previous leftovers, which
may then form another usable pair. This supports ordinary fee reinvestment;
it does not guarantee that most fee value will be deployed when the fee stream
is persistently one-sided.

## Future destination-pool balancing extension (outside v1)

Use the exact bound destination pool if balancing is added. No aggregator,
intermediate token, arbitrary route, or caller-selected recipient is necessary.
A single atomic operation can swap excess inventory, settle the venue receipt,
add supported liquidity at the resulting price, and retain both residuals.
An aborted deposit rolls back the preceding swap in that transaction too.

Selling half is a useful approximation only for a one-sided balance and a
position needing roughly equal asset values, with negligible fees and price
impact. For example, at one Quote per Meme with a 50/50 value target, 100 Meme
and 40 Quote need approximately 30 Meme sold: 70 Meme and 70 Quote remain.
Selling 50 Meme would leave 50 Meme and 90 Quote. Real CLMM sizing must use
the fixed range's required ratio and account for the swap changing the price,
fees, tick crossings, and rounding. Exact optimization is unnecessary if a
bounded approximation leaves residuals safely available for subsequent runs.

Existing migration dependencies help with integration, but are not evidence
that every swap interface is already vendored or verified. At inspection,
`sui/migrators/interfaces/cetus/sources/pool.move` exposes position creation,
liquidity deposits, fee collection, and pool reads, but no swap functions.
Adding Cetus swaps requires pinned swap and repayment signatures plus live-ABI
and execution verification. Consult the venue's [swap documentation](https://cetus-1.gitbook.io/cetus-developer-docs/developer/via-sdk/features-available/swap)
and [deposit documentation](https://cetus-1.gitbook.io/cetus-developer-docs/developer/via-sdk/features-available/add-liquidity).

For permissionless execution, the wrapper must constrain spend, direction,
destination, and acceptable execution through its own policy. A malicious
caller can choose zero minimum output; a quote from the same manipulated spot
price cannot by itself establish fair execution either. The first swap-enabled
release needs a concrete price-reference policy, stale/unavailable-reference
behavior, and limits on loss and repeated turnover. Keep collection and
no-swap deposits available independently when a swap cannot satisfy that policy.
Do not add a dormant swap entry point before those decisions are settled.

## Authority and enrollment

For the smallest first release, enrollment happens after migration. The actual
capability holder commits the destination pool, source LP vault, launch, asset
pair, and venue during creation. The SDK verifies their migration provenance
before presenting the enrollment for signature. Contracts validate available
type, position, and pool relationships and freeze the destination; callers
cannot substitute it later.

The existing LP vault's `pool_id` getter is package-only. Do not claim a new
external package can independently discover and authenticate every canonical
migration association through the current public ABI. Initial destination
selection is creator-authorized. Fully permissionless automatic binding before
migration requires an additional source-authentication design and is deferred.

The cap is stored privately and never returned or lent, even by immutable
reference. Collection calls borrow it internally and retain both output coins
within the same Move call. Keep the separate metadata capability with its
owner. There is no caller-selected payout, cap recovery, LP withdrawal, or
public mutable UID accessor.

Recommended economic commitment: both the cap and reinvested LP are permanently
committed, and residual balances remain dedicated to future LP deposits. This
is opt-in and must be disclosed before enrollment. The package must become
immutable before the product promises an irreversible lock; upgradeable source
restrictions alone cannot establish that promise.

Holder rewards and auto-LP are separate choices for a launch in v1: one linear
cap cannot be deposited into both. A future mixed strategy requires one cap
custodian with a bounded, conserved allocation policy, not multiple cap owners.

## Execution

1. Anyone can trigger source venue fee collection through its current adapter.
   Its existing protocol/creator allocation remains in force.
2. The new vault claims creator-owned fees from the bound launch and source LP
   vault using the internally held cap, joining Meme and Quote into balances.
   Each source claim is independently callable, because existing claims abort
   when no fees are available. Do not make all sources mandatory in every run.
3. Collect fees earned by the new position without decreasing its liquidity.
   These net venue fees go entirely back into the auto-LP vault: the proposal
   adds no second Blast fee charge on the new position's earnings.
4. Compute the maximum liquidity supported by available balances at the fixed
   range and current venue price, using the venue's integer rounding rules.
   Open the position lazily when funding is sufficient; subsequently increase
   it. Derive full-range, tick-spacing-aligned bounds, not keeper-selected ticks.
5. Retain every unused unit in the appropriate typed balance. Verify the
   resulting position belongs to the bound pool and liquidity increased by the
   expected amount. No successful deposit may decrease principal.

Stop after that deposit even when a residual remains. If the available
balances support no positive liquidity, return without depositing; newly
collected fees remain in custody. Do not create an unsettled venue receipt on
this skip path.

Collection and investment should be separate public operations so inadequate
funding or a failed deposit guard does not prevent independent fee collection.
They may be composed in one PTB; failure then rolls back that entire PTB.
Insufficient funds should leave balances available for a later attempt.

No assets or position references escape through intermediate public results.
Venue-specific mint/deposit receipts are settled inside the wrapper call.
Conservation is checked per asset: opening idle balance plus receipts equals
deposits plus assessed venue/wrapper fees plus closing idle balance. Do not
count fees sent back to the source vault as a new auto-LP receipt until claimed.
Events record actual receipts, deposits, fees,
residuals, position identity, and final liquidity for replay; a keeper is not
reported as the fee beneficiary.

## Triggering, gas, and price bounds

Asset custody, claims, deposit arithmetic, and settlement can all run on-chain.
Execution still needs submitted transactions. A Sui clock supplies transaction
time; it does not schedule a future call. An endless Move loop exhausts the gas
budget instead of waiting for future fees. See [Sui on-chain time](https://docs.sui.io/sui-stack/on-chain-primitives/access-time)
and [Sui's transaction execution model](https://docs.sui.io/paper/sui.pdf).

Run a keeper that observes balances and submits transactions when a meaningful
deposit is possible. Its only privilege is paying gas; anyone can trigger the
same contract operations. Start with operator-funded SUI gas and no reward
deducted from the vault. A stopped keeper delays compounding while assets stay
in custody. Running continuously means a service submitting separate bounded
transactions, not a continuously executing contract.

Use venue amount bounds, minimum liquidity, and deadlines where supported.
Caller-provided slippage bounds protect an honest keeper from execution drift;
they do not constrain a malicious permissionless caller who chooses weak bounds.
Avoid claiming that no swaps eliminates pool-price manipulation: liquidity
deposits still use the current pool price. Before public release, validate the
venue's attack economics and either accept/document that exposure explicitly
or enforce a vault-owned policy against a sufficiently robust price reference.
An arbitrary launch-price anchor or a single current-price read is not a
substitute for that analysis. Swap-enabled compounding requires stronger price
protection and is outside this proposal.

## Venue distinctions and verification

CLMM fees accrue separately from position liquidity, so explicit collection
and reinvestment are required; see [Cetus fees](https://cetus-1.gitbook.io/cetus-docs/clmm/fees).
Aftermath base-pool trading fees already accrue into reserves, while Blast's
DAO-fee wrapper supplies separately claimable revenue. Its future auto-LP
adapter must deposit that revenue and retain the newly minted LP coins; it
must not withdraw existing LP to manufacture claimable fees. See
[ADR 0066](../decisions/0066-aftermath-dao-fee-pool.md).

Implementation acceptance must cover real cap enrollment; both fee sources;
no cap, balance, or principal extraction; frozen destination and pair ordering;
zero and one-sided balances; rounding and retained dust; collection without
principal loss; repeated principal increases; malicious caller bounds; atomic
failure; keeper outages; and replay conservation. Verify the chosen venue's
published ABI and deposit/collection behavior against live bytecode before
release. Local interface stubs alone cannot prove venue integration.

No executable code was changed or feature tests run for this design. The user
approved the custody and no-swap deposit behavior. Record the accepted protocol
decision and settle the concrete venue execution policy during implementation;
balancing swaps are outside the first release.

The clarified Blast V2 destination is described at the top of this document.
The [all-venue audit](sui-auto-lp-all-venue-audit.md) and
[fee comparison](sui-dex-fee-economics.md) remain evidence for the alternatives.
They do not change existing immutable pool bindings or authorize moving locked
principal.
